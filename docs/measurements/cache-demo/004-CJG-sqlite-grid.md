# 004 SQLite 원본의 전체 시나리오 grid

## 앞 기록과 달라진 점

- **범위:** 001\~003은 시나리오 일부만 쟀습니다. 이번에는 `cache_bench.py`의 시나리오 18개(상세 균등·집중, 목록 반복·다양, 검색 반복·다양 × 조회·수정 비율 100:0, 99:1, 90:10)를 TTL 60초와 2초로 모두 쟀습니다. 입력은 상품 10,000개 seed 1, 연결 32개, 초당 500요청, 준비 3초, 측정 10초, 2회입니다. 전체 실행은 32분이 걸렸습니다.
- **머신:** 001\~003은 macOS arm64에서 쟀고, 이번에는 WSL2에서 쟀습니다. 지연 숫자는 머신이 달라 001\~003과 나란히 비교하지 않습니다. 적중률과 원본 조회 횟수는 요청 계획으로 정해지므로 머신과 상관없이 비교할 수 있습니다.
- **코드:** 003(`82b93ad`) 뒤에 바뀐 코드는 다음과 같습니다. 데모(`demo/`)는 수정 요청의 `Content-Type` 검사를 좁혔고(`118fdef`), 원본 구현이 Linux에서도 빌드되게 고쳤고(`9b6c3da`), 팀 코드 규칙에 맞춰 이름, 상수, 함수 배치를 정리했습니다(`e600237`). mini-redis(`src/`)는 entry 해제 함수의 이름을 바꿨고(`b1ac565`), 헤더 64개를 넘는 요청을 `431`로, `Transfer-Encoding`이 있는 요청을 `411`로 거절하게 바뀌었습니다(`67548ea`, `2c0280a`). 이 측정의 요청은 `431`이나 `411`에 해당하지 않습니다. 정리한 커밋이 지연에 준 영향은 따로 재지 않았습니다.

## 결론

- **반복 조건:** 같은 조건을 반복하는 목록은 적중률 90\~100%로 원본 조회가 거의 사라지고, p50이 약 20\~32 ms에서 약 5\~9 ms로 줄었습니다. 같은 조건을 반복하는 검색은 원본 조회가 거의 사라졌지만, cache off의 p50이 약 5\~6 ms로 이미 작아서 cache on이 0.2\~2.5 ms 느렸습니다.
- **상세 조회:** 캐시를 켜면 p50이 약 1.3\~2.1 ms에서 약 7\~17 ms로 늘었습니다. 원본 조회는 적중률만큼 줄었습니다(TTL 60초에서 33\~53%). 단일 스레드 데모가 mini-redis 왕복을 기다리기 때문입니다.
- **다양한 조건:** 목록과 검색 모두 적중이 0%라서 왕복 비용만 더해지고, p50이 최대 약 2.2배 늘었습니다. cache on의 p95는 회에 따라 크게 흔들렸습니다(검색 다양에서 최대 약 496 ms). 원인은 확인하지 않았습니다.
- **TTL 2초:** 상세 조회의 적중률이 35.9%→11.3%(균등), 53.1%→22.5%(집중)로 떨어졌습니다. 같은 조건을 반복하는 목록과 검색은 TTL 2초에도 적중률이 99.9%였고, 원본 조회는 측정 10초 동안 5번이었습니다.
- **수정 비율:** 수정이 10%로 늘면 반복 조건의 적중률이 약 90%로 떨어졌습니다. 목록·검색 캐시 전체를 무효화하는 설계 때문입니다.
- **003과 같은 시나리오:** 적중률과 원본 조회 횟수(예: 상세 집중 99:1 TTL 60초 53.1%, 4,956→2,322)는 003과 같았습니다.
- **처리량:** 모든 시나리오에서 두 모드 모두 502.4/s(제안 부하 한도)였고, 오류와 timeout은 0이었습니다. 수정이 섞인 시나리오 12개의 모든 실행(96개)에서 측정 뒤 정확성 대조(12개 경로)가 일치했습니다. 조회 전용 시나리오 6개는 `cache_bench.py`가 대조하지 않습니다.
