# 005 요청이 고르게 도착할 때의 전체 시나리오 grid

## 앞 기록과 달라진 점

- **도착 모양:** 001\~004는 `cache_bench.py`가 연결 32개마다 64 ms 간격의 시간표를 두었고, 모든 시간표가 같은 시각에 시작했습니다. 그래서 64 ms마다 요청 32개가 한꺼번에 도착했습니다. 이번에는 시간표 하나가 2 ms마다 요청을 하나 내고 연결들에 차례로 맡깁니다(`3b8e6f6`, `--arrival even`). 연결 수, 초당 요청 수, 요청 계획, 지연을 재는 방법은 같습니다. 예전 모양은 `--arrival burst`로 남겼습니다.
- **잇는 측정:** 004와 이어 보려고 상세 균등, TTL 60초를 `burst`로도 2회 쟀습니다. 004와 같은 지연이 다시 나왔습니다(아래 "burst로 다시 잰 상세 균등").
- **코드:** 004(`0b27d7b`) 뒤에 `src/`와 `demo/`의 동작은 바뀌지 않았습니다. 바뀐 것은 측정 도구(`scripts/bench/cache_bench.py`)와 문서입니다.
- **요청 수:** 고르게 보내면 10초에 정확히 5,000개를 보내고, 004는 5,024개였습니다. 적중률과 원본 조회 횟수는 이 차이만큼 004와 조금 다릅니다.
- **머신과 입력:** 004와 같습니다. 상품 10,000개 seed 1, 연결 32개, 초당 500요청, 준비 3초, 측정 10초, 2회입니다. 전체 실행은 약 33분이 걸렸습니다.

## 결론

- **004의 상세 조회 지연은 대부분 측정 도구 때문이었습니다.** 상세 균등의 cache on p50은 `burst`에서 8.73\~8.98 ms(004는 8.57\~8.64 ms), `even`에서 0.44\~0.51 ms였습니다. 요청 32개가 한꺼번에 오면, 스레드 하나인 데모가 mini-redis 왕복을 기다리며 차례로 처리하므로 뒤쪽 요청이 앞 요청들의 처리 시간만큼 기다렸습니다.
- **고르게 도착해도 상세 조회는 캐시를 켜면 느립니다.** cache on의 p50이 0.34\~0.76 ms, cache off가 0.17\~0.35 ms였습니다. 적중률 53%인 상세 집중도 cache on이 느렸습니다. 같은 프로세스 안에서 SQLite로 상품 하나를 찾는 비용보다 mini-redis 왕복의 비용이 큽니다. 이 차이 가운데 mini-redis 자체의 비용이 얼마인지는 재지 않았습니다.
- **반복 조건의 목록은 캐시로 빨라졌습니다.** p50이 0.91\~1.10 ms에서 0.27\~0.45 ms로 줄었습니다. 반복 조건의 검색은 cache off도 0.31\~0.42 ms로 작아서 두 모드가 비슷했습니다.
- **다양한 조건에서 cache on이 크게 튀는 회가 남았습니다.** 네 시나리오에서 회 2개 가운데 하나의 p95가 203\~1,557 ms까지 늘었습니다. TTL 60초의 목록 다양 99:1과 90:10, 검색 다양은 그 회의 p50도 16\~423 ms였고, TTL 2초의 목록 다양 99:1은 p95만 203 ms였습니다. cache off에서는 이런 회가 없었고, 적중률이 0%라 요청마다 캐시 조회, 원본 조회, 캐시 저장을 모두 하는 시나리오에서만 나타났습니다. 고르게 도착해도 나타나므로 도착 모양 때문은 아닙니다. 원인은 확인하지 않았습니다.
- **TTL 2초와 수정 비율:** 적중률과 원본 조회 횟수는 004와 같은 모양입니다. 상세 조회의 적중률은 TTL 2초에서 11\~22%로 떨어졌고, 수정이 10%면 반복 조건의 적중률이 약 90%로 떨어졌습니다.
- **처리량과 정확성:** 모든 시나리오에서 두 모드 모두 500.00/s였고, 오류와 timeout은 0이었습니다. 수정이 섞인 시나리오 12개의 모든 실행(96개)에서 측정 뒤 정확성 대조(12개 경로)가 일치했습니다.
