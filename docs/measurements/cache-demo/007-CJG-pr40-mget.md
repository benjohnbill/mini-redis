# 병합 사슬 #40: 상세 조회의 캐시 요청을 POST /mget으로 묶음

## 앞 기록과 달라진 점

- **코드:** #39 단계(`fb598a7`)에 PR #40만 병합했습니다. mini-redis에 `POST /mget`이 생겼고(`src/api.c`), 데모가 같은 처리 바퀴의 상세 조회를 모아 두 건 이상이면 캐시에 한 번에 묻습니다. 같은 상품은 한 번만 묻습니다(`demo/product_demo.c`, `demo/cache_client.c`).
- **서버 코드:** `src/server.c`는 응답을 송신 버퍼로 복사한 뒤 `api_response_destroy`를 부르는 한 줄만 바뀌었습니다. 기존 GET 경로의 동작은 같으므로 서버 사슬은 다시 재지 않았습니다.
- **머신과 명령:** 앞 단계와 같습니다.

## 결론

**캐시를 켠 상세 조회가 크게 빨라졌습니다.** 캐시 왕복이 회마다 15,008번에서 약 1,200번으로 줄었기 때문입니다. 캐시를 끈 쪽은 앞 단계와 같습니다.

| TTL | 캐시 | #39 p50, 3회 (ms) | #40 p50, 3회 (ms) | 판정 |
|---|---|---|---|---|
| 60초 | off | 6.04, 5.96, 6.03 | 5.95, 5.75, 5.78 | 차이 없음 |
| 60초 | on | 5.59, 5.96, 5.98 | 3.22, 3.20, 3.27 | 약 45% 개선 |
| 2초 | off | 6.00, 5.92, 5.86 | 5.74, 6.27, 5.93 | 차이 없음 |
| 2초 | on | 10.35, 10.07, 10.38 | 8.35, 8.37, 8.39 | 약 19% 개선 |

- **TTL 60초(적중률 71.7%)에서 on이 off보다 확실히 빠릅니다.** 앞 단계에서는 on과 off가 거의 같았는데, 이제 on p50이 off의 약 55%입니다.
- **캐시 왕복 수:** TTL 60초 1회째에 `POST /mget` 782번이 key 14,565개를 실었고(묶음 하나에 평균 약 18.6개), 단건 GET은 418번 남았습니다. 앞 단계의 단건 GET 15,008번과 견주면 왕복이 약 1,200번으로 줄었습니다.
- **적중률이 71.8%에서 71.7%로 바뀐 것은 분모가 바뀌었기 때문입니다.** 같은 묶음의 같은 상품을 한 번만 물어서 캐시 조회 수가 15,008에서 14,982\~14,988로 줄었습니다. 원본 조회 수(4,239)는 같습니다.
- **TTL 2초(적중률 11.1%)는 아직 on이 off보다 약 2.5 ms 느립니다.** 미스마다 캐시 PUT을 하나씩 보내는 비용이 남아 있고, #41이 이 PUT을 묶습니다.
