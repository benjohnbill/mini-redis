# 병합 사슬 #39: 응답을 만든 직후 전송

## 앞 기록과 달라진 점

- **코드:** B2(`409f6b9`)에 PR #39만 병합했습니다. 데모가 요청 하나의 응답을 만들 때마다 `mg_io_send`로 바로 전송을 시도합니다. 전에는 같은 처리 바퀴의 요청을 모두 처리한 뒤에야 응답이 소켓에 쓰였습니다(`demo/product_demo.c`).
- **머신과 명령:** B2와 같습니다.

## 결론

**캐시 off와 on 모두 p50이 약 3분의 1 줄었고, TTL 60초에서 목표를 통과했습니다.** 몰려 온 요청 32개 중 앞쪽 요청이 뒤쪽 요청의 처리를 기다리지 않게 되었기 때문입니다.

| TTL | 캐시 | B2 p50, 3회 (ms) | #39 p50, 3회 (ms) | 판정 |
|---|---|---|---|---|
| 60초 | off | 8.69, 9.18, 8.84 | 6.04, 5.96, 6.03 | 개선 |
| 60초 | on | 10.03, 9.39, 9.14 | 5.59, 5.96, 5.98 | 개선 |
| 2초 | off | 8.60, 8.70, 8.70 | 6.00, 5.92, 5.86 | 개선 |
| 2초 | on | 16.64, 16.36, 17.39 | 10.35, 10.07, 10.38 | 개선 |

- **TTL 60초(적중률 71.8%)에서 on p50이 off p50보다 크지 않습니다.** 회마다 on 5.59, 5.96, 5.98 ms와 off 6.04, 5.96, 6.03 ms로, 2회째는 같고 나머지는 on이 작습니다. 차이가 작아서 아슬아슬한 통과입니다.
- **TTL 2초(적중률 11.3%)는 여전히 on이 off보다 약 4.3 ms 느립니다.** 적중률이 50% 미만이라 목표의 대상은 아니지만, 미스마다 캐시 GET과 PUT 왕복이 원본 조회에 더해지는 비용이 남아 있습니다. #40과 #41이 이 왕복을 묶습니다.
- **꼬리 지연도 줄었습니다.** TTL 60초 on의 p99가 16.85\~18.35 ms에서 14.76\~17.29 ms로, off의 p95가 11.20\~12.92 ms에서 10.74\~11.36 ms로 내려갔습니다.
- **원본 조회 수와 적중률은 B2와 같습니다.** #39는 응답을 보내는 시점만 바꿨기 때문입니다.
