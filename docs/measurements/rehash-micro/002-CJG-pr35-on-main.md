# #37과 SipHash 뒤에도 남은 #35의 조회 이득

## 앞 기록과 달라진 점

- **목적:** 병합 사슬의 [#35 서버 기록](../server/015-CJG-pr35-rehash-thresholds.md)에서 조회 이득이 서버 지연에 보이지 않아, 같은 코드에서 이득 자체가 남아 있는지 서버 없이 다시 쟀습니다.
- **코드:** 001(`7d2f5cf`) 뒤에 #37(rehash 나눠옮기기)과 #36(SipHash 1-2)이 store와 해시 테이블을 바꿨습니다. #35가 들어간 `main`(`409f6b9`)에서, 범위만 `-D`로 바꿔 (4, 2, 1)과 (2, 1, 0.5)를 견줍니다.
- **회 수:** 001의 3회보다 늘려 설정마다 5회를 번갈아 실행했습니다.

## 결론

**조회 이득은 남아 있습니다.** (2, 1, 0.5)의 조회 하나가 (4, 2, 1)보다 중앙값으로 key 100,000개에서 119 ns(16.5%), 1,048,576개에서 286 ns(19.1%), 4,194,304개에서 408 ns(22.3%) 빨랐습니다. 001의 약 25%보다 조금 작습니다.

- **key 100만 개 이상에서는 5회 범위가 겹치지 않습니다.** key 100,000개에서는 (2, 1, 0.5)의 1회째(751.0 ns)가 (4, 2, 1)의 범위(649.9\~889.6 ns) 안에 있습니다.
- **저장 평균도 빨라졌습니다**(4,194,304개에서 2,393.3 → 1,794.7 ns). 저장도 같은 key가 있는지 먼저 찾기 때문으로 봅니다.
- **치른 값:** 버킷 배열이 두 배이고, key 하나당 RSS가 약 8바이트(4%) 늘었습니다. 가장 긴 저장(버킷 배열을 새로 만드는 저장)은 4,194,304개에서 15.5\~28.8 ms가 29.2\~39.6 ms로 늘었습니다.
