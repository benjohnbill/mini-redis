# 새 버킷 배열을 버킷마다 처음 쓸 때 초기화함

## 앞 기록과 달라진 점

- **코드:** 버킷을 늘리거나 줄일 때 새 배열을 `calloc`으로 받고, 버킷마다 처음 쓸 때 `list_init`합니다(`src/hash.c`의 `bucket_ready`). 전에는 새 배열의 버킷 전부를 `rehash` 한 번에 초기화했습니다. 측정한 binary는 실험 브랜치의 `853dd85`로 빌드했고, 이 기록의 commit(`8860ac8`)과 `src/`가 같습니다.
- **설정:** 지금의 (2, 1, 0.5)와, 조회를 더 빠르게 하려고 함께 본 (1, 0.5, 0.25)를 즉시 초기화와 나눈 초기화로 각각 빌드했습니다. 팀은 (2, 1, 0.5)를 유지합니다.

## 결론

**가장 긴 저장(버킷 배열을 새로 만드는 저장)이 약 10분의 1로 줄었습니다.** (2, 1, 0.5)에서 key 4,194,304개일 때 32.4\~58.1 ms가 2.4\~5.2 ms가 되었습니다. 초기화하는 일 자체가 사라진 것이 아니라 이후의 저장과 조회로 나뉘었습니다.

| (2, 1, 0.5), key 수 | 가장 긴 저장, 즉시 (ms) | 가장 긴 저장, 나눔 (ms) | 조회 중앙값, 즉시 → 나눔 (ns) |
|---|---|---|---|
| 100,000 | 0.860\~2.639 | 0.218\~0.680 | 645.9 → 701.4 |
| 1,048,576 | 10.171\~23.115 | 1.457\~7.309 | 1127.4 → 1151.9 |
| 4,194,304 | 32.385\~58.149 | 2.393\~5.205 | 1291.2 → 1264.5 |

- **조회는 판정할 차이가 없습니다.** 세 key 수 모두 5회 범위가 겹칩니다. 나눈 초기화는 버킷을 쓸 때마다 `head.next`가 NULL인지 한 번 봅니다.
- **저장 평균은 key 100,000개에서 776.0 ns가 891.6 ns로 늘었습니다.** 새 배열의 페이지를 처음 쓰는 비용이 그 페이지를 처음 건드리는 저장으로 옮겨 갔기 때문으로 봅니다. key 4,194,304개에서는 1779.1 ns와 1828.0 ns로 거의 같습니다.
- **메모리는 같습니다.** 버킷 배열의 크기와 key 하나당 RSS가 설정마다 즉시 초기화와 같습니다.
- **(1, 0.5, 0.25)도 나누면 가장 긴 저장이 4.7\~9.5 ms입니다**(즉시 54.8\~72.7 ms). 조회는 (2, 1, 0.5)보다 key 100만 개 이상에서 약 17\~20% 빠르지만, key 하나당 RSS가 208 B에서 224 B로 늘어서 팀은 고르지 않았습니다.
