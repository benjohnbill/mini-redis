# 005 성능 개선 전의 서버 기준선

## 앞 기록과 달라진 점

- **목적:** M7 `perf`의 서버 기준선입니다. 이후 `server/` 기록은 이 기록과 견줍니다. 이 머신에서 시나리오 9개(lab, A\~E, f\~h)를 모두 잰 첫 기록입니다.
- **머신:** 004와 같은 머신입니다. 001\~003은 다른 머신(Ultra 9 275HX)에서 쟀으므로 lab과 A\~E의 숫자를 나란히 비교하지 않습니다.
- **코드:** 004(`b501b1d`) 뒤에 `src/`가 바뀐 커밋은 다음과 같습니다. 주기 청소가 S보다 많이 늦으면 다음 기한을 지금 + S로 잡습니다(`481f582`). 저장이 heap이 실제로 늘어날 때만 칸을 확보합니다(`b65bf34`). 헤더 64개를 넘는 요청을 `431`로, chunked가 아닌 `Transfer-Encoding`을 `411`로 거절합니다(`67548ea`, `2c0280a`). 나머지(`20722d1`, `b1ac565`, `f3d8fb4`)는 이름과 규칙을 정리했습니다. 측정 요청은 `431`이나 `411`에 해당하지 않습니다. `6b1ec7d`는 문서만 바꿨으므로 `src/`는 `main`의 `5d68b81`과 같습니다.

## 결론

목표는 "방해 요청이 있어도 작은 GET의 p99 10 ms 이하"([M3 spec](../../milestones/concurrency/spec.md) Q10)입니다.

| 시나리오 | 작은 GET p99, 3회 (ms) | 판정 |
|---|---|---|
| A 방해 없음 | 0.604, 5.906, 0.794 | 통과 |
| B 16 MiB 저장 | 85.280, 35.976, 23.718 | 초과 (3회 모두) |
| C rehash 경계 | 0.797, 1.371, 7.349 | 통과 |
| D 16 MiB 삭제 | 0.898, 9.561, 0.940 | 통과 |
| E 버킷을 한 번 늘림 | 477.413, 586.699, 442.718 | 초과 (3회 모두) |
| f 한꺼번에 만료 | 0.854, 0.784, 117.469 | 3회째만 초과 |
| g 꾸준한 만료 | 1.454, 0.942, 0.790 | 통과 |
| h 큰 value의 만료 | 1.423, 0.894, 0.768 | 통과 |

- **B와 E는 3회 모두 목표를 넘었습니다.** B에서 16 MiB 저장 하나는 p50 29\~44 ms였고, E에서 버킷을 늘리는 저장 하나는 535\~676 ms였습니다. 두 증상은 README의 "알려진 한계"에 이미 있습니다.
- **f의 3회째(p99 117 ms)는 원인을 가르지 못했습니다.** 같은 회에 client가 늦게 보낸 정도도 p99 12.4 ms, max 43.4 ms로 컸습니다. 004에서도 같은 머신에서 이런 회가 있었고, 측정 client(python)나 WSL이 멈춘 것으로 보았습니다. A의 2회째(p99 5.9 ms, client 늦음 max 28.3 ms)도 같은 모양입니다.
- **이 머신에서는 회마다 흔들림이 큽니다.** 측정하는 동안 사용 가능한 메모리는 약 5\~7 GiB, load average는 약 2.5\~3.2였습니다. 원인을 쪼개는 측정(M7의 B 단계)은 회 수를 늘리거나, client 늦음이 큰 회를 따로 표시해야 합니다.
- **f, g, h는 004의 S 25, K 2,000과 같은 범위입니다.** 회수 지연은 f가 4\~24 ms, g가 key마다 max 26.6\~27.9 ms, h가 11\~31 ms였습니다.
