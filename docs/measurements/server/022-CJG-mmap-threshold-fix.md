# 서버가 시작할 때 glibc의 mmap 기준값을 고정함

## 앞 기록과 달라진 점

- **코드:** `main`(`28100ac`)에 이 commit만 더했습니다. 서버가 시작할 때 `mallopt(M_MMAP_THRESHOLD, 128 KiB)`로 glibc `malloc`의 mmap 기준값을 고정합니다(`src/server.c`의 `malloc_mmap_threshold_fix`). glibc가 아닌 C 라이브러리에서는 부르지 않습니다.
- **목적:** [019](019-CJG-h-mmap-threshold.md)는 환경 변수 `MALLOC_MMAP_THRESHOLD_=131072`로 기준값을 고정하면 #42 뒤 h의 멈춤이 사라진다는 것을 보였습니다. 같은 일을 서버 코드가 하도록 바꾸고, 16 MiB를 다루는 b와 d도 함께 쟀습니다.
- **commit:** 이 기록을 더한 commit은 `src/server.c`의 주석 한 줄(d의 멈춤과 이 기록의 번호)만 더 바꿨습니다. 컴파일되는 코드는 잰 `44aa1c2`와 같습니다.
- **명령:** 고치기 전과 뒤의 binary를 번갈아 실행해, 시점에 따른 차이가 한쪽에 몰리지 않게 했습니다.

## 결론

**h와 d의 멈춤이 사라졌습니다.** 두 시나리오 모두 16 MiB value를 해제할 때 서버가 약 35\~40 ms 멈췄는데, 이제 작은 GET의 max가 3\~13 ms입니다. b는 같습니다.

| 지표 | 고치기 전 (5회) | 고친 뒤 (5회) | 판정 |
|---|---|---|---|
| h 작은 GET max (ms) | 33.530, 38.131, 36.241, 40.657, 38.231 | 4.330, 13.044, 12.301, 5.186, 46.047 | 개선 (5회째는 아래) |
| d 16 MiB 삭제 max (ms) | 32.511, 34.868, 35.335, 37.857, 37.588 | 6.471, 6.049, 5.986, 5.325, 5.637 | 개선 |
| d 작은 GET max (ms) | 33.684, 36.780, 36.947, 39.944, 39.214 | 3.896, 8.392, 12.598, 3.120, 3.506 | 개선 |
| b 16 MiB 저장 p50 (ms) | 26.184, 27.369, 25.853, 23.829, 24.106 | 26.741, 24.996, 25.021, 26.672, 26.099 | 차이 없음 |
| b 작은 GET p99 (ms) | 20.316, 19.499, 18.249, 18.670, 17.567 | 20.449, 18.320, 18.584, 19.956, 18.833 | 차이 없음 |
| d, h 최대 RSS (MiB) | 844.2\~845.5 | 841.3\~841.7 | 약 3 MiB 감소 |

- **h 5회째의 46.0 ms**는 같은 회의 client 늦음이 p99 7.2 ms, max 17.7 ms로 다른 회보다 크게 나와서, 측정 client가 멈춘 회로 봅니다. 나머지 4회는 4.3\~13.0 ms입니다.
- **d의 멈춤도 같은 원인으로 봅니다.** d는 16 MiB value를 하나씩 지우는 시나리오이고, 지울 때 서버가 멈추는 일은 #42보다 앞선 [B1](013-CJG-b1-baseline.md)에도 있었습니다(16 MiB 삭제 max 49.3\~53.2 ms). 기준값을 고정하자 이 멈춤도 사라졌으므로, #42 전에도 다른 큰 해제가 기준값을 올리고 있었던 것으로 봅니다. 기준값이 오르면 16 MiB entry가 mmap이 아니라 heap에 할당되고, heap에서 해제한 큰 덩어리를 돌려주는 데 시간이 걸린 것으로 봅니다. 해제가 어디서 시간을 쓰는지는 프로파일로 보지 않았습니다.
- **d의 16 MiB 삭제 p50은 약 0.1 ms에서 약 1 ms로 늘었습니다.** 이제 16 MiB entry가 mmap으로 할당되어, 지울 때마다 `munmap`이 페이지를 돌려주기 때문으로 봅니다. 서버 전체의 멈춤(max)은 약 35 ms에서 약 6 ms로 줄었으므로 치를 만한 값입니다.
