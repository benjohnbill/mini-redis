# 새 버킷 배열을 버킷마다 처음 쓸 때 초기화함: 서버

## 앞 기록과 달라진 점

- **코드:** [`rehash-micro/003`](../rehash-micro/003-CJG-lazy-buckets.md)과 같습니다. 측정한 binary는 실험 브랜치의 `853dd85`로 빌드했고, 이 기록의 commit(`8860ac8`)과 `src/`가 같습니다.
- **시나리오:** 버킷 배열을 쓰는 a(방해 없음), c(rehash 경계), e(버킷을 한 번 늘림)만 쟀습니다. b, d, f, g, h는 재지 않았습니다.
- **e의 빌드:** 이 측정은 [`server/023`](023-CJG-grow-delay.md)의 `bench.py` 수정 전에 했습니다. 고치기 전의 e는 버킷을 늘리는 저장이 빨리 끝나면 쉬는 연결 기한에 걸려 실패하므로, e만 두 binary 모두 `IDLE_TIMEOUT_MS`를 60초로 바꿔 쟀습니다. 바꾼 것은 그 상수 하나입니다.

## 결론

**e의 멈춤이 사라졌습니다.** 버킷을 늘리는 저장이 99.9\~110.2 ms에서 0.21\~0.29 ms가 되었고, 작은 GET p99가 3회 모두 목표(10 ms) 안입니다. a와 c는 같습니다.

| 지표 | 즉시 (3회) | 나눔 (3회) | 판정 |
|---|---|---|---|
| e 버킷을 늘리는 저장 (ms) | 110.160, 103.406, 99.937 | 0.244, 0.288, 0.211 | 개선 |
| e 작은 GET p99 (ms) | 17.542, 12.313, 11.102 | 0.902, 0.658, 0.888 | 개선, 목표 통과 |
| e 최대 RSS (MiB) | 965.4 | 938.4\~938.8 | 약 27 MiB 감소 |
| a, c 작은 GET p50 (ms) | 0.077\~0.079 | 0.075\~0.086 | 차이 없음 |
| c 작은 GET p99 (ms) | 0.613, 1.044, 0.873 | 0.892, 0.774, 0.647 | 차이 없음 |
| c 최대 RSS (MiB) | 837.4 | 837.4 | 같음 |

- **e의 최대 RSS가 줄어든 것은 e가 옮기기의 시작만 보기 때문입니다.** 새 배열에서 아직 쓰지 않은 페이지는 메모리에 올라오지 않습니다. 옮기기를 끝까지 마친 c에서는 즉시 초기화와 같았습니다.
- **고친 `bench.py`로도 확인했습니다.** [`server/023`](023-CJG-grow-delay.md)에서 같은 binary(쉬는 연결 기한 10초)가 3회 모두 0.13\~0.56 ms였습니다.
