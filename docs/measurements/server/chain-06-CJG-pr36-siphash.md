# 병합 사슬 #36: store마다 무작위 seed를 섞는 SipHash 1-2

## 앞 기록과 달라진 점

- **코드:** #42 단계(`25241f4`)에 PR #36만 병합했습니다. store가 key를 FNV 대신 store마다 무작위 seed를 섞는 SipHash 1-2로 hash합니다(`src/store.c`, `vendor/siphash/`).
- **머신과 명령:** 앞 단계와 같습니다. 3회에 약 10분 20초가 걸렸습니다.

## 결론

**이 사슬의 key 길이에서는 SipHash의 비용이 보이지 않습니다.** #36은 속도가 아니라 공격 방어를 위한 변경이며, 치를 값은 hash 한 번의 시간입니다. [`hash-micro/001`](../hash-micro/001-CJG-hash-functions.md)이 짧은 key에서 수 ns로 잰 차이가 작은 GET 하나(약 80 µs)의 흔들림 안에 묻혔습니다.

| 지표 | #42 (3회) | #36 (3회) | 판정 |
|---|---|---|---|
| 작은 GET p50, 8개 시나리오 × 3회 (ms) | 0.075\~0.100 | 0.073\~0.095 | 차이 없음 |
| c 작은 GET p99 (ms) | 0.660, 0.775, 0.667 | 0.711, 0.772, 0.848 | 차이 없음 |
| e 버킷을 늘리는 저장 (ms) | 96.067, 94.637, 117.446 | 105.003, 107.705, 103.484 | 차이 없음 |
| 최대 RSS (모든 시나리오) | | | 1 MiB 안에서 같음 |

- **e의 p99가 3회 모두 목표를 조금 넘었지만(10.7\~14.6 ms), #36 때문으로 보지 않습니다.** 작은 GET은 초당 5,000개이고 버킷을 늘리는 멈춤은 약 100 ms라서, 멈춤 동안 약 500개가 밀립니다. 이는 50,000개의 1%와 같아서 p99가 멈춤의 경계에 걸립니다. #35 단계부터 e의 p99는 같은 이유로 1.0 ms와 24.2 ms 사이를 오갔습니다. 멈춤 자체(버킷을 늘리는 저장)는 #42 단계와 같은 범위입니다.
- **a 1회째의 p99 5.3 ms**는 같은 회의 client 늦음 max가 14.8 ms라서 측정 client가 멈춘 회로 봅니다.
- **긴 key의 비용은 이 기록에 없습니다.** `bench.py`의 key는 짧습니다. 4,096바이트 key에서의 비용은 `hash-micro/001`과 [`hash-function.md`](../../milestones/perf/ideas/hash-function.md)가 추정한 값만 있습니다.
- **h의 약 40 ms 멈춤(39.9\~45.2 ms)과 d, h의 RSS 845 MiB는 #42 단계와 같습니다.** 원인은 [#42 기록](chain-05-CJG-pr42-recv-buffer.md)에 적은 가설 그대로입니다.
