# 병합 사슬 #39\~#41: 상품 데모를 위한 변경 뒤의 서버

## 앞 기록과 달라진 점

- **코드:** #36 단계(`409f6b9`)에 PR #39, #40, #41을 차례로 병합했습니다. 세 PR의 주된 변경은 상품 데모(`demo/`)에 있고, 상품 데모의 숫자는 `cache-demo/` 사슬 기록에 있습니다. 서버에서 바뀐 것은 아래 세 가지입니다.
  - `POST /mget`과 `POST /mset`이 생겼습니다(`src/api.c`). `bench.py`는 이 경로를 부르지 않습니다.
  - 응답을 송신 버퍼로 복사한 뒤 `api_response_destroy`를 부릅니다(`src/server.c`).
  - body를 선언한 길이만큼 받지 못한 요청을 처리하지 않습니다. 요청마다 `Content-Length` 헤더를 한 번 찾습니다(`src/server.c`의 `body_is_complete`).
- **머신과 명령:** 앞 단계와 같습니다.
- **측정 시점:** 다른 Claude 세션이 돌지 않는 상태에서 쟀습니다. 처음 잰 #41 단계는 다른 세션과 겹쳐서 기록하지 않았습니다.

## 결론

**서버의 숫자는 #36 단계와 같습니다.** `bench.py`가 부르는 경로에서 세 PR이 더한 일은 요청마다 헤더를 한 번 찾는 것뿐이고, 그 비용은 작은 GET의 흔들림 안에 묻혔습니다.

| 지표 | #36 (3회) | #41 (3회) | 판정 |
|---|---|---|---|
| 작은 GET p50, 8개 시나리오 × 3회 (ms) | 0.073\~0.095 | 0.077\~0.133 | 차이 없음 (1회째가 모든 시나리오에서 느림) |
| e 버킷을 늘리는 저장 (ms) | 105.003, 107.705, 103.484 | 141.175, 68.216, 73.517 | 차이 없음 |
| h 작은 GET max (ms) | 39.923, 45.069, 45.157 | 57.342, 52.862, 136.123 | 차이 없음 (근거 절) |
| 최대 RSS (모든 시나리오) | | | 0.5 MiB 안에서 같음 |

- **1회째는 a부터 h까지 모든 시나리오의 작은 GET p50이 0.093\~0.133 ms로 2, 3회째보다 느렸습니다.** 세 PR과 상관없는 a(방해 없음)도 느렸으므로 노트북의 상태로 봅니다. 2, 3회째는 0.077\~0.115 ms입니다.
- **e의 멈춤은 68\~141 ms로 흔들렸습니다.** #35 단계부터 이 멈춤은 72\~117 ms 사이에서 흔들렸고, 세 PR은 store를 바꾸지 않았습니다. e의 p99도 같은 이유로 1.2 ms와 50.8 ms 사이를 오갑니다.
- **h의 3회째 136 ms**는 같은 회의 client 늦음 max가 13.2 ms라서 측정 client도 멈춘 회입니다.

## 근거: h를 두 binary로 번갈아 잼

h의 멈춤이 #36 단계의 40\~45 ms보다 길게 나와서, `409f6b9`와 `9e1812d`의 binary로 h만 번갈아 5회씩 쟀습니다. 멈춤의 범위가 겹치므로 #41이 h를 늦게 만들지 않았다고 판정합니다. 같은 binary도 사슬 측정 때보다 짧게 나왔으므로, h의 멈춤은 측정 시점에 따라 약 10 ms씩 흔들립니다.

| binary | h 작은 GET max, 5회 (ms) | 회수 지연, 5회 (ms) |
|---|---|---|
| `409f6b9` (#36) | 28.046, 35.004, 34.634, 31.398, 32.569 | 21, 20, 24, 20, 17 |
| `9e1812d` (#41) | 31.389, 36.388, 30.216, 36.489, 39.474 | 13, 27, 17, 29, 34 |
