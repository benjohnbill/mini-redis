# 05: 느린 클라이언트가 다른 요청을 막지 않는다

**Status:** ready-for-agent

**What to build:** 헤더를 반쯤 보내고 멈춘 클라이언트나 큰 body를 천천히 보내는 클라이언트가 있어도, 다른 서버의 요청은 바로 응답을 받습니다. spec이 4단계로 넘긴 확인이며, 서버 코드는 바꾸지 않고 기능 테스트로 확인만 합니다. 결과가 예상과 다르면 구현하지 말고 팀에 가져옵니다. 결정은 `../spec.md`의 "Q10 M2의 범위"를 따릅니다.

**Blocked by:** 04

테스트 시나리오(팀 확인 2026-11-13). 테스트 이름은 아래 문장을 그대로 씁니다.

- [x] (기능) 헤더를 반쯤 보내고 멈춘 연결이 있어도 다른 요청은 바로 응답을 받는다
- [x] (기능) 큰 body를 천천히 보내는 연결이 있어도 다른 요청은 바로 응답을 받는다
- [x] 끝까지 오지 않는 연결을 mongoose가 언제 닫는지 확인해 `## Comments`에 기록한다. 닫지 않으면 `make verify`가 멈출 수 있으므로 테스트로 두지 않습니다
- [x] `make verify`가 통과한다

## Comments

- 두 기능 테스트는 서버 코드를 바꾸지 않고 통과했습니다. 다른 요청은 매번 새 연결로 보내고, 0.5초 안에 `404 key_not_found`가 와야 통과합니다. 큰 body는 256 KiB를 64 KiB씩 4번, 0.05초 간격으로 보냅니다. 조각마다 다른 요청을 확인하고, 끝까지 보낸 뒤 `204`와 같은 value의 조회를 확인합니다. 두 테스트는 합해서 약 0.3초 걸립니다. 서버를 SIGSTOP으로 멈추면 같은 확인이 `TimeoutError`로 실패하는 것도 따로 확인했습니다. 서버가 막히면 테스트가 잡습니다.
- **mongoose는 끝까지 오지 않는 연결을 닫지 않습니다.** 실제 서버(ASan 빌드)에 세 연결을 열어 두었습니다: 아무것도 보내지 않은 연결, 헤더를 반쯤 보낸 연결, `Content-Length: 100`에 body 3바이트만 보낸 연결. 셋 다 120초 동안 서버가 아무것도 보내지 않았고 닫지도 않았습니다. 그동안 다른 요청은 바로 응답을 받았고, SIGTERM으로 끈 서버는 0으로 끝났습니다.
- 근거(`vendor/mongoose/mongoose.c`, 7.23): `mg_mgr_poll`(14950행)은 `is_draining`이나 `is_closing`이 선 연결만 닫고(14984~14985행), 시간을 보지 않습니다. `http_cb`(4728행)는 `MG_EV_POLL`에서 받은 바이트를 다시 해석할 뿐, 시간 제한이 없습니다. 받은 연결에 시간이 걸린 것은 `accept_conn`(14668행)이 부르는 `setsockopts`(14592행)의 `SO_KEEPALIVE`뿐입니다. 이것은 상대가 사라진 연결을 커널이 정리하는 장치이고(이 머신의 `tcp_keepalive_time`은 7200초), 살아 있지만 보내지 않는 클라이언트는 닫지 않습니다.
- 팀이 정할 것: 이런 연결은 클라이언트가 닫거나 서버가 끝날 때까지 남아 fd와 수신 버퍼를 차지합니다. 받아들일지, 서버가 `MG_EV_POLL`에서 마지막으로 받은 시각을 보고 닫을지 정해야 합니다. 닫는다면 시간과 이유를 spec에 적어야 합니다. 이 티켓의 범위 밖이므로 구현하지 않았습니다.
