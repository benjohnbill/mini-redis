# M2 `api` spec

Status: ready-for-agent

요구사항: L3, L10, L14 (`docs/requirements.md`). 문제는 `overview.md`에 있고, 이 문서는 2단계 grill(2026-11-13)에서 팀이 합의한 답입니다.

## Problem Statement

M1이 끝난 지금, store는 key와 value를 주소와 길이 한 쌍으로 받아 저장, 조회, 삭제할 수 있습니다. 하지만 서버(`src/server.c`)는 어떤 요청에도 `ok`를 돌려줄 뿐 store를 부르지 않습니다. 네트워크 너머의 다른 서버는 아직 mini-redis에 key와 value를 넣거나, 꺼내거나, 지울 방법이 없습니다. 팀은 다른 서버가 코드를 읽지 않고도 쓸 수 있는 요청 규칙을 정하고, 그 규칙이 실제 서버에서 지켜지는지 바깥에서 확인할 수 있어야 합니다.

## Solution

다른 서버는 HTTP로 mini-redis를 부릅니다. 동작은 메서드(`PUT` 저장, `GET` 조회, `DELETE` 삭제)로, key는 경로 `/keys/<key>`로, value는 body의 바이트 그대로 구분합니다. 응답은 상태 코드로 결과를 알리고, 오류일 때는 body에 오류 이유를 담습니다. 연결과 요청 해석은 서버 라이브러리 mongoose가 맡고, 요청을 store 호출과 응답으로 바꾸는 일은 HTTP 라이브러리를 모르는 api 층이 맡습니다. api 층은 단위 테스트로, 실제 서버는 바깥에서 요청을 보내는 기능 테스트로 확인합니다(L14). 사용법은 `README.md`의 "API" 절에 적습니다(L10).

## User Stories

1. 다른 서버의 개발자로서, `PUT /keys/<key>`에 value를 body로 보내 저장하기를 원합니다. 그래야 HTTP 메서드만 보고 동작을 짐작할 수 있습니다.
2. 다른 서버의 개발자로서, `GET /keys/<key>`로 저장한 value를 body로 받기를 원합니다.
3. 다른 서버의 개발자로서, `DELETE /keys/<key>`로 key를 지우기를 원합니다.
4. 다른 서버의 개발자로서, 이미지처럼 `'\0'`이나 UTF-8이 아닌 바이트가 든 value를 인코딩 없이 그대로 저장하고 그대로 돌려받기를 원합니다.
5. 다른 서버의 개발자로서, `/`, 공백, 한글, `'\0'`이 든 key를 퍼센트 인코딩(`%2F`, `%20`, `%ED%95%9C`, `%00`)으로 보내면 그 바이트 그대로 key가 되기를 원합니다.
6. 다른 서버의 개발자로서, `%2F`가 경로 구분자가 아니라 key 안의 `/` 바이트로 다뤄지기를 원합니다. 그래야 key에 `/`를 넣을 수 있습니다.
7. 다른 서버의 개발자로서, 서버가 퍼센트 인코딩을 정확히 한 번만 풀기를 원합니다. 그래야 `%2541`이 `%41`이라는 key로 남고 `A`가 되지 않습니다.
8. 다른 서버의 개발자로서, 0바이트 value를 저장하고 조회하면 `200`과 0바이트 body를 받기를 원합니다. 그래야 빈 value와 없는 key를 구분할 수 있습니다.
9. 다른 서버의 개발자로서, 없는 key를 조회하면 `404`와 오류 이유 `key_not_found`를 받기를 원합니다.
10. 다른 서버의 개발자로서, 저장에 성공하면 새로 만들었든 덮어썼든 `204`를 받기를 원합니다.
11. 다른 서버의 개발자로서, 있는 key를 지우면 `204`를, 없는 key를 지우면 `404`와 `key_not_found`를 받기를 원합니다.
12. 다른 서버의 개발자로서, `/keys/`로 시작하지 않는 경로로 잘못 요청하면 `404`와 오류 이유 `route_not_found`를 받기를 원합니다. 그래야 경로 오타를 "key 없음"으로 오해하지 않습니다.
13. 다른 서버의 개발자로서, `/keys/`처럼 key가 비어 있으면 `400`과 `empty_key`를 받기를 원합니다.
14. 다른 서버의 개발자로서, `%G1`이나 끝이 잘린 `%2`처럼 깨진 인코딩을 보내면 `400`과 `bad_key_encoding`을 받기를 원합니다.
15. 다른 서버의 개발자로서, `/keys/<key>`에 `POST` 같은 지원하지 않는 메서드를 보내면 `405`와 `method_not_allowed`를 받기를 원합니다.
16. 다른 서버의 개발자로서, body가 상한(16 MiB)을 넘으면 연결이 이유 없이 끊기는 대신 `413`과 `body_too_large`를 받기를 원합니다.
17. 다른 서버의 개발자로서, 서버의 메모리가 부족해 저장하지 못하면 `500`과 `out_of_memory`를 받기를 원합니다.
18. 다른 서버의 개발자로서, 오류 응답의 body가 `{"error":"<오류 이유>"}` JSON이기를 원합니다. 그래야 상태 코드가 같은 두 오류도 고정된 문자열로 나눠 처리할 수 있습니다.
19. 다른 서버의 개발자로서, 조회 응답의 `Content-Type`은 `application/octet-stream`, 오류 응답은 `application/json`이기를 원합니다.
20. 다른 서버의 개발자로서, 큰 value를 보내는 클라이언트나 느린 클라이언트가 있어도 내 요청이 그 요청이 끝날 때까지 기다리지 않기를 원합니다.
21. 다른 서버의 개발자로서, 코드를 읽지 않고 `README.md`의 "API" 절만 보고 요청을 보내기를 원합니다(L10).
22. 다른 서버의 개발자로서, "API" 절에서 저장, 조회, 삭제의 `curl` 예시와 상태 코드 표, 오류 이유 목록을 보기를 원합니다.
23. 팀원으로서, 요청을 store 호출과 응답으로 바꾸는 api 층이 HTTP 라이브러리의 타입을 모르기를 원합니다. 그래야 M3에서 서버의 연결 처리를 다시 짜도 api 층과 그 테스트가 그대로 남습니다.
24. 팀원으로서, 서버가 mongoose 이벤트를 받아 api 층에 넘기고 응답을 보내는 일만 하기를 원합니다. 그래야 서버 코드를 연결 처리 하나로 설명할 수 있습니다.
25. 팀원으로서, `store_get`이 빌려준 value를 응답으로 보낼 때 그 주소가 무효가 될 경로가 없음을 설명할 수 있기를 원합니다.
26. 팀원으로서, store의 0바이트 key 지원은 그대로 두고, HTTP 입구에서만 0바이트 key를 거절하기를 원합니다.
27. 팀원으로서, mongoose를 레포에 넣은 뒤에도 `make verify`의 경고와 sanitizer 설정이 우리 코드에 그대로 적용되기를 원합니다.
28. 팀원으로서, mongoose 파일은 원본과 대조할 수 있도록 포맷과 이름 검사에서 빼기를 원합니다.
29. 팀원으로서, 레포가 mongoose의 라이선스(GPLv2)를 따른다는 사실이 LICENSE 파일에 드러나기를 원합니다.
30. 테스트 작성자로서, 소켓 없이 api 층의 공개 함수만 불러 경로 해석, 상태 코드, 오류 이유를 확인하기를 원합니다.
31. 테스트 작성자로서, 실제 서버를 띄우고 바깥에서 요청을 보내 저장, 조회, 삭제가 동작하는지 확인하기를 원합니다(L14).
32. 테스트 작성자로서, 기능 테스트가 `make verify`와 CI에서 함께 실행되고, CI에 새 의존성을 들이지 않기를 원합니다.
33. 발표하는 팀원으로서, 요청 하나가 서버, api 층, store를 차례로 지나 응답이 되는 흐름을 코드에서 짚어 설명하기를 원합니다.

## Implementation Decisions

grill의 질문 번호(Q2~Q13)를 함께 적습니다.

- **모듈:** api 층 모듈 하나를 새로 만들고, 서버를 mongoose 위로 다시 짭니다. store 모듈은 고치지 않습니다.
- **Q2 동작 구분:** `PUT`, `GET`, `DELETE`가 저장, 조회, 삭제입니다. 그 밖의 메서드는 `405`입니다.
- **Q3 key의 위치:** key는 경로에서 `/keys/` 뒤의 나머지 전부입니다. 퍼센트 인코딩을 아직 풀지 않은 경로를 받아, `%HH`를 정확히 한 번 풀고 그 결과를 길이와 함께 key로 씁니다. `%2F`도 key 안의 `/` 바이트가 됩니다. 0바이트 key는 `400`으로 거절합니다. 이유: `/keys/`가 "빈 key"와 "key 목록" 두 가지로 읽힐 여지를 없애기 위해서입니다. store의 0바이트 key 지원(M1 Q10)은 그대로 둡니다. 경로에 인코딩하지 않은 `?`가 있으면 `400 bad_key_encoding`으로 거절하고, key 안의 `?`는 `%3F`로 보내야 합니다. 그래서 서버는 mongoose가 `?` 앞(`uri`)과 뒤(`query`)로 나눈 요청 대상을 다시 합쳐 api 층에 넘깁니다. 이유: `?`는 HTTP에서 경로와 query를 나누는 문자라서, mongoose가 `PUT /keys/a?b=1`을 key `a`로 저장했습니다. 다른 서버나 라이브러리도 `?` 뒤를 key로 보지 않습니다(5단계 코드 리뷰에서 결정, 2026-11-13).
- **Q6 value의 형식:** value는 body의 바이트 그대로이고, 길이는 `Content-Length`가 알려줍니다. JSON으로 감싸지 않습니다. 이유(팀원 문장): 우리가 구현하는 범위 내에서는 HTTP의 헤더와 body 부분만 있어도 충분하기 때문에, JSON을 사용할 이유가 없습니다.
- **Q5, Q8, Q9 응답:**

  | 상황 | 상태 코드 | body |
  |---|---|---|
  | 조회 성공 | `200` | value 바이트 (`application/octet-stream`) |
  | 저장 성공 (새로 만듦, 덮어씀 구분 없음) | `204` | 없음 |
  | 삭제 성공 | `204` | 없음 |
  | 조회, 삭제할 key가 없음 | `404` | `key_not_found` |
  | `/keys/`로 시작하지 않는 경로 | `404` | `route_not_found` |
  | 0바이트 key | `400` | `empty_key` |
  | 깨진 퍼센트 인코딩 | `400` | `bad_key_encoding` |
  | 경로에 인코딩하지 않은 `?` | `400` | `bad_key_encoding` |
  | 지원하지 않는 메서드 | `405` | `method_not_allowed` (`Allow: GET, PUT, DELETE` 헤더와 함께) |
  | `Transfer-Encoding: chunked` 요청 | `411` | `length_required` |
  | body가 상한을 넘음 | `413` | `body_too_large` |
  | 메모리 부족 (`store_set`의 `false`) | `500` | `out_of_memory` |

  오류 body는 `{"error":"<오류 이유>"}`이고 `Content-Type`은 `application/json`입니다. 서버가 만들어 내보내기만 하므로 JSON parser는 쓰지 않습니다. 저장 성공을 새로 만듦과 덮어씀으로 나누지 않는 이유는 `store_set`이 두 경우를 구분하지 않기 때문입니다. `?`, `405`의 `Allow` 헤더, `411` 줄은 (5단계 코드 리뷰에서 결정, 2026-11-13)에 더했습니다.
- **오류의 우선순위 (4단계에서 결정, 2026-11-13):** api 층은 경로, 메서드, key 순서로 검사하고 처음 걸린 오류 하나로 답합니다. 그래서 `POST /nope`는 `404 route_not_found`, `POST /keys/`는 `405`, `GET /keys`(끝에 `/`가 없음)는 `404 route_not_found`입니다. 이유: 경로가 틀린 요청에 메서드나 key 오류를 알리면 다른 서버가 엉뚱한 곳을 고치게 됩니다. 헤더 단계의 검사는 경로, 메서드, key보다 먼저 합니다. 헤더가 도착한 이벤트에서 `Transfer-Encoding`이 있으면 `411 length_required`, 그다음 `Content-Length`가 상한을 넘으면 `413`이고, 둘 다 api 층의 `api_reject_headers`가 응답을 만듭니다(5단계 코드 리뷰에서 결정, 2026-11-13).
- **Q7 서버 라이브러리:** mongoose 7.23의 `mongoose.c`와 `mongoose.h`를 레포에 넣어 씁니다. 스레드를 만들지 않고, 서버의 루프가 `mg_mgr_poll`을 반복해서 부릅니다. 레포는 mongoose의 라이선스를 따라 GPLv2로 공개하고 LICENSE 파일을 둡니다(팀 동의 2026-11-13). 버린 대안은 libmicrohttpd(key 경로를 길이 없이 넘겨서 해석을 끄는 옵션이 필요하고, body를 조각으로 모으는 코드와 CI 설치 단계가 늘어남), picohttpparser(연결 처리를 모두 직접 짜야 함), libuv(HTTP를 모르는 이벤트 루프 라이브러리)입니다. 비교 예제는 팀 레포 바깥에서 만들어 확인했습니다.
- **Q7 빌드:** mongoose는 프로젝트의 `-D_POSIX_C_SOURCE=200809L`만으로는 `alloca`와 `ip_mreq` 선언이 숨어서 빌드되지 않습니다. `-D_DEFAULT_SOURCE`를 더하면 `make verify`와 같은 경고와 sanitizer 설정(`-std=c11 -Wall -Wextra -Werror`, ASan, UBSan)에서 오류 없이 빌드됩니다(3단계에서 확인). mongoose 파일은 `.clang-format-ignore`에 더해 포맷과 이름 검사에서 뺍니다.
- **Q11 api 층의 인터페이스:** api 층은 store, 메서드, 인코딩을 풀지 않은 경로, body를 모두 주소와 길이 한 쌍으로 받고, 응답의 상태 코드, `Content-Type`, body(주소와 길이)를 돌려줍니다. mongoose의 타입(`struct mg_str` 등)을 쓰지 않습니다. 이유: M3가 서버의 연결 처리를 다시 짜도 api 층과 그 테스트를 건드리지 않게 하고, api 층의 테스트가 mongoose를 링크하지 않게 하기 위해서입니다.
- **Q11 서버의 일:** 서버는 mongoose의 요청 이벤트에서 메서드, 경로, body를 꺼내 api 층에 넘기고, 돌려받은 응답을 보냅니다. 경로는 mongoose가 주소와 길이로 주므로, `%00`이 든 key도 잘리지 않습니다.
- **문제 5 빌린 value:** 조회 성공 응답의 body는 `store_get`이 빌려준 주소를 그대로 가리켜도 됩니다. 서버는 api 층에서 돌아오자마자, 다음 store 호출 전에 mongoose의 송신 함수로 응답을 보내고, 송신 함수는 바이트를 연결의 송신 버퍼에 복사합니다. 그래서 응답을 다 보내기 전에 그 주소가 무효가 될 경로가 없습니다. 이 근거는 서버가 스레드 하나로 요청을 하나씩 처리한다는 사실에 기대므로, M3에서 다시 봅니다.
- **Q10 body 상한:** body의 상한은 16 MiB(16,777,216바이트)입니다(정확한 값은 4단계에서 결정). 서버는 헤더가 도착한 이벤트(`MG_EV_HTTP_HDRS`)에서 `Content-Length`를 api 층에 넘기고, 상한을 넘으면 api 층이 만든 `413` 응답을 body를 받기 전에 보내고 연결을 닫습니다. `413` 응답을 api 층이 만드는 이유는 오류 body 형식을 한 곳에 두고 단위 테스트로 확인하기 위해서입니다. mongoose의 수신 버퍼 상한(`MG_MAX_RECV_SIZE`, 기본 3 MiB이며 넘으면 응답 없이 연결을 끊음)은 컴파일 옵션으로 16 MiB보다 조금 크게 올립니다. 헤더도 같은 버퍼에 들어가므로, 두 값이 같으면 mongoose가 먼저 연결을 끊을 수 있기 때문입니다. 이유: 조각으로 받아도 요청 전체가 메모리에 모인 뒤 store가 한 번 더 복사하므로, 상한이 없으면 요청 하나가 서버의 메모리를 바닥내 모든 데이터를 잃게 할 수 있습니다. 16 MiB는 보통의 이미지를 받으면서 요청 하나의 메모리를 약 32 MiB로 묶는 값입니다. mongoose의 수신 버퍼에는 헤더도 함께 들어가므로, 아주 긴 key와 상한 크기의 body가 함께 오면 mongoose가 `413` 없이 연결을 끊을 수 있습니다. 이 경우는 받아들입니다.
- **chunked 요청 (5단계 코드 리뷰에서 결정, 2026-11-13):** `Transfer-Encoding: chunked` 요청은 헤더가 도착한 이벤트에서 `411`과 `length_required`로 거절하고, `413`처럼 응답을 보낸 뒤 연결을 닫습니다. 이유: chunked body는 끝까지 받아야 길이를 알 수 있어서 상한을 body 전에 검사할 수 없습니다. 실제로 17 MB chunked `PUT`은 `413`을 받지 못하고 mongoose가 "Invalid chunk"로 연결을 끊었습니다. 응답을 api 층이 만드는 이유는 `413`과 같습니다. 오류 body를 한 곳에 두고 단위 테스트로 확인하기 위해서입니다.
- **수신 버퍼 늘리기 (5단계 코드 리뷰에서 결정, 2026-11-13):** 서버의 `receive_buffer_grow`(커밋 `feca08f`)는 수신 버퍼가 차면 헤더가 알린 요청 길이까지 두 배씩 늘립니다. 이유: mongoose는 버퍼를 `MG_IO_SIZE`(16 KiB)씩 늘리며 매번 새로 할당해 복사하므로, ASan 빌드에서 16 MiB `PUT` 하나가 30초 걸렸고, 두 배씩 늘린 뒤 1초 안으로 줄었습니다. 이 코드는 mongoose가 `MG_EV_READ`를 HTTP 처리가 끝난 뒤에 부른다는 사실에 기댑니다. 그래야 버퍼를 옮겨도 mongoose가 옛 주소를 들고 있지 않습니다. M3가 연결 처리를 다시 짜면 이 전제를 다시 확인해야 합니다.
- **Q10 M2의 범위:** 요청 형식, 경로, key, store 층의 실패를 다룹니다. mongoose는 루프 하나가 non-blocking으로 여러 연결을 번갈아 처리하므로 느린 클라이언트가 다른 요청을 막지 않을 것으로 보지만, 4단계에서 테스트로 확인합니다. 끝까지 오지 않는 연결을 mongoose가 언제 닫는지도 4단계에서 확인합니다.
- **Q13 사용 문서:** `README.md`에 "API" 절을 하나 둡니다. 메서드와 경로, 위 응답 표, 오류 이유 목록, 저장, 조회, 삭제의 `curl` 예시를 담습니다. 별도의 API 문서 파일은 만들지 않습니다.
- **용어:** `GLOSSARY.md`의 api 층과 오류 이유를 씁니다. 마일스톤 이름 `api`와 api 층을 섞어 쓰지 않습니다.

## Testing Decisions

- **좋은 테스트:** 공개 함수나 HTTP 요청처럼 바깥에서 보이는 동작만 확인합니다. 기대하는 상태 코드와 body는 검사 대상 코드로 계산하지 않고 직접 적습니다. 퍼센트 디코딩 helper나 mongoose 이벤트 순서 같은 내부는 확인하지 않습니다.
- **seam 두 개 (grill Q11, Q12에서 팀 확인):**
  - api 층의 공개 함수: 소켓과 mongoose 없이 메서드, 경로, body를 넘겨 응답을 확인합니다. 응답 표의 모든 줄과 key 해석 규칙(`%2F`, `%00`, 한 번만 풀기, 깨진 인코딩)을 여기서 확인합니다.
  - 실제 서버: 서버를 띄우고 바깥에서 HTTP 요청을 보냅니다. 저장, 조회, 삭제의 한 바퀴, 바이너리 value, `%00` key, `413`, 느린 클라이언트가 다른 요청을 막지 않음처럼 연결을 지나야만 보이는 동작을 확인합니다.
- **파일과 도구:** api 층의 테스트는 CONVENTION대로 마일스톤 하나에 파일 하나이고, acutest의 `TEST_LIST`에 한국어 문장 이름을 적습니다. 선례는 M1의 store 테스트입니다. 기능 테스트는 `tests/functional/`에 둡니다. 도구는 "CI에 새 의존성을 들이지 않는다"는 제약 안에서 4단계 드라이버가 정합니다. python3은 이미 ID 검사에 쓰고 있어 이 제약을 만족합니다. 어느 도구든 테스트마다 동작을 말하는 한국어 문장을 이름으로 출력합니다.
- **격리:** api 층의 테스트는 테스트마다 새 store를 만들고 없앱니다. 기능 테스트는 서버를 한 번 띄우고, 테스트마다 서로 다른 key를 써서 서로 영향을 주지 않게 합니다.
- **`make verify`:** 서버를 빌드하고, 띄우고, 기능 테스트를 돌리고, 끄는 순서를 `make verify`에 넣습니다. CI는 같은 명령을 실행합니다.
- **시나리오 후보 (4단계에서 팀이 확인):** User Stories 1~20의 각 줄.
- **테스트하지 않는 것:** 메모리 부족(`500`)은 M1처럼 할당 함수를 바꿔 끼울 seam이 없어서 자동 테스트하지 않고 리뷰로 확인합니다.
- **ID:** ADR의 `결정:` 줄이나 `docs/requirements.md`의 `근거` 칸이 인용하는 테스트에만 ID를 붙이고, M1의 `T4` 다음 번호부터 씁니다. 어느 테스트를 인용할지는 4단계에서 정합니다.

## Out of Scope

- 여러 스레드, store를 여러 스레드에서 지키는 구조, 빌린 value의 수명 재검토, 연결 층의 나머지 실패(연결 수 초과 등): M3 `concurrency`.
- 보관 기간과 그것을 요청에 싣는 방법: M4 `expire`.
- key 목록 조회, 여러 key 한 번에 처리, 존재 확인 같은 추가 동작.
- key의 길이 상한: key는 경로에 실리므로 mongoose의 수신 버퍼 상한이 함께 막습니다. 따로 상한이나 `414`를 두지 않습니다.
- HTTPS, 인증, 압축.
- `HEAD`와 `OPTIONS` 같은 다른 메서드: `405`로 답합니다.

## Redis와 대조

Redis 7.2 소스(`networking.c`, `config.c`, `t_string.c`, `db.c`, `server.c`, `ae.c`, `tests/test_helper.tcl`)로 확인했습니다. 6단계에서 팀이 배운 것을 이 절에 더합니다. 스레드에 관한 Redis의 방식은 M3의 답이라서 이 절에 적지 않습니다.

| 주제 | 우리 생각 | Redis의 방식 | 우리가 고른 것 |
|---|---|---|---|
| 통신 규칙 | HTTP 메서드와 경로로 동작과 key를 나타냅니다. | HTTP를 쓰지 않고 TCP 위에 자체 프로토콜 RESP를 씁니다. 요청은 `SET key value` 같은 명령을 문자열 배열로 보내고, 동작은 첫 문자열(명령 이름)로 구분합니다. | HTTP. L3 해석이 HTTP이기 때문입니다. |
| 바이트 안전성 | value는 raw body와 `Content-Length`, key는 퍼센트 인코딩입니다. | 인자마다 `$3\r\nfoo\r\n`처럼 길이를 앞에 붙입니다. key와 value 모두 아무 바이트나 담을 수 있고, 인코딩 단계가 없습니다. | key는 URL에 실리므로 인코딩이 필요합니다. 길이를 따로 알린다는 생각은 같습니다. |
| 빈 value와 없는 key | `200`과 0바이트 body 대 `404`입니다. | 빈 문자열(`$0`)과 null(`$-1`, `shared.null`)이라는 다른 응답 타입으로 구분합니다(`getGenericCommand`). | 상태 코드로 구분. 같은 생각입니다. |
| 없는 key 삭제 | `404`와 `key_not_found`입니다. | `DEL`은 지운 key의 개수를 정수로 돌려주고(`delGenericCommand`의 `addReplyLongLong`), 없으면 0입니다. 오류로 보지 않습니다. | `404`. Redis와 다릅니다. 다른 서버가 이 결과를 오류로 처리할 수 있다는 점을 6단계에서 다시 봅니다. |
| 저장 성공 | `204`이고, 새로 만듦과 덮어씀을 구분하지 않습니다. | `SET`은 `+OK`를 돌려주고, 역시 구분하지 않습니다. | 같은 생각입니다. |
| 오류 | 상태 코드와 오류 이유 문자열입니다. | `-ERR ...`, `-OOM command not allowed when used memory > 'maxmemory'.`처럼 앞머리 단어가 붙은 오류 문자열을 보냅니다. | 고정된 문자열로 오류를 나눈다는 생각은 같습니다. |
| 연결과 해석 | 서버 라이브러리 mongoose입니다. | 외부 네트워크 라이브러리 없이 자체 이벤트 루프(`ae.c`)와 자체 parser(`networking.c`)를 씁니다. | mongoose. Redis와 다릅니다. |
| 크기 상한 | body 16 MiB, 넘으면 `413`입니다. | 인자 하나의 상한 `proto-max-bulk-len`이 기본 512MB이고, 넘으면 `Protocol error: invalid bulk length` 오류입니다. 클라이언트 하나의 입력 버퍼 상한 `client-query-buffer-limit`은 기본 1GB입니다. | 상한을 두고 이유를 알린다는 생각은 같고, 값은 훨씬 작습니다. |
| 층 분리 | 서버는 연결, api 층은 요청을 store 호출로 바꾸는 일을 맡습니다. | 연결과 해석은 `networking.c`, 명령 실행은 `t_string.c` 같은 명령 파일, 저장소 접근은 `db.c`가 맡습니다. | 같은 생각입니다. |
| 기능 테스트 | 실제 서버를 띄우고 바깥에서 요청을 보냅니다. | Tcl로 짠 테스트 묶음이 실제 서버를 띄우고 명령을 보냅니다. | 같은 생각이고, 도구는 4단계에서 정합니다. |

## Further Notes

- ADR: Q6과 Q2, Q3은 `http-methods-and-raw-body`입니다. Q7(mongoose와 GPLv2)도 ADR 기준을 통과하지만, 팀원이 말한 이유 문장이 아직 없어서 ADR로 쓰지 않았습니다. 이유 문장이 생기면 `mongoose-with-gplv2`로 씁니다.
- M3 overview에 넘길 문제: 빌린 value를 응답으로 보내는 근거가 스레드 하나에 기댄다는 점, store를 여러 스레드에서 지키는 구조, 연결 수 초과. 요청을 끝까지 보내지 않는 연결을 서버가 닫지 않는다는 점(티켓 05의 관찰: 120초 동안 닫지 않았고, 클라이언트가 끊거나 서버가 끝날 때까지 fd와 수신 버퍼를 차지합니다), 수신 버퍼 늘리기가 `MG_EV_READ`의 순서에 기댄다는 점(5단계 코드 리뷰에서 결정, 2026-11-13).
- M2 grill에서 쓴 비교 예제(parser 방식, libmicrohttpd 방식)는 팀 레포 바깥에 있고, 이 레포의 기록이 아닙니다.
