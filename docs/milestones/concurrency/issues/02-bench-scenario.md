## Comments

- 만든 것: `scripts/bench/open_loop.py`(열린 루프 client)와 `scripts/bench/bench.py`의 시나리오 `a-quiet`, `b-big-store`, `c-rehash`, `d-big-delete`. 01의 `prefill` 시나리오는 `c-rehash`가 같은 미리 채우기로 시작하므로 뺐습니다. 3회 측정의 표와 환경은 `../spec.md`의 "측정 결과"에 있습니다.
- 작은 GET(100연결, 초당 5,000개, 10초, 3회)의 p50 / p99 / max(ms): A 0.025~0.028 / 0.088~0.106 / 1.8~3.5, B 0.032~0.033 / 10.7~11.0 / 18.7~19.7, C 0.034~0.038 / 311~328 / 342~370, D 0.027~0.031 / 0.093~0.107 / 11.9~12.9.
- 방해 요청 자신의 지연(ms): 16 MiB 저장 p50 14.6~14.9, max 35~38. rehash 경계의 저장 p50 329~346, 삭제 p50 302~316. 16 MiB 삭제 p50 0.030~0.038, max 11.8~12.8.
- A와 wrk 기준선: python의 A(p99 약 0.1 ms)는 wrk 기준선(p99 약 0.47 ms)보다 작습니다. wrk는 100연결이 항상 응답을 기다리는 가득 찬 서버를 재고, 열린 루프는 초당 5,000개로 한가한 서버를 재기 때문입니다. client가 예정 시각보다 늦게 보낸 정도는 p99 0.03 ms 이하라서 python client는 병목이 아닙니다.
- 경계의 위치: `hash.c`는 entry 4,194,304개에서 버킷 2²¹개, 4,194,303개에서 2²⁰개를 씁니다. 4,194,304개를 채운 그대로 새 key를 저장하면 4,194,305개가 되어 rehash가 일어나지 않습니다. 그래서 `c-rehash`는 key 하나를 먼저 지워 4,194,303개로 만든 뒤 새 key 저장과 삭제를 번갈아 보냅니다. 이때 요청마다 300~370 ms가 걸리는 것으로 rehash가 요청마다 일어남을 확인했습니다.
- B의 원인(따로 만든 C 프로그램으로 같은 WSL에서 잼): 새로 `malloc`한 메모리에 16 MiB를 `memcpy`하는 데 10.3~10.9 ms, 16 MiB를 한 바이트씩 0으로 쓰는 데 1.8~1.9 ms. 서버에서는 `store_set`의 value 복사와 mongoose `mg_iobuf_del`의 `mg_bzero`에 해당합니다. 합이 작은 GET에서 거꾸로 셈한 멈춤(저장 하나에 약 12~13 ms)과 맞습니다. 서버 안에서 직접 잰 값은 아닙니다.
- D의 12 ms: 삭제마다 지연을 출력해 보니 50번째(마지막) 삭제 하나만 12.06 ms였고 나머지는 0.03~0.23 ms였습니다(첫 삭제만 1.01 ms). glibc가 해제된 800 MiB를 그때 한꺼번에 운영체제에 돌려주는 것으로 추정하며, 확인하지는 않았습니다. 삭제하는 key의 수나 순서가 바뀌면 이 값이 나오는 자리도 바뀔 수 있습니다.
- C의 간격: 방해 요청을 1초마다 보냅니다. 0.5초마다 보내면 서버가 시간의 약 2/3를 rehash에 써서 작은 GET의 p50이 82 ms가 됩니다(p99 329 ms, max 360 ms). p99는 두 간격에서 같습니다.
- python client가 정해진 시각을 지키는 방법: epoll의 기다림은 ms 단위로 올림되어 늦게 깨므로, 다음 예정 시각이 2 ms 안으로 들어오면 기다리지 않고 계속 확인합니다. 그래서 측정 중에 client가 CPU 코어 하나를 다 씁니다. 16 MiB body는 256 KiB씩 나눠 보내 작은 GET의 송신을 오래 막지 않습니다.
- 지연의 목표(Q10)와의 대조는 하지 않았습니다. 06이 합니다.
