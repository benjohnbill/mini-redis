# 03: 10초 동안 바이트가 오가지 않는 연결을 닫는다

**Status:** ready-for-agent

**What to build:** 요청을 끝까지 보내지 않고 멈춘 client는 10초 뒤 `408`과 `request_timeout`을 받고 연결이 닫힙니다. 응답을 받은 뒤 쉬는 연결은 10초 뒤 응답 없이 닫힙니다. 기한은 받기와 보내기 모두에서 마지막으로 바이트가 오간 때부터 세므로, 느린 네트워크로 큰 body를 보내거나 큰 응답을 받아 가는 정상 client는 끊기지 않습니다. `408` 응답은 api 층이 만들고(M2의 `411`, `413`과 같음), 검사는 같은 mongoose 루프 안에서 합니다. 스레드를 더하지 않습니다(ADR `single-thread-event-loop`). 결정은 `../spec.md`의 Q4, 응답 표, Testing Decisions의 "10초 기다림"을 따릅니다.

**Blocked by:** None (can start immediately)

테스트 시나리오(팀 확인 전). 테스트 이름은 아래 문장을 그대로 씁니다.

- [x] 요청 시간 초과 응답은 408과 {"error":"request_timeout"}이고 Content-Type은 application/json이다
- [x] [T12] (기능) 헤더를 보내다 10초 동안 멈춘 연결은 408과 request_timeout을 받고 닫힌다
- [x] (기능) body를 보내다 10초 동안 멈춘 연결은 408과 request_timeout을 받고 닫힌다
- [x] (기능) 응답을 받은 뒤 10초 동안 쉬는 연결은 응답 없이 닫힌다
- [x] (기능) body를 10초보다 오래 걸려 꾸준히 보내는 연결은 끊기지 않고 저장된다
- [x] (기능) 16 MiB 응답을 10초보다 오래 걸려 천천히 받아 가는 연결은 끊기지 않는다

그 밖의 완료 조건:

- [x] 서버의 기한은 10초로 고정하고, 테스트를 위한 인자나 테스트용 빌드를 만들지 않는다
- [x] 기다리는 기능 테스트들을 같은 시간 안에서 함께 돌려, `make verify`가 늘어나는 시간이 약 15초를 넘지 않게 한다
- [x] 천천히 받아 가는 테스트는 커널의 소켓 버퍼가 응답을 다 받아 두지 못하도록, 서버가 보내는 속도보다 느리게 읽는다
- [x] M1·M2의 기존 테스트가 그대로 통과하고, `make verify`가 통과한다

## Comments

- 서버는 연결마다 마지막으로 바이트를 받거나 보낸 시각(`mg_millis()`)을 `connection->data` 맨 앞 8바이트에 적습니다. `MG_EV_OPEN`, `MG_EV_READ`, `MG_EV_WRITE`에서 적고, `MG_EV_POLL`(100 ms 이내마다)에서 `IDLE_TIMEOUT_MS`(10,000)가 지났는지 봅니다. 리스너는 보지 않습니다.
- 기한이 지났을 때 수신 버퍼에 요청 조각이 남아 있으면 "요청을 받는 중"으로 보고 `408`을 보낸 뒤 송신 버퍼가 비면 닫습니다(`is_draining`). 수신 버퍼가 비어 있으면(응답 뒤에 쉬는 중, 아무것도 보내지 않은 새 연결, 응답을 받아 가지 않는 연결) 응답 없이 바로 닫습니다.
- 구현 중 찾은 것: mongoose는 연결을 닫을 때(`MG_EV_CLOSE`) 받다 만 요청도 받은 데까지를 body로 삼아 `MG_EV_HTTP_MSG`를 부릅니다. 그래서 `408`을 보내고 닫으면 body 10바이트가 저장되는 것을 "body를 보내다 멈춘" 테스트가 잡았습니다. 같은 이유로 M2의 `413`도, 헤더 뒤에 body 일부를 함께 보낸 요청은 닫힐 때 잘린 body가 저장되는 것을 따로 확인했습니다(`Content-Length: 16777217`과 body 10바이트를 보내면 `413`을 받은 뒤 조회가 `200 0123456789`). `request_handle`이 닫는 중인 연결(`is_draining`)의 요청을 처리하지 않게 해서 둘 다 막았습니다. client가 body 중간에 스스로 연결을 끊는 경우(닫는 중이 아닌 연결)는 이 수정이 막지 않습니다.
- 천천히 받아 가는 테스트는 client의 수신 소켓 버퍼를 64 KiB로 고정하고 16 MiB를 14초에 걸쳐 고르게 읽습니다. 받기만 세도록 서버를 바꿔 돌려 보니 이 테스트가 약 11.6초, 13,932,105바이트를 받은 곳에서 연결이 닫혀 실패했습니다. 그때 커널 버퍼에 남아 있던 양이 약 3 MB이므로, 서버의 마지막 보내기는 요청 뒤 약 11.5초에 옵니다. 보내기를 세지 않는 서버를 이 테스트가 잡습니다.
- 기다리는 테스트 5개는 스레드로 함께 돌리고, 티켓 05의 시간을 재는 테스트 2개는 그 앞에 하나씩 돌립니다. 함께 도는 16 MiB 저장이 0.5초 측정을 흔들지 않게 하기 위해서입니다. 기다리는 묶음은 약 15초(천천히 받아 가는 테스트의 16 MiB 저장과 14초 읽기)가 걸렸고, 이 브랜치의 `make verify` 전체가 빌드가 끝난 상태에서 약 17초였습니다.
