# 04: 동시 연결을 128개까지만 받는다

**Status:** ready-for-agent

**What to build:** 서버가 연결 128개를 쓰고 있을 때 새로 연 연결은 `503`과 `too_many_connections`를 받고 닫힙니다. 열린 연결이 닫혀 자리가 나면 새 연결을 다시 받습니다. 그래서 연결이 몰려도 서버가 새 연결을 조용히 놓치지 않고, 수신 버퍼 메모리의 최악값이 약 2 GiB로 묶입니다. `503` 응답은 api 층이 만들고, 연결 수는 같은 mongoose 루프 안에서 셉니다. 리스너 연결은 세지 않습니다. 결정은 `../spec.md`의 Q8과 응답 표를 따릅니다.

**Blocked by:** None (can start immediately)

테스트 시나리오(팀 확인 전). 테스트 이름은 아래 문장을 그대로 씁니다.

- [x] 연결 수 초과 응답은 503과 {"error":"too_many_connections"}이고 Content-Type은 application/json이다
- [x] [T13] (기능) 연결 128개가 열려 있을 때 129번째 연결은 503과 too_many_connections를 받고 닫힌다
- [x] (기능) 열린 연결 하나가 닫혀 자리가 나면 새 연결이 다시 정상 응답을 받는다
- [x] (기능) 129번째 연결이 거절되는 동안에도 이미 열린 연결의 요청은 정상 응답을 받는다

그 밖의 완료 조건:

- [x] 기능 테스트는 10초 안에 끝나고, 연 연결을 모두 닫는다. 03이 함께 병합되면 쉬는 연결은 10초 뒤에 닫히기 때문이다
- [ ] 03과 같은 서버 코드와 api 층을 고치므로, 병합할 때 두 티켓의 변경이 모두 남는지 확인한다
- [x] M1·M2의 기존 테스트가 그대로 통과하고, `make verify`가 통과한다

## Comments

- 연결 수는 `MG_EV_ACCEPT`에서 `manager->conns`를 한 번 돌며 셉니다. 리스너와 `is_closing`인 연결은 빼고, 503을 보내고 닫는 중(`is_draining`)인 연결은 아직 fd와 버퍼를 쥐고 있으므로 셉니다. 새 연결 자신도 목록에 들어 있으므로 센 값이 128을 넘으면 거절합니다.
- mongoose의 `listen` 대기열은 `MG_SOCK_LISTEN_BACKLOG_SIZE` 기본값 3입니다. 기능 테스트는 연결마다 요청 하나에 응답을 받은 뒤 다음 연결을 열어, 대기열이 넘치지 않고 서버가 그 연결을 세었음을 확인합니다.
- 기존 버그를 함께 고쳤습니다. mongoose는 `MG_EV_HTTP_MSG` 전에 `is_resp`를 세우고 `mg_http_reply`만 내리는데, 서버는 `mg_printf`와 `mg_send`로 응답하므로 연결 하나에서 두 번째 요청부터 응답이 오지 않았습니다(M2의 기능 테스트는 요청마다 새 연결을 써서 드러나지 않았습니다). `request_handle`이 응답 뒤 `is_resp`를 내립니다. "이미 열린 연결의 요청은 정상 응답을 받는다" 테스트가 이 수정 없이는 5초 뒤 시간 초과로 실패합니다.
- 503으로 거절한 연결이 닫히기 전에 client의 요청을 읽으면 두 번째 응답을 보내지 않도록, `request_handle`은 `is_draining`인 연결을 건너뜁니다. client가 요청을 보낸 뒤 서버가 읽지 않은 채 닫으면 커널이 리셋을 보내 503을 못 받을 수 있어서, 기능 테스트의 넘친 연결은 요청을 보내지 않고 응답만 읽습니다.
- 연결 상한 기능 테스트 세 개는 ASan 빌드에서 합쳐 약 0.2초에 끝나고(WSL, 2026-11-14), 10번 반복해 모두 통과했습니다.
