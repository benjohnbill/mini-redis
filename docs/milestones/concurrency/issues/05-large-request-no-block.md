# 05: 큰 요청이 도는 중에도 작은 GET이 바로 응답받는다

**Status:** ready-for-agent

**What to build:** 다른 client가 16 MiB value를 저장하거나 조회하는 중에도, 작은 GET은 넉넉한 기한(0.5초) 안에 응답을 받습니다. 이것은 "느린 요청이 다른 요청을 막지 않는다"를 `make verify`에서 확인하는 티켓이고, 서버 코드는 바꾸지 않습니다. 결과가 예상과 다르면 구현하지 말고 팀에 가져옵니다(M2 티켓 05와 같은 방식). 지연의 숫자는 02의 측정이 맡습니다. 결정은 `../spec.md`의 Q11과 Testing Decisions를 따릅니다.

**Blocked by:** None (can start immediately)

테스트 시나리오(팀 확인 전). 테스트 이름은 아래 문장을 그대로 씁니다.

- [x] [T14] (기능) 다른 연결이 16 MiB value를 저장하는 중에도 작은 GET은 0.5초 안에 응답을 받는다
- [x] (기능) 다른 연결이 16 MiB value를 조회해 받아 가는 중에도 작은 GET은 0.5초 안에 응답을 받는다

그 밖의 완료 조건:

- [x] 0.5초는 ASan 빌드 기준의 넉넉한 기한이다. 서버를 SIGSTOP으로 멈추면 같은 확인이 실패하는 것도 한 번 따로 확인해 `## Comments`에 적는다
- [x] `make verify`가 통과한다

## Comments

- 두 기능 테스트는 서버 코드를 바꾸지 않고 통과했습니다(ASan 빌드). 작은 GET은 매번 새 연결로 보내고, 0.5초 안에 `404 key_not_found`가 와야 통과합니다. 두 테스트는 합해서 약 0.5초 걸립니다.
- 저장 테스트는 헤더(`Content-Length: 16777216`)를 보낸 뒤 body를 1 MiB씩 쉬지 않고 보내고, 4 MiB마다(0, 4, 8, 12 MiB를 보낸 뒤) 작은 GET을 보냅니다. 끝까지 보낸 뒤 `204`와 같은 value의 조회를 확인합니다.
- 조회 테스트는 16 MiB를 먼저 저장하고, 다른 연결에서 GET을 보내 헤더만 읽은 뒤 body를 1 MiB씩 받습니다. 4 MiB마다(0, 4, 8, 12 MiB를 받기 전) 작은 GET을 보냅니다. 끝까지 받은 뒤 `200`, `Content-Length`, body가 저장한 value와 같은지 확인합니다.
- 한 번 잰 작은 GET의 시간: 저장 중 0.0015~0.0142초, 조회 중 0.0016~0.0106초였습니다. 0.5초는 이 값보다 30배 넘게 넉넉합니다.
- 서버를 SIGSTOP으로 멈추면 같은 확인이 실패하는 것을 테스트 밖에서 한 번 따로 확인했습니다. 두 테스트의 첫 작은 GET 직전에 서버를 멈추자, 두 테스트 모두 첫 작은 GET이 0.501초에 `TimeoutError`로 실패했습니다. 서버가 막히면 이 테스트가 잡습니다.
