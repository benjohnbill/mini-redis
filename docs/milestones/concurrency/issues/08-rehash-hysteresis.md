# 08: rehash가 경계에서 반복되지 않게 줄이는 기준을 늦춘다

**Status:** ready-for-agent

**What to build:** entry 수가 2의 거듭제곱 경계에 있는 store에 저장과 삭제가 번갈아 와도, 요청마다 entry 전부를 옮기지 않습니다. `hash.c`의 `rehash`는 버킷당 entry가 `MIN_ELEMS_PER_BUCKET`(1) 이상 `MAX_ELEMS_PER_BUCKET`(4) 이하인 동안 버킷 수를 바꾸지 않습니다. 두 상수는 Pintos가 정해 두고도 쓰지 않던 기준입니다. key 수가 2배로 늘어나는 순간의 한 번 멈춤은 남기고 한계로 기록합니다. 결정은 `../spec.md`의 "rehash: 나눠 옮기기에서 줄이는 기준 늦추기로 변경"을 따릅니다.

**Blocked by:** 06

테스트 시나리오(팀 확인 전). 테스트 이름은 아래 문장을 그대로 씁니다.

- [x] key를 많이 넣었다가 대부분 지워도 남은 key를 모두 조회하고 지운 key는 조회되지 않는다
- [x] 같은 key를 저장하고 지우기를 반복해도 다른 key를 모두 조회할 수 있다

그 밖의 완료 조건:

- [x] `hash.h`의 공개 함수와 `store.c`는 바꾸지 않는다
- [x] `make bench`의 `c-rehash`(경계에서 저장과 삭제 반복)에서 작은 GET의 p99가 10 ms 이하다
- [x] key 수가 2배로 늘어나는 순간의 멈춤을 재는 시나리오 `e-grow-once`를 더하고, 결과를 `../spec.md`의 "측정 결과"에 적는다
- [x] `README.md`의 "알려진 한계"와 `docs/requirements.md` L8의 `남은 일`을 새 결과에 맞춘다
- [x] `make verify`가 통과한다

## Comments

- 바뀐 곳은 `rehash` 앞부분의 검사 하나입니다. 버킷 수를 계산하기 전에, 버킷당 entry 수가 1~4개 안이면 돌아갑니다. 버킷을 늘리고 줄일 때의 새 버킷 수 계산(이상값 2개)은 Pintos 그대로입니다.
- 버킷은 entry가 버킷의 4배를 넘을 때 2배로 늘고, 버킷 수보다 적어질 때 줄어듭니다. 그래서 같은 경계에서 저장과 삭제가 번갈아 와도 버킷 수가 바뀌지 않습니다.
- 다시 잰 결과(3회): `c-rehash`의 작은 GET p99 0.087~0.183 ms(전에는 311~328 ms). `e-grow-once`의 작은 GET p99 212.6~252.8 ms, 버킷을 늘리는 저장 하나 310~350 ms. 나머지 시나리오는 전과 같은 범위입니다. 표는 `../spec.md`의 "기준 늦추기 뒤 재측정"에 있습니다.
- 단위 테스트 두 개는 store의 공개 함수로 버킷이 늘고 줄어도 조회가 맞는지 봅니다. 멈춤이 사라졌는지는 시간을 재야 하므로 `make bench`가 맡습니다.
