# M3 `concurrency`: 여러 요청을 함께 받기

## 요구사항

L8 (`docs/requirements.md`)

## 앞 마일스톤

- M1 `store`: `store_get`은 value를 복사하지 않고 store 안의 주소로 빌려줍니다. 그 주소는 같은 store에 다음 `store_set` 또는 `store_delete`를 부르기 전까지만 유효합니다(ADR `get-lends-value-until-next-change`). rehash는 원소를 한 번에 새 버킷 배열로 옮기므로, rehash가 일어나는 `store_set` 한 번은 오래 걸립니다.
- M2 `api`: 서버는 mongoose 위에서 돌고, 스레드 하나가 `mg_mgr_poll`을 반복해서 부르며 요청을 하나씩 처리합니다. mongoose는 스레드를 스스로 만들지 않습니다. 요청을 store 호출과 응답으로 바꾸는 api 층은 mongoose를 모르므로, 연결 처리를 다시 짜도 api 층과 그 테스트는 그대로 남습니다. 결정과 이유는 `docs/milestones/api/spec.md`와 ADR `http-methods-and-raw-body`에 있습니다.
- M1과 M2가 M3로 넘긴 것:
  - 서버가 빌린 value를 응답으로 보내도 안전한 근거는 "스레드 하나가 요청을 하나씩 처리한다"는 사실 하나뿐입니다.
  - rehash 동안 멈추는 시간.
  - 서버의 `receive_buffer_grow`는 mongoose가 `MG_EV_READ`를 HTTP 처리가 끝난 뒤에 부른다는 순서에 기댑니다.
  - 요청을 끝까지 보내지 않는 연결을 서버가 닫지 않습니다. 클라이언트가 끊을 때까지 파일 디스크립터와 수신 버퍼가 남습니다(README "알려진 한계").
  - 동시에 들어오는 연결의 수에 상한이 없습니다.

## 탐구할 문제

여러 다른 서버가 같은 순간에 mini-redis에 저장, 조회, 삭제를 요청합니다.

1. L8은 "동시성 문제가 발생하지 않도록"이라고 합니다. 우리 서버에서 "동시성 문제"는 무엇인가요? 결과가 틀리는 문제와 응답이 늦어지는 문제를 나눠서 말할 수 있나요? 지금의 서버에서 둘 중 무엇이 실제로 생기나요?
2. 지금 서버에서 요청 하나가 오래 걸리면 다른 요청은 어떻게 되나요? 16 MiB value를 저장하거나 rehash가 일어나는 요청, store를 오래 붙잡는 요청을 예로 들어 보세요. 그 시간을 어떻게 재나요?
3. 두 요청이 정말로 같은 순간에 store를 부른다면, 어떤 순서에서 무엇이 깨지나요? 같은 key에 동시에 저장하는 경우, 조회 중에 같은 key를 지우는 경우, rehash 중에 조회하는 경우를 하나씩 따라가 보세요.
4. `store_get`이 빌려준 주소의 규칙은 그 상황에서도 지켜지나요? 지켜지지 않는다면 바꿀 곳은 store의 약속인가요, 부르는 쪽인가요?
5. 요청을 처리하는 실행 흐름(스레드나 프로세스)을 몇 개 둘 건가요? 연결을 받는 일, HTTP를 해석하는 일, store를 부르는 일, 응답을 보내는 일을 각각 누가 맡나요? 하나보다 많이 둔다면, mongoose의 루프 밖에서 만든 결과를 어떻게 그 연결의 응답으로 돌려보내나요?
6. 고른 구조에서 `receive_buffer_grow`가 기대는 순서는 여전히 성립하나요?
7. 요청을 끝까지 보내지 않는 연결과 너무 많은 연결은 어떻게 다루나요? 몇 개까지 받고, 얼마 동안 기다린 뒤 닫나요? 닫을 때 다른 서버는 무엇을 받나요?
8. 경쟁 조건은 가끔만 드러납니다. 어떤 테스트가 "동시성 문제가 없다"를 보여 줄 수 있나요? 지금 `make verify`는 AddressSanitizer를 켜고 돕니다. 동시성 버그를 찾는 도구가 AddressSanitizer와 함께 켜지지 않는다면, `make verify`와 CI에는 어떻게 넣나요?
9. 발표에서 고른 구조를 그림 하나로 설명하려면, 요청 하나가 서버 안에서 어떤 실행 흐름을 거쳐 응답이 되는지 무엇을 그려야 하나요?
