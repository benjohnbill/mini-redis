# M3 `concurrency` spec

Status: ready-for-agent

요구사항: L8 (`docs/requirements.md`). 문제는 `overview.md`에 있고, 이 문서는 2단계 grill(2026-11-14)에서 팀이 합의한 답입니다.

## Problem Statement

여러 client가 같은 순간에 mini-redis에 저장, 조회, 삭제를 요청합니다. 지금 서버는 스레드 하나가 mongoose 루프를 돌며 요청을 하나씩 끝까지 처리하므로, 동시에 온 요청 때문에 결과가 틀리는 일은 없습니다. 하지만 요청 하나가 오래 걸리면 다른 client는 그 요청이 끝날 때까지 응답을 기다립니다. 16 MiB value를 store로 복사하는 일, rehash가 모든 entry를 한 번에 옮기는 일, 16 MiB 응답을 송신 버퍼로 복사하는 일이 그렇습니다. 특히 rehash는 저장, 덮어쓰기, 삭제에서 모두 일어나고, entry 수가 2의 거듭제곱인 경계에서는 저장과 삭제를 번갈아 보내는 client가 요청마다 entry 전부를 옮기게 만듭니다. 팀은 이 기다림이 얼마인지 잴 방법이 없습니다.

연결 쪽에도 기다림을 만드는 원인이 있습니다. 요청을 끝까지 보내지 않는 연결을 서버가 닫지 않아서, client가 끊을 때까지 파일 디스크립터와 수신 버퍼가 남습니다. 동시에 들어오는 연결의 수에도 상한이 없습니다. 그래서 연결이 쌓이면 새 연결이 조용히 실패하고, 수신 버퍼의 메모리에도 끝이 없습니다. L8은 "동시성 문제가 발생하지 않도록 하려면 어떤 구조를 가져야 할지" 묻는데, 팀은 아직 우리 서버에서 "동시성 문제"가 무엇인지, 그것이 없다는 것을 어떻게 보일지 정하지 않았습니다.

## Solution

L8의 동시성 문제를 지연으로 정의합니다(`GLOSSARY.md`의 **동시성 문제**). 요청 하나를 처리하는 동안 다른 요청의 응답이 늦어지는 것입니다. 서버는 지금처럼 프로세스 1개, 스레드 1개로 모든 요청을 처리하므로, 동시에 온 요청 때문에 결과가 틀리는 문제는 구조상 생기지 않습니다(ADR `single-thread-event-loop`).

그 위에서 지연을 세 가지로 다룹니다.

- **연결 지키기:** 10초 동안 바이트가 한 번도 오가지 않는 연결은 `408`과 `request_timeout`을 받고 닫힙니다. 동시 연결이 128개를 넘으면 새 연결은 `503`과 `too_many_connections`를 받고 닫힙니다.
- **재기:** 방해가 없을 때의 기준선과 처리량은 wrk로 재고(실험실), 16 MiB 저장, 4,194,304개 경계의 rehash, 16 MiB 삭제가 섞일 때 작은 GET의 지연은 python 열린 루프로 잽니다(실제 시나리오). 둘 다 `make verify` 밖의 별도 명령이고, 숫자는 이 문서에 적습니다.
- **목표:** 방해 요청이 있어도 작은 GET의 p99는 10 ms 이하입니다. 측정 결과 목표를 넘는 항목은 드라이버가 판단해 줄이고, 그 원리를 PR에 적습니다.

`make verify`는 기능의 존재(느린 요청이 다른 요청을 막지 않음, 타임아웃, 연결 상한)를 넉넉한 기한으로 확인하고, 지연의 숫자는 측정이 맡습니다.

## User Stories

1. client 개발자로서, 다른 client가 16 MiB value를 저장하는 중에도 내 작은 조회가 곧바로 응답받기를 원합니다.
2. client 개발자로서, 다른 client가 16 MiB value를 조회하거나 삭제하는 중에도 내 작은 요청이 곧바로 응답받기를 원합니다.
3. client 개발자로서, store에 key가 수백만 개 있어도 내 조회가 rehash 때문에 오래 멈추지 않기를 원합니다.
4. client 개발자로서, 방해 요청이 있어도 작은 조회의 p99가 10 ms 이하이기를 원합니다. 그래야 원본 API 대신 mini-redis를 캐시로 쓸 이유가 생깁니다(L15, L17).
5. client 개발자로서, 동시에 같은 key에 저장, 조회, 삭제를 보내도 각 응답이 요청을 하나씩 처리한 어떤 순서의 결과와 같기를 원합니다.
6. client 개발자로서, 조회 응답의 value가 다른 client의 덮어쓰기나 삭제 때문에 중간에 바뀌거나 깨지지 않기를 원합니다.
7. client 개발자로서, 헤더나 body를 보내다 10초 동안 멈추면 `408`과 `{"error":"request_timeout"}`을 받기를 원합니다. 그래야 연결이 끊긴 이유를 네트워크 오류와 구분할 수 있습니다.
8. client 개발자로서, 큰 body를 느린 네트워크로 꾸준히 보내거나 16 MiB 응답을 천천히 받아 가는 동안에는 10초가 지나도 연결이 끊기지 않기를 원합니다. 기한은 마지막으로 바이트를 주고받은 뒤부터 세기 때문입니다.
9. client 개발자로서, 응답을 받은 뒤 다음 요청 없이 쉬는 연결은 10초 뒤에 응답 없이 닫히는 것을 알기를 원합니다. 그래야 연결을 다시 열 때를 압니다.
10. client 개발자로서, 서버가 연결 128개를 쓰고 있을 때 새로 연 연결이 `503`과 `{"error":"too_many_connections"}`를 받고 닫히기를 원합니다. 그래야 잠시 뒤에 다시 시도할 수 있습니다.
11. client 개발자로서, 다른 연결이 닫혀 자리가 나면 새 연결이 다시 정상으로 받아들여지기를 원합니다.
12. client 개발자로서, `408`과 `503`의 body도 M2의 다른 오류처럼 `{"error":"<오류 이유>"}` JSON이고 `Content-Type`이 `application/json`이기를 원합니다.
13. client 개발자로서, 요청을 끝까지 보내지 않는 다른 client가 여럿 있어도 내 요청이 응답받기를 원합니다.
14. client 개발자로서, `README.md`의 "API" 절에서 `408`, `503`, 연결 상한, 쉬는 시간 기한을 읽을 수 있기를 원합니다.
15. 운영하는 팀원으로서, 끝나지 않는 연결이 파일 디스크립터와 수신 버퍼를 무한히 붙잡지 않기를 원합니다.
16. 운영하는 팀원으로서, 수신 버퍼 메모리의 최악값이 연결 상한으로 약 2 GiB(128 × 16 MiB)에 묶이기를 원합니다.
17. 운영하는 팀원으로서, 연결이 몰려도 서버가 죽거나 새 연결을 조용히 놓치지 않고, 넘친 연결에 이유를 알리기를 원합니다.
18. 팀원으로서, 서버가 프로세스 1개, 스레드 1개로 연결 받기, HTTP 해석, store 호출, 응답 보내기를 모두 맡는다는 사실 하나로 "결과가 틀리지 않는다"를 설명하기를 원합니다.
19. 팀원으로서, 타임아웃과 연결 상한을 검사하는 일도 같은 mongoose 루프 안에서 하고, 타이머 스레드를 따로 두지 않기를 원합니다.
20. 팀원으로서, `store_get`이 빌려준 value를 응답으로 보내도 안전한 근거(스레드 하나가 요청을 하나씩 처리)가 M3에서도 그대로 지켜지기를 원합니다.
21. 팀원으로서, 수신 버퍼 늘리기가 기대는 mongoose의 이벤트 순서가 M3에서도 그대로 성립하기를 원합니다.
22. 팀원으로서, `408`과 `503` 응답을 api 층이 만들기를 원합니다. 그래야 M2의 `411`, `413`처럼 오류 body를 한 곳에 두고 단위 테스트로 확인합니다.
23. 측정하는 팀원으로서, 방해가 없을 때 작은 GET 100연결의 p50, p99와 초당 처리량을 wrk 명령 하나로 재기를 원합니다.
24. 측정하는 팀원으로서, 16 MiB 저장, rehash 경계의 저장과 삭제, 16 MiB 삭제가 도는 동안 작은 GET의 지연을 python 스크립트로 재기를 원합니다.
25. 측정하는 팀원으로서, 작은 GET을 정해진 시각마다 보내고 지연을 "보냈어야 할 시각"부터 재기를 원합니다. 그래야 서버가 멈춘 동안 쌓인 기다림이 숫자에서 빠지지 않습니다.
26. 측정하는 팀원으로서, 요청 종류별로 지연을 따로 보기를 원합니다. 그래야 "작은 GET만의 p99"를 방해 요청의 지연과 섞지 않습니다.
27. 측정하는 팀원으로서, store에 4,194,304개(2²²)를 빠르게 미리 채우고, 그 경계에서 저장과 삭제를 번갈아 보내는 시나리오를 재기를 원합니다.
28. 측정하는 팀원으로서, 측정은 sanitizer를 끈 최적화 빌드에서 하기를 원합니다. AddressSanitizer 빌드는 몇 배 느려서 숫자에 의미가 없기 때문입니다.
29. 측정하는 팀원으로서, 측정 명령이 `make verify`와 CI에 들어가지 않기를 원합니다. 시간 기준의 판정은 머신마다 흔들리기 때문입니다.
30. 측정하는 팀원으로서, 측정 결과와 측정 환경(머신, 빌드, 명령)을 이 문서에 적어 6단계에서 Redis 숫자와 나란히 보기를 원합니다.
31. 드라이버로서, 측정 결과 목표를 넘는 항목이 나오면 직접 판단해 줄이고, 무엇이 넘었고 어떤 원리로 줄였는지 PR에 적기를 원합니다.
32. 테스트 작성자로서, 16 MiB 저장이 처리되는 중에도 작은 GET이 넉넉한 기한 안에 응답받는지 `make verify`에서 확인하기를 원합니다.
33. 테스트 작성자로서, 헤더나 body를 보내다 10초 동안 멈춘 연결이 `408`을 받고 닫히는지 `make verify`에서 확인하기를 원합니다.
34. 테스트 작성자로서, 129번째 연결이 `503`을 받고, 자리가 나면 다시 받아들여지는지 `make verify`에서 확인하기를 원합니다.
35. 테스트 작성자로서, api 층의 공개 함수만 불러 `408`, `503` 응답의 상태 코드와 오류 body를 소켓 없이 확인하기를 원합니다.
36. 테스트 작성자로서, 새 테스트가 CI에 새 의존성을 들이지 않기를 원합니다. wrk는 측정에만 쓰고 `make verify`에는 쓰지 않습니다.
37. 발표하는 팀원으로서, 스레드 하나가 여러 연결의 이벤트를 번갈아 처리하고 어디서 멈추는지를 측정 숫자와 함께 설명하기를 원합니다.

## Implementation Decisions

grill의 질문 번호(Q1~Q14)와 overview의 문제 번호를 함께 적습니다.

- **모듈:** 서버는 연결 수를 세고, 연결마다 마지막으로 바이트를 받은 시각을 기억해 쉬는 시간 기한을 검사합니다. api 층에는 `408`과 `503` 응답을 만드는 공개 함수를 더합니다. store와 `hash.c`는 고치지 않습니다(Q13 보류 참고). 측정 도구 두 가지(wrk 실험실 스크립트, python 열린 루프 스크립트)를 새로 만듭니다.
- **Q1 동시성 문제의 정의:** 동시성 문제는 지연 문제입니다. 요청 하나를 처리하는 동안 다른 요청의 응답이 늦어지는 것을 말하고, 동시에 온 요청 때문에 결과가 틀리는 문제는 이 말에 넣지 않습니다. 결과가 틀리는 문제는 Q6의 구조가 생기지 않게 합니다.
- **Q6 실행 흐름 (문제 5):** 서버는 프로세스 1개, 스레드 1개로 돕니다. 그 스레드가 mongoose 루프 안에서 연결 받기, HTTP 해석, store 호출, 응답 보내기를 모두 맡고, store를 부르지 않는 보조 일(큰 메모리 해제, 타이머)도 다른 스레드에 맡기지 않습니다(ADR `single-thread-event-loop`). 이유: 스레드가 하나면 "결과가 틀리지 않는다"의 근거가 그 한 문장으로 끝납니다.
- **문제 3, 4 store 호출과 빌린 value:** store를 동시에 부르는 순간이 없으므로, 같은 key 동시 저장, 조회 중 삭제, rehash 중 조회에서 깨지는 순서가 없습니다. `store_get`이 빌려준 주소의 규칙은 그대로 지켜지고, store의 약속도 부르는 쪽도 바꾸지 않습니다. ADR `get-lends-value-until-next-change`는 그대로 유효합니다.
- **문제 6 수신 버퍼 늘리기:** 서버의 구조(mongoose 루프 하나)가 바뀌지 않으므로, 수신 버퍼 늘리기가 기대는 순서(mongoose가 `MG_EV_READ`를 HTTP 처리가 끝난 뒤에 부름)도 그대로 성립합니다. 타임아웃과 연결 상한을 더하는 코드는 수신 버퍼를 옮기지 않습니다.
- **Q4 쉬는 시간 기한 (문제 7):** 연결에서 마지막으로 바이트를 주고받은 뒤(받기와 보내기 모두) 10초 동안 바이트가 오가지 않으면, 요청을 받는 중이면 `408`과 `request_timeout`을 보낸 뒤 연결을 닫고, 응답을 보낸 뒤 다음 요청을 기다리며 쉬는 중이면 응답 없이 닫습니다. 검사는 같은 mongoose 루프 안에서 합니다. 보내기도 기준에 넣는 이유(to-spec 확인에서 결정, 2026-11-14): 받은 때만 세면 초당 1.6 MB보다 느린 client는 16 MiB 응답을 끝까지 받지 못합니다. 느린 정상 전송은 자르지 않고 악용은 연결 상한으로 묶는다는 원칙을 받기와 보내기에 똑같이 적용합니다. 바이트를 아주 조금씩 계속 보내거나 받아 가는 연결은 이 규칙을 피하므로, 그 피해는 Q8의 연결 상한으로 묶습니다. 버린 대안: 요청 전체 기한(헤더부터 body 끝까지 M초)은 느린 네트워크로 16 MiB를 보내는 정상 요청도 자를 수 있습니다.
- **아무것도 보내지 않은 새 연결 (5단계에서 결정, 2026-11-14):** 연결만 열고 바이트를 하나도 보내지 않은 연결은 10초 뒤 응답 없이 닫습니다. `408`은 수신 버퍼에 받던 요청 조각이 있을 때만 보냅니다. 이유: 시작된 요청이 없으므로 "요청 시간 초과"를 알릴 대상이 없고, 응답 뒤에 쉬는 연결과 같은 규칙으로 다룰 수 있습니다.
- **닫는 중인 연결의 요청 (5단계에서 결정, 2026-11-14):** 서버는 닫기로 표시한 연결(`408`, `503`, `411`, `413`을 보낸 연결)에 온 요청을 처리하지 않습니다. 이유: 거절한 연결에는 거절 응답 하나만 가야 합니다. 또 mongoose는 연결을 닫을 때 받다 만 요청도 받은 데까지를 body로 삼아 요청 이벤트를 부르므로, 이 처리가 없으면 `408`이나 M2의 `413` 뒤에 잘린 body가 저장됩니다(티켓 03에서 확인). client가 body 중간에 스스로 연결을 끊는 경우는 이 처리가 막지 않으며, M3의 범위 밖입니다.
- **keep-alive 버그 (5단계에서 결정, 2026-11-14):** 연결 하나로 보낸 두 번째 요청부터 응답이 오지 않던 M2의 버그(티켓 04에서 확인)는 M3와 따로 버그 수정 PR(`DA-keepalive`)로 고칩니다. M3의 연결 재사용 기능과 wrk 측정이 이 수정에 기대므로, M3 PR은 그 PR이 병합된 뒤에 올립니다.
- **Q8 연결 수 상한 (문제 7):** 동시 연결은 128개까지 받습니다. 129번째 연결은 받은 뒤 `503`과 `too_many_connections`를 보내고 닫습니다. 리스너 연결은 세지 않습니다. 이유: 128은 Q2의 기준 100연결을 다 받으면서 수신 버퍼 메모리의 최악값을 약 2 GiB로 묶습니다. 넘친 연결에 오류 이유를 보내는 것은 M2의 원칙(오류마다 고정된 오류 이유)과 같습니다. 버린 대안: 512(최악 메모리 약 8 GiB), 상한 없음(파일 디스크립터 상한에서 조용히 실패), 응답 없이 닫기(네트워크 오류와 구분 불가), 자리가 날 때까지 받지 않기(client에게 멈춘 것처럼 보임).
- **응답 표에 더하는 줄:**

  | 상황 | 상태 코드 | body |
  |---|---|---|
  | 요청을 받는 중 10초 동안 바이트가 오가지 않음 | `408` | `request_timeout` |
  | 동시 연결이 128개일 때 새 연결 | `503` | `too_many_connections` |

  두 응답 모두 오류 body는 `{"error":"<오류 이유>"}`이고 `Content-Type`은 `application/json`이며, 보낸 뒤 연결을 닫습니다. 응답은 api 층이 만들고 서버가 보냅니다.
- **Q2 기준 규모:** 측정과 테스트의 기준은 동시 연결 100개입니다. 요청은 대부분 1 KiB 이하의 작은 value이고, 일부만 상한 크기인 16 MiB value입니다. 이유: 파일 디스크립터 기본 상한(1024) 안에서 노트북 한 대로 재현할 수 있습니다.
- **Q3 측정 방법 (문제 2):** 기준 지표는 "작은 GET 하나의 응답 시간"입니다.
  - 실험실(wrk): 방해가 없을 때 작은 GET 100연결의 p50, p99와 초당 처리량을 잽니다. 요청 한 종류만 보내므로 멈춤이 없고, 닫힌 루프의 약점이 숫자에 영향을 주지 않습니다.
  - 실제 시나리오(python 표준 라이브러리): 작은 GET을 정해진 시각마다 보내고(열린 루프), 지연을 보냈어야 할 시각부터 잽니다. 요청 종류별로 따로 기록하고, 방해 요청(16 MiB 저장, rehash 경계의 저장과 삭제 반복, 16 MiB 삭제)을 시간표대로 넣습니다.
  - 둘 다 sanitizer를 끈 최적화 빌드에서 `make verify` 밖의 별도 명령 `make bench` 하나로 돌리고(이름은 to-spec 확인에서 결정, 2026-11-14), 하나만 돌릴 때는 스크립트를 직접 실행합니다. 그리고 결과 숫자와 환경을 이 문서의 "측정 결과" 절에 적습니다. wrk 설치(`sudo apt install wrk`)는 측정하는 팀원에게만 필요합니다.
  - 버린 대안: wrk, hey, ab만 쓰기(닫힌 루프라서 서버가 멈춘 동안의 기다림이 숫자에서 빠지고, 요청 종류별 지연을 나눌 수 없음), hey를 함께 쓰기(URL 하나만 보내서 wrk와 역할이 겹침), `make verify` 안의 시간 기준 테스트(머신마다 흔들리고 ASan 빌드의 숫자는 의미가 없음).
- **Q9 rehash 시나리오:** store에 4,194,304개(2²², value 약 100바이트)를 넣고, 그 경계에서 새 key 저장과 삭제를 번갈아 보냅니다. 지금 `hash.c`는 버킷 수를 "entry 수 ÷ 2보다 작거나 같은 가장 큰 2의 거듭제곱(최소 4)"로 맞추고, 그 값이 바뀔 때마다 `hash_insert`, `hash_replace`, `hash_delete` 어디서든 entry 전부를 한 번에 옮깁니다. 그래서 이 경계에서는 요청마다 rehash가 일어납니다. 미리 채우기는 wrk의 Lua 스크립트(요청마다 key를 바꿈)로 하고, 지연은 python으로 잽니다. 이유: 500만 개 규모를 재려는 의도에서, rehash가 요청마다 일어나는 최악의 경우를 만들 수 있는 가장 가까운 값입니다.
- **Q10 목표 (2단계 끝에 확정, 2026-11-14):** 방해 요청이 있어도 작은 GET의 p99는 10 ms 이하입니다. 이유: mini-redis를 쓰는 목적은 원본 API의 응답을 담아 두는 캐시(L15, L17)이고, 원본 API는 보통 수십 ms 이상 걸립니다. mini-redis의 꼬리 지연이 원본에 가까우면 캐시를 쓴 쪽이 더 느려집니다. 같은 컴퓨터의 Redis는 방해가 있어도 p99가 2 ms 안이었으므로("Redis와 대조"), HTTP를 해석하는 비용을 감안해 5배쯤 여유를 둡니다. 버린 대안: p99 100 ms(원본 API보다 느린 꼬리 지연을 허용함), 숫자 없이 측정 뒤 판단(기준이 결과에 끌려감).
- **Q14 목표를 넘는 항목:** 측정에서 목표를 넘는 항목(16 MiB 복사, 큰 `free`, rehash 등)이 나오면 드라이버가 판단해 줄이고, 무엇이 넘었고 어떤 원리로 줄였는지 PR 본문에 적습니다. 팀은 리뷰에서 그 원리를 확인합니다(`CONVENTION.md` 6번). 결정은 이 문서에도 "(5단계에서 결정, 날짜)"로 더합니다.
- **Q13 rehash를 줄이는 방법 (보류):** 측정에서 rehash가 목표를 넘을 때만 정합니다. 후보는 나눠 옮기기, 줄이는 기준 늦추기, 버킷을 처음부터 크게 잡기, 한계로 기록하기입니다. 앞의 세 방법은 모두 `hash.c`의 `rehash`를 고쳐야 하고, 이것은 L2의 해석 "해시 테이블 자료구조는 Pintos `hash.c`를 가져다 쓴다(팀과 코치 합의)"에 닿습니다. 그래서 고치게 되면 코치에게 먼저 확인합니다. store 층에서 테이블 두 개로 나눠 옮기는 방법은 새 테이블이 커질 때 `hash.c`가 다시 한 번에 rehash하므로 멈춤이 사라지지 않습니다.
- **rehash의 초과와 Q13의 답 (5단계에서 결정, 2026-11-14):** rehash 경계에서 저장과 삭제를 반복하는 중 작은 GET의 p99는 311~328 ms로 목표의 약 30배입니다("측정 결과"의 "목표와 대조"). Q13의 답은 나눠 옮기기입니다. 옛 테이블과 새 테이블을 함께 두고 요청마다 조금씩 옮겨, 요청 하나의 멈춤에 상한을 둡니다. 이유: 줄이는 기준 늦추기는 경계에서의 반복만 없애고 버킷이 두 배가 될 때의 멈춤(약 419만 개에서 약 300 ms)을 남겨서 목표를 지키지 못합니다. `hash.c`를 고치는 것은 L2의 합의에 어긋나지 않습니다(드라이버 확인: 수정을 예상하고 있었음). PR은 나눕니다. 이 PR은 rehash의 멈춤을 한계로 기록하고, 나눠 옮기기는 08번 티켓부터 다음 PR로 합니다.
- **16 MiB 저장의 초과 (5단계에서 결정, 2026-11-14):** 16 MiB 저장을 반복하는 중 작은 GET의 p99는 10.7~11.0 ms로 목표를 약 1 ms 넘습니다("측정 결과"의 "목표와 대조"). 줄이지 않고 한계로 기록합니다. 이유: 초과가 약 1 ms이고 상한 크기의 value를 초당 5번 저장할 때만 생기며, 줄이는 방법(body 상한 낮추기, store가 수신 버퍼를 복사 없이 넘겨받기)은 모두 M1, M2의 결정을 바꿉니다. 예상하지 못한 결과이므로 PR 본문과 `README.md`의 "알려진 한계"에 눈에 띄게 적습니다.
- **Q5 용어:** 요청을 보내는 쪽은 `client`, L8의 동시성 문제는 **동시성 문제**로 씁니다(`GLOSSARY.md`, 2단계에서 더함).

## Testing Decisions

- **좋은 테스트:** 공개 함수나 HTTP 요청처럼 바깥에서 보이는 동작만 확인합니다. 기대하는 상태 코드와 body는 검사 대상 코드로 계산하지 않고 직접 적습니다. 연결 수를 세는 변수나 타이머의 내부는 확인하지 않습니다.
- **seam 두 개 (to-spec에서 팀 확인, 2026-11-14):** M2의 두 seam을 그대로 쓰고 새 seam은 만들지 않습니다.
  - api 층의 공개 함수: 소켓과 mongoose 없이 `408`과 `503` 응답의 상태 코드, `Content-Type`, 오류 body를 확인합니다. 선례는 M2의 `411`, `413` 응답 테스트입니다.
  - 실제 서버: 서버를 띄우고 바깥에서 연결과 요청을 보냅니다. 16 MiB 저장 중의 작은 GET, 10초 뒤의 `408`, 쉬는 연결이 닫힘, 129번째 연결의 `503`, 자리가 난 뒤 다시 받아들임을 확인합니다. 선례는 M2의 "느린 연결이 있어도 다른 요청은 바로 응답을 받는다" 테스트이고, 같은 방식으로 넉넉한 기한(ASan 빌드 기준)을 둡니다.
- **파일과 도구:** api 층의 테스트는 CONVENTION대로 `tests/concurrency_test.c` 하나에 acutest의 한국어 문장 이름으로 적습니다. 기능 테스트는 `tests/functional/`에 두고 python3 표준 라이브러리만 씁니다. `make verify`가 두 테스트를 모두 실행합니다.
- **Q11 `make verify`의 범위 (문제 8):** 기능의 존재(막히지 않음, 타임아웃, 상한)는 CI가 맡고, 지연의 숫자는 측정이 맡습니다. rehash 멈춤은 ASan 빌드에서 400만 개를 HTTP로 넣으면 몇 분이 걸리므로 측정에서만 봅니다. 스레드가 없으므로 ThreadSanitizer는 쓰지 않습니다.
- **10초 기다림 (to-spec 확인에서 결정, 2026-11-14):** 기능 테스트는 서버의 10초 기한을 실제로 기다립니다. 기한을 바꾸는 서버 인자나 테스트용 빌드는 만들지 않습니다. 이유: 테스트에 맞춰 서버 코드를 바꾸는 것보다 `make verify`가 약 10초 늘어나는 편이 낫습니다. `408` 확인과 쉬는 연결이 닫힘 확인은 같은 기다림 안에서 함께 해서, 기다림이 두 번 쌓이지 않게 합니다.
- **격리:** api 층의 테스트는 테스트마다 새 store를 만들고 없앱니다. 기능 테스트는 테스트마다 서로 다른 key를 쓰고, 연결 상한 테스트가 연 연결은 테스트가 끝날 때 모두 닫아 다른 테스트에 영향을 주지 않게 합니다.
- **시나리오 후보 (4단계에서 팀이 확인):** User Stories 1~13, 32~35의 각 줄.
- **테스트하지 않는 것:** 지연 목표(p99 ≤ 10 ms)는 측정으로 확인하고 자동 테스트로 판정하지 않습니다. 바이트를 아주 조금씩 계속 보내는 연결은 막지 않으므로 테스트하지 않습니다.
- **ID:** ADR의 `결정:` 줄이나 `docs/requirements.md`의 `근거` 칸이 인용하는 테스트에만 ID를 붙이고, `T11` 다음 번호부터 씁니다. 어느 테스트를 인용할지는 4단계에서 정합니다.

## Out of Scope

- 여러 스레드, 여러 프로세스, 소켓 읽기와 쓰기만 맡는 I/O 스레드, 큰 메모리를 해제하는 백그라운드 스레드: Q6에서 프로세스 1개, 스레드 1개로 정했습니다.
- rehash 나눠 옮기기의 구현: 이 PR의 범위 밖입니다. 08번 티켓부터 다음 PR로 합니다("rehash의 초과와 Q13의 답").
- 바이트를 아주 조금씩 계속 보내는 연결을 막는 규칙(요청 전체 기한): 피해는 연결 상한으로 묶습니다.
- client마다의 요청 수 제한, 연결 수를 client(IP)마다 나누는 상한.
- 연결 상한과 쉬는 시간 기한을 실행 중에 바꾸는 설정.
- 보관 기간: M4 `expire`. 메모리가 가득 찰 때 key를 내보내는 정책(eviction): LMS에 없습니다.
- 발표 그림(overview 문제 9): Q12 보류. 6단계에서 정합니다.

## Redis와 대조

Redis 8.0.5를 WSL(Ubuntu 26.04)에 설치해, 설정 기본값은 `CONFIG GET`으로, 지연은 `redis-benchmark`로 확인했습니다(2026-11-14). 6단계에서 팀이 배운 것을 이 절에 더합니다.

| 주제 | 우리 생각 | Redis의 방식 | 우리가 고른 것 |
|---|---|---|---|
| 동시성 문제의 뜻 | 요청 하나 때문에 다른 요청의 응답이 늦어지는 지연입니다. | 명령을 하나씩 실행하므로 명령 하나는 다른 명령과 섞이지 않습니다(원자적). 오래 걸리는 명령이 다른 client를 기다리게 하는 지연을 주의점으로 둡니다. | 같은 생각입니다. |
| 실행 흐름 | 프로세스 1개, 스레드 1개. 보조 일도 다른 스레드에 맡기지 않습니다. | 명령 실행은 주 스레드 하나가 이벤트 루프(epoll)에서 합니다. 큰 값의 해제(`UNLINK`, lazyfree 설정)와 디스크 동기화는 백그라운드 스레드가 맡고, 소켓 읽기와 쓰기만 나눠 맡는 I/O 스레드도 켤 수 있습니다(`io-threads` 기본 1, 곧 꺼짐). `DEL`의 lazyfree(`lazyfree-lazy-user-del`)도 기본은 꺼져 있습니다. | 핵심(명령 실행은 스레드 하나)은 같고, 보조 스레드를 두지 않는 점이 다릅니다. |
| rehash | 지금은 한 번에 모두 옮깁니다. 줄이는 방법은 측정 뒤에 정합니다. | 테이블 두 개를 함께 두고, 명령이 올 때마다 버킷 하나씩 옮기며, 쉴 때는 주기 작업이 조금씩 옮깁니다(`activerehashing` 기본 yes). 늘릴 때와 줄일 때 기준이 달라서, 원소 수가 버킷 수의 약 1/8~1/10 아래로 떨어져야 줄입니다(버전마다 조금 다름). | 나눠 옮기기(5단계에서 결정, 구현은 다음 PR). Redis는 "나눠 옮기기"와 "줄이는 기준 늦추기"를 함께 씁니다. |
| 쉬는 연결 | 10초 동안 바이트가 오지 않으면 `408`을 보내고 닫습니다. | `timeout` 기본값이 0이라 쉬는 client를 닫지 않습니다. 대신 client 하나의 입력 버퍼가 `client-query-buffer-limit`(기본 1 GB)을 넘으면 그 연결을 닫습니다. | 10초 기한. Redis와 다릅니다. 2단계 끝 대조에서 팀이 바꾸지 않기로 했습니다. |
| 연결 수 상한 | 128개, 넘치면 `503 too_many_connections`를 보내고 닫습니다. | `maxclients` 기본 10000이고, 넘치면 연결을 받은 뒤 `-ERR max number of clients reached`를 보내고 닫습니다. | 방식은 같고, 숫자가 다릅니다. |
| 큰 value | body 상한 16 MiB입니다. | 문자열 하나의 상한 `proto-max-bulk-len`이 기본 512 MB입니다. | M2에서 정한 대로 16 MiB입니다. |
| 지연 측정 | wrk 실험실과 python 열린 루프를 `make verify` 밖에 둡니다. | `redis-benchmark`(닫힌 루프), `redis-cli --latency`, 서버 안의 `LATENCY` 모니터와 slowlog(느린 명령 기록)를 씁니다. | 바깥에서 재는 도구만 만듭니다. 서버 안에서 재는 도구는 범위 밖입니다. |

Redis의 지연(WSL, `redis-benchmark -c 100`, 작은 GET, value 100바이트, ms):

| 경우 | p50 | p99 | max |
|---|---|---|---|
| 방해 없음(key 10만 개) | 0.247 | 0.975 | 5.263 |
| 16 MiB 값 저장을 20번 반복하는 중 | 0.263 | 2.023 | 3.911 |
| 4,194,304개를 넣고 경계에서 저장과 삭제를 반복하는 중 | 0.295 | 1.271 | 3.503 |

`redis-benchmark`는 닫힌 루프라서 멈춘 순간이 실제보다 작게 잡힐 수 있고, 방해 요청과 측정 요청이 정확히 겹쳤는지는 따로 확인하지 않았습니다. 그래서 이 숫자는 목표(Q10)를 정할 때 참고한 비교 자료입니다.

- 빌드: `make bench`가 `build/bench/mini-redis`를 `-std=c11 -Wall -Wextra -Werror -O2`로 만듭니다. sanitizer는 끄고 `assert`는 남깁니다. mongoose에는 `make verify`와 같은 `-D_DEFAULT_SOURCE -DMG_MAX_RECV_SIZE=16842752`를 줍니다.
- 명령: `make bench`. 시나리오 `lab`, `a-quiet`, `b-big-store`, `c-rehash`, `d-big-delete`를 차례로 돌립니다(약 2분). 시나리오 하나만 돌릴 때는 `python3 -B scripts/bench/bench.py build/bench/mini-redis lab`처럼 이름을 줍니다. 시나리오마다 서버를 새로 띄우고, 끝나면 SIGTERM으로 끕니다.

### 실험실 기준선 (티켓 01, 2026-11-14)

key 100,000개(value 100바이트)를 미리 채운 뒤, 그 key 가운데 무작위 하나를 고르는 작은 GET만 100연결로 10초 동안 보냈습니다. 지연은 wrk가 잰 값이고, 단위는 ms입니다. 서버는 쉬는 시간 기한(03)과 연결 수 상한(04)을 합친 코드입니다.

```console
$ wrk -t4 -c100 -d600s -s scripts/bench/prefill.lua <url> -- 100000 4 100 <완료 표시 디렉터리>
$ wrk --latency -t4 -c100 -d10s -s scripts/bench/lab_get.lua <url> -- 100000
```

| 회 | p50 | p99 | 초당 처리량 |
|---|---|---|---|
| 1 | 0.285 | 0.488 | 318,702 |
| 2 | 0.284 | 0.476 | 321,091 |
| 3 | 0.276 | 0.453 | 329,079 |

방해가 없을 때 작은 GET의 p99는 목표(Q10, 10 ms)의 약 1/20입니다. "Redis와 대조"의 방해 없음(p50 0.247, p99 0.975)과 도구가 달라(`redis-benchmark`와 wrk) 나란히 놓고 볼 때만 참고합니다.

### 미리 채우기 (티켓 01, 2026-11-14)

티켓 01의 `prefill` 시나리오가 key 4,194,304개(2²²)를 14.8초에 저장했습니다(초당 약 283,000개). 티켓 02부터는 `c-rehash` 시나리오가 같은 미리 채우기로 시작하므로 `prefill` 시나리오는 따로 두지 않습니다. 채운 뒤 처음, 가운데, 끝과 무작위 key 8개를 조회해 value가 맞는지 보고, 범위 밖 key `prefill-4194304`는 없음(`404`)을 확인합니다. key 100,003개로 미리 채운 뒤 모든 key를 하나씩 조회해, 빠진 key와 범위 밖 key가 없음도 한 번 확인했습니다.

```console
$ wrk -t4 -c100 -d600s -s scripts/bench/prefill.lua <url> -- 4194304 4 100 <완료 표시 디렉터리>
```

이 저장 동안 wrk가 잰 최대 지연은 328.46 ms였습니다. 저장만 보내는 닫힌 루프의 값이라, 작은 GET의 지연은 열린 루프 시나리오(티켓 02)가 잽니다.

- wrk는 시간으로 끝나므로, 스레드마다 맡은 저장의 응답을 모두 받으면 그 스레드를 멈추고 표시 파일을 남깁니다. `bench.py`는 표시 파일이 스레드 수만큼 생기면 wrk에 SIGINT를 보냅니다.
- 저장의 응답(`204`)에는 헤더가 없어 wrk가 Lua의 `response()`를 부르지 않습니다. 그래서 받은 응답의 수를 `request()`가 불린 횟수에서 연결 수를 빼서 셉니다. wrk 4.1.0은 시작 전에 첫 스레드의 `request()`를 한 번 더 부르므로 그 호출은 세지 않습니다. 자세한 내용은 `scripts/bench/prefill.lua`의 주석에 있습니다.
- wrk는 연결 하나로 요청을 이어 보내므로, 측정은 서버가 같은 연결의 두 번째 요청에도 답한다는 것(기능 테스트 "(기능) 연결 하나로 보낸 두 번째 요청도 응답을 받는다")에 기댑니다.

### 열린 루프 시나리오 (티켓 02, 2026-11-14)

python 열린 루프(`scripts/bench/open_loop.py`, 표준 라이브러리만 씀)가 작은 GET을 100연결에 걸쳐 초당 5,000개씩 10초 동안 보냈습니다(연결 하나는 20 ms마다 하나). 요청마다 보낼 시각을 먼저 정하고, 지연은 응답을 다 받은 시각에서 그 예정 시각을 뺀 값입니다. 연결이 앞 요청의 응답을 기다리는 중이면 새 요청은 그 연결에서 줄을 섰다가 나가고, 그 기다림도 지연에 들어갑니다. 방해 요청은 101번째 연결 하나로 정해진 간격마다 보내고, 지연을 같은 방법으로 따로 잽니다. 서버는 실험실 기준선과 같은 코드(03, 04를 합친 서버)입니다.

| 시나리오 | 미리 채운 key | 방해 요청 |
|---|---|---|
| A `a-quiet` | 100,000개 | 없음 |
| B `b-big-store` | 100,000개 | 0.2초마다 16 MiB(16,777,216바이트) value를 새 key에 저장, 50번 |
| C `c-rehash` | 4,194,304개를 넣고 하나를 지워 4,194,303개 | 1초마다 새 key 저장과 그 key 삭제를 번갈아, 각 5번 |
| D `d-big-delete` | 100,000개와 16 MiB value 50개 | 0.2초마다 16 MiB value 하나를 삭제, 50번 |

C에서 key 하나를 먼저 지우는 이유: `hash.c`는 entry가 4,194,304개(2²²)면 버킷 2²¹개, 4,194,303개면 버킷 2²⁰개를 씁니다. 그래서 entry 수가 4,194,303과 4,194,304 사이를 오가야 저장과 삭제가 모두 rehash를 일으킵니다. 4,194,304개에서 새 key를 저장하면 4,194,305개가 되어 버킷 수가 바뀌지 않습니다.

`make bench`를 3회 돌린 값이고, 단위는 ms입니다. 작은 GET은 회마다 50,000개입니다. 방해 요청은 회마다 50개 이하라서 p99 대신 max를 적습니다.

| 시나리오 | 회 | 작은 GET p50 | 작은 GET p99 | 작은 GET max | 방해 요청 p50 | 방해 요청 max |
|---|---|---|---|---|---|---|
| A 방해 없음 | 1 | 0.027 | 0.098 | 3.480 | | |
| | 2 | 0.028 | 0.088 | 1.896 | | |
| | 3 | 0.025 | 0.106 | 1.827 | | |
| B 16 MiB 저장 | 1 | 0.033 | 10.673 | 19.313 | 14.570 | 35.214 |
| | 2 | 0.033 | 10.706 | 18.651 | 14.733 | 35.155 |
| | 3 | 0.032 | 10.994 | 19.686 | 14.901 | 37.615 |
| C rehash 경계 | 1 | 0.038 | 328.479 | 369.883 | 저장 345.681, 삭제 311.652 | 저장 369.085, 삭제 319.388 |
| | 2 | 0.038 | 328.117 | 367.356 | 저장 335.901, 삭제 316.368 | 저장 366.511, 삭제 341.014 |
| | 3 | 0.034 | 311.399 | 342.424 | 저장 328.762, 삭제 301.663 | 저장 341.774, 삭제 312.767 |
| D 16 MiB 삭제 | 1 | 0.030 | 0.106 | 11.873 | 0.038 | 11.771 |
| | 2 | 0.031 | 0.107 | 12.864 | 0.034 | 12.761 |
| | 3 | 0.027 | 0.093 | 11.997 | 0.030 | 11.975 |

client가 예정 시각보다 늦게 보낸 정도(연결이 비어 있던 요청만)는 모든 회에서 p50 0.005~0.007 ms, p99 0.016~0.031 ms, max 1.0~8.2 ms였습니다.

- **A와 wrk 기준선:** python으로 잰 A(p50 약 0.03 ms, p99 약 0.1 ms)는 wrk 기준선(p50 약 0.28 ms, p99 약 0.47 ms)보다 작습니다. wrk는 닫힌 루프라서 100연결이 모두 항상 응답을 기다리고(초당 약 320,000개), 요청 하나는 서버가 나머지 연결을 한 바퀴 도는 시간(100 ÷ 320,000초 ≈ 0.31 ms)을 기다립니다. 열린 루프는 초당 5,000개라서 서버에 요청이 대개 하나뿐입니다. python client가 느려서 생긴 지연이면 A가 wrk보다 커야 하는데 반대이고, client가 늦게 보낸 정도도 p99 0.03 ms 이하이므로 python client는 병목이 아닙니다. 다만 두 숫자는 부하가 달라서 같은 것을 잰 값이 아닙니다. A는 한가한 서버의 응답 시간이고, wrk 기준선은 가득 찬 서버의 응답 시간입니다.
- **B:** 16 MiB 저장 하나마다 서버가 약 12~13 ms 동안 다른 요청에 답하지 않습니다. 작은 GET 50,000개 가운데 1%인 500개가 10.7 ms 넘게 기다렸고, 저장이 50번이므로 저장 하나에 약 10개(2 ms 분량)가 그만큼 기다린 셈입니다. 같은 WSL에서 따로 만든 C 프로그램으로 재면, 새로 `malloc`한 메모리에 16 MiB를 `memcpy`하는 데 10.3~10.9 ms(대부분 새 페이지를 받는 시간), 16 MiB를 한 바이트씩 0으로 쓰는 데 1.8~1.9 ms가 걸립니다. 서버에서는 앞의 것이 `store_set`이 entry에 value를 복사하는 일이고, 뒤의 것이 mongoose가 처리한 요청을 수신 버퍼에서 지우는 일(`mg_iobuf_del`의 `mg_bzero`)입니다. 서버 안에서 직접 잰 값은 아닙니다. 방해 요청의 max(35~38 ms)는 수신 버퍼를 16 MiB까지 늘리는 일이 더해지는 첫 저장으로 보입니다.
- **C:** 경계에서는 저장과 삭제 하나하나가 300~370 ms 걸립니다. 그 동안 서버는 어떤 요청에도 답하지 않으므로, 그 사이에 보낼 차례가 된 작은 GET은 rehash가 끝날 때까지 기다립니다. 그래서 작은 GET의 p99와 max가 rehash 하나의 시간과 같습니다. 방해 요청의 간격이 1초라서 작은 GET의 약 1/3이 기다렸고 p50은 영향을 받지 않았습니다. 간격을 0.5초로 줄여 한 번 재면 p50 82.080 ms, p99 329.436 ms, max 360.454 ms였습니다. p99는 간격이 아니라 rehash 하나의 시간이 정합니다.
- **D:** 16 MiB 삭제는 대부분 0.03~0.05 ms에 끝나고, 작은 GET의 p99도 A와 같습니다. 회마다 삭제 하나만 약 12 ms가 걸렸고, 삭제마다 지연을 출력해 한 번 확인하니 50번째(마지막) 삭제였습니다. 작은 GET의 max도 그때 나옵니다. 원인은 glibc의 `free`가 앞서 해제된 16 MiB 덩어리 50개(800 MiB)를 마지막 해제 때 합쳐 한꺼번에 운영체제에 돌려주는 것으로 추정합니다. 직접 확인하지는 않았습니다.
