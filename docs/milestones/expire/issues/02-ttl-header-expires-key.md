# 02: TTL 헤더로 저장한 key가 만료 뒤 404를 받는다

**Status:** ready-for-agent

**What to build:** client가 `PUT`에 `TTL: <초>`를 붙여 저장하면, 그 key는 보관 기간이 지난 뒤 없는 key와 똑같이 `404 key_not_found`를 받습니다. 보관 기간은 서버가 요청 헤더를 다 받은 순간부터 세고(Q11), 만료 시각과 같은 순간부터 만료입니다(Q12). 조회는 만료된 key를 "없음"으로 답하고 지우지 않으며, 삭제는 만료된 key를 지우고 "없음"으로 답합니다. 덮어쓰면 새 요청이 보관 기간을 정하고, `TTL` 없이 덮어쓰면 기간이 사라집니다(Q7). 이 티켓은 1 이상의 정수인 `TTL`만 다루고, 잘못된 값은 티켓 03이 다룹니다. 시계는 `mg_millis`입니다(ADR `monotonic-clock-for-expiry`). 결정은 `../spec.md`를 따릅니다.

**Blocked by:** 01

테스트 시나리오(팀 확인). 테스트 이름은 아래 문장을 그대로 씁니다.

- [x] [T15] 만료 시각 1 ms 전에는 조회되고, 만료 시각과 같은 순간에는 없다
- [x] 만료된 key를 삭제하면 지운 것이 없다고 답한다
- [x] 만료된 key를 조회해도 store에서 지우지 않는다
- [x] 기간과 함께 저장한 key를 다른 기간으로 덮어쓰면 새 기간이 지나야 만료된다
- [x] 기간과 함께 저장한 key를 기간 없이 덮어쓰면 만료되지 않는다
- [x] 기간이 남은 key를 조회해도 만료 시각이 늦춰지지 않는다
- [x] TTL 60을 받으면 헤더를 받은 시각부터 60초 뒤가 만료 시각이다
- [x] [T16] (기능) TTL 1로 저장한 key는 2초 뒤 404와 key_not_found를 받는다
- [x] (기능) TTL 없이 저장한 key는 2초 뒤에도 조회된다
- [x] (기능) TTL로 저장한 key를 TTL 없이 덮어쓰면 2초 뒤에도 조회된다

그 밖의 완료 조건:

- [x] 서버는 헤더를 다 받은 순간의 시각을 연결마다 기억하고, `TTL` 헤더의 값을 api 층에 넘긴다. api 층은 HTTP 라이브러리를 모르는 채로 남는다
- [x] 기다리는 기능 테스트들을 같은 시간 안에서 함께 돌려, `make verify`가 늘어나는 시간이 약 3초를 넘지 않게 한다
- [x] M1·M2·M3의 기존 테스트가 그대로 통과하고, `make verify`가 통과한다
