# M4 `expire` spec

Status: ready-for-agent

요구사항: L9 (`docs/requirements.md`). 문제는 `overview.md`에 있고, 이 문서는 2단계 grill(2026-11-14)에서 팀이 합의한 답입니다. grill의 질문 번호(Q1~Q22)와 overview의 문제 번호를 함께 적습니다.

## Problem Statement

client는 mini-redis에 값을 저장하면 지울 때까지 영원히 남는다는 것만 압니다. M5 `cache`에서 원본 API의 응답을 담아 두려면 "이 값은 60초 동안만 쓸 수 있다"를 말할 방법이 필요한데, 지금 API에는 그 자리가 없습니다. body는 value의 바이트 그대로이고(ADR `http-methods-and-raw-body`), 경로의 인코딩하지 않은 `?`는 `400 bad_key_encoding`으로 거절하기 때문입니다.

기간을 붙일 수 있게 되면 새 문제가 생깁니다. 기간이 지난 key를 조회하면 무엇을 답할지, 아무도 다시 조회하지 않는 key의 메모리를 언제 돌려받을지, 그 정리 작업이 M3에서 정한 지연 목표(방해 요청이 있어도 작은 GET의 p99 10 ms 이하)를 깨지 않게 하려면 한 번에 얼마나 해야 할지 정해야 합니다. 시스템 시각이 바뀌거나 느린 client가 큰 body를 올리는 동안에도 만료가 예측 가능해야 합니다.

## Solution

client는 `PUT` 요청에 `TTL: <초>` 헤더를 붙여 key마다 **보관 기간**을 정합니다. 헤더가 없으면 그 key는 만료되지 않습니다. 서버는 헤더를 다 받은 순간에 단조 시계로 **만료 시각**을 정하고, 만료 시각과 같은 순간부터 그 key를 없는 key와 똑같이 다룹니다(`404 key_not_found`).

만료된 key는 두 길로 지워집니다. 조회와 삭제 요청은 만료를 검사해 만료된 key를 없는 것으로 답하고, 서버는 요청과 상관없이 **주기 청소**로 만료된 key를 지워 메모리를 돌려받습니다. 주기 청소는 만료 시각 순으로 줄을 세운 min-heap의 맨 앞부터 꺼내므로, 비용이 전체 key 수가 아니라 만료된 key 수를 따라갑니다. 한 번의 청소는 최대 K개만 지우고, 청소 간격 S와 K는 `make bench`에 더하는 세 시나리오로 재서 고릅니다.

## User Stories

1. client 개발자로서, `PUT`에 `TTL: 60` 헤더를 붙여 그 key가 60초 동안만 조회되기를 원합니다. 그래야 원본 API의 응답을 담아 두고 기간이 지나면 다시 받아 올 수 있습니다(L15).
2. client 개발자로서, `TTL` 헤더 없이 `PUT`한 key는 지금처럼 지울 때까지 남기를 원합니다.
3. client 개발자로서, 만료된 key를 `GET`하면 없는 key와 같은 `404`와 `{"error":"key_not_found"}`를 받기를 원합니다. 그래야 "없음"과 "만료됨"을 따로 처리하지 않아도 됩니다.
4. client 개발자로서, 만료된 key를 `DELETE`해도 없는 key와 같은 `404 key_not_found`를 받기를 원합니다.
5. client 개발자로서, 만료 시각과 정확히 같은 순간에 보낸 조회도 `404`를 받기를 원합니다. 그래야 "N초 뒤에는 없다"가 정확히 성립합니다.
6. client 개발자로서, 보관 기간을 초 단위의 1 이상 정수로 보내기를 원합니다.
7. client 개발자로서, `TTL`에 0, 음수, 숫자가 아닌 값, 빈 값, 너무 큰 값을 보내면 `400`과 `{"error":"bad_ttl"}`을 받기를 원합니다. 그래야 실수가 조용히 "만료 없음"이나 "바로 삭제"로 바뀌지 않습니다.
8. client 개발자로서, 한 요청에 `TTL` 헤더를 두 번 보내면 `400 bad_ttl`을 받기를 원합니다. 그래야 어느 값이 쓰였는지 모르는 채 `204`를 받지 않습니다.
9. client 개발자로서, 보관 기간이 남은 key에 `TTL: 5`로 다시 `PUT`하면 새 요청의 5초가 새 보관 기간이 되기를 원합니다.
10. client 개발자로서, 보관 기간이 남은 key에 `TTL` 헤더 없이 다시 `PUT`하면 보관 기간이 사라지기를 원합니다. 그래야 기간을 없애는 방법이 따로 필요 없습니다.
11. client 개발자로서, `GET`이 보관 기간을 바꾸지 않기를 원합니다. 그래야 자주 읽는 캐시 값도 정한 기간이 지나면 만료됩니다.
12. client 개발자로서, `GET`과 `DELETE`에 붙인 `TTL` 헤더는 무시되기를 원합니다.
13. client 개발자로서, 16 MiB body를 느리게 올려도 보관 기간이 헤더를 보낸 순간부터 세어지기를 원합니다. 그래야 업로드 시간만큼 만료가 늦어지지 않습니다.
14. client 개발자로서, 서버의 시스템 시각이 바뀌어도 내 key의 보관 기간이 갑자기 끝나거나 늘어나지 않기를 원합니다.
15. client 개발자로서, 많은 key가 한꺼번에 만료되는 동안에도 내 작은 조회가 곧바로 응답받기를 원합니다.
16. client 개발자로서, `README.md`의 "API" 절에서 `TTL` 헤더의 단위, 받는 값, `bad_ttl`, 덮어쓰기 규칙을 읽을 수 있기를 원합니다.
17. 운영하는 팀원으로서, 아무도 다시 조회하지 않는 만료된 key도 메모리에서 지워지기를 원합니다. 16 MiB value 1,000개를 1분 기간으로 넣고 잊어도 16 GiB가 남지 않아야 합니다.
18. 운영하는 팀원으로서, 같은 key를 기간과 함께 계속 덮어써도 주기 청소의 자료구조가 커지지 않기를 원합니다. M5의 캐시는 같은 key를 기간이 지날 때마다 다시 저장하기 때문입니다.
19. 운영하는 팀원으로서, key 400만 개 가운데 10개만 기간이 있을 때 주기 청소가 400만 개를 훑지 않기를 원합니다.
20. 운영하는 팀원으로서, 주기 청소가 연결 수와 상관없이 루프 한 바퀴에 한 번만 돌기를 원합니다.
21. 운영하는 팀원으로서, 한 번의 청소가 지우는 key 수에 상한 K가 있기를 원합니다. 그래야 10만 개가 한꺼번에 만료돼도 서버가 그동안 멈추지 않습니다.
22. 팀원으로서, 주기 청소도 스레드를 더하지 않고 같은 루프에서 돌기를 원합니다(ADR `single-thread-event-loop`).
23. 팀원으로서, 주기 청소가 handler 밖에서만 돌아서, `store_get`이 빌려준 value를 응답으로 복사하는 동안 청소가 끼어들지 않기를 원합니다(ADR `get-lends-value-until-next-change`).
24. 팀원으로서, 만료 판정과 M3의 쉬는 시간 기한이 같은 시계(`mg_millis`)를 쓰기를 원합니다. 그래야 서버 안의 "지금"이 하나입니다.
25. 팀원으로서, `bad_ttl` 응답을 api 층이 만들기를 원합니다. 그래야 M2의 다른 오류처럼 소켓 없이 단위 테스트로 확인합니다.
26. 측정하는 팀원으로서, 청소 간격 S, 한 번에 지우는 최대 개수 K, 루프의 대기 시간 `POLL_INTERVAL_MS`를 빌드할 때 바꿔 `make bench`로 조합마다 재기를 원합니다.
27. 측정하는 팀원으로서, "한꺼번에 만료", "꾸준한 만료", "큰 value의 만료" 세 시나리오에서 작은 GET의 p99와, 만료된 key가 만료 시각 뒤에 얼마나 남았는지를 함께 재기를 원합니다.
28. 측정하는 팀원으로서, 세 시나리오 모두에서 p99가 10 ms 이하인 조합 가운데 만료된 key가 가장 짧게 남는 조합을 기본값으로 고르기를 원합니다.
29. 테스트 작성자로서, store에 "지금" 시각을 직접 넘겨, `sleep` 없이 만료 경계를 ms 단위로 확인하기를 원합니다.
30. 테스트 작성자로서, 실제 서버에 `TTL: 1`로 저장하고 1~2초 기다려 `404`를 받는지 `make verify`에서 확인하기를 원합니다.
31. 발표하는 팀원으로서, 만료 시각 순 min-heap이 왜 전체 훑기보다 나은지와, 덮어쓰거나 지운 key를 heap에서 바로 빼는 이유를 숫자와 함께 설명하기를 원합니다.

## Implementation Decisions

- **모듈:** store가 만료 시각과 min-heap을 갖고, 만료 판정과 주기 청소를 맡습니다. api 층은 `TTL` 헤더의 값을 검사해 보관 기간을 만료 시각으로 바꾸고, 잘못된 값이면 `400 bad_ttl`을 만듭니다. 서버는 헤더를 다 받은 순간의 시각을 연결마다 기억하고, `TTL` 헤더의 값과 개수를 api 층에 넘기며, 루프에서 주기 청소를 부릅니다. `hash.c`는 고치지 않습니다.
- **Q2 누가 정하나 (문제 1):** client가 key마다 정합니다. 정하지 않은 key는 만료되지 않고, 서버가 모든 key에 정하는 기본 기간은 없습니다.
- **Q6, Q13 보내는 자리 (문제 1):** `PUT` 요청의 `TTL` 헤더로 받습니다(ADR `ttl-in-request-header`). 버린 대안: query string(M2의 `?` 거절 규칙을 바꿔야 하고, 인코딩하지 않은 `?`가 든 key가 조용히 다른 key에 저장되는 문제가 좁은 범위에서 다시 생김), body JSON(ADR `http-methods-and-raw-body`를 뒤집음), 별도 경로(`/keys/a/ttl`이 key `a/ttl`이 됨). 헤더 이름으로 `Expires`와 `Cache-Control: max-age`는 HTTP 캐시의 뜻이 이미 정해져 있어 쓰지 않고, RFC 6648을 따라 `X-` 접두사도 붙이지 않습니다.
- **Q10, Q11 입력 형식 (문제 2):** 보관 기간은 "지금부터 N초"인 상대 시각입니다. 서버는 요청 헤더를 다 받은 순간(mongoose의 헤더 이벤트)의 시각에 N초를 더해 만료 시각을 정합니다. 그래서 오차는 편도 전송 지연뿐이고, 항상 조금 늦게 만료됩니다. 버린 대안: 절대 시각(오차가 client 시계와 서버 시계의 차이라 방향이 정해지지 않고, 받는 순간에 벽시계가 필요함), body를 다 받은 순간부터 세기(16 MiB를 초당 1 MB로 올리면 약 16초 늦게 만료됨).
- **Q12, Q14 단위와 잘못된 값 (문제 2):** 단위는 초입니다. 1 이상의 정수만 받고, 0, 음수, 숫자가 아닌 값, 빈 값, ms로 바꿔 지금 시각에 더했을 때 넘치는 값은 `400`과 오류 이유 `bad_ttl`로 거절합니다. 0을 "바로 지우기"로 받지 않는 이유는 client의 실수가 조용히 데이터 삭제로 이어지기 때문입니다.
- **Q15 중복 헤더:** 한 요청에 `TTL` 헤더가 두 개 이상이면 `400 bad_ttl`입니다. mongoose의 헤더 조회는 첫 번째 값만 돌려주므로, 서버는 개수를 세어 넘깁니다.
- **TTL 값의 공백과 `+` 부호 (5단계에서 결정, 2026-11-14):** 값 앞뒤의 공백과 탭은 받습니다. HTTP 헤더 문법에서 값 앞뒤의 공백은 값에 속하지 않고, mongoose가 헤더를 해석할 때 지운 뒤 넘기기 때문입니다(`vendor/mongoose/mongoose.c`의 `mg_http_parse_headers`). `+` 부호와 숫자 사이의 공백은 `400 bad_ttl`입니다. api 층은 10진수 숫자만 받습니다. 부호를 받으면 `-`는 거절하고 `+`만 받는 예외가 하나 생기기 때문입니다. 테스트 이름: "TTL에 + 부호가 붙으면 400과 bad_ttl을 받는다", "TTL 숫자 사이에 공백이 있으면 400과 bad_ttl을 받는다", "(기능) TTL 값 앞뒤의 공백은 서버가 지우고 받는다".
- **`GET`과 `DELETE`의 `TTL` 헤더 (Q6에서 따라 나옴):** 무시합니다. 요청과 상관없는 헤더를 무시하는 HTTP의 관례를 따릅니다.
- **Q3 만료된 key의 응답 (문제 3):** 없는 key와 똑같이 `404`와 `{"error":"key_not_found"}`입니다. 구분하려면 지운 뒤에도 "만료로 지웠다"를 기억해야 하고, 기억하지 않으면 청소가 언제 돌았는지에 따라 같은 요청의 답이 달라집니다.
- **경계 (Q12):** 만료 시각과 같은 순간부터 만료입니다. "지금 ≥ 만료 시각"이면 만료된 key입니다.
- **Q7 덮어쓰기와 조회 (문제 5):** `PUT`은 entry를 통째로 바꾸므로(`GLOSSARY.md`의 **entry**), 보관 기간도 새 요청이 정합니다. `TTL` 없이 다시 `PUT`하면 보관 기간이 사라지고, 이것이 기간을 없애는 방법입니다. `GET`은 보관 기간을 바꾸지 않습니다.
- **Q8 기간만 다루는 API (문제 5):** 만들지 않습니다. value를 다시 보내지 않고 기간만 바꾸기, 남은 기간 묻기, 기간 없애기는 L9와 M5 어디에도 요구가 없습니다.
- **Q5 시계 (문제 7):** 만료 판정과 만료 시각 계산은 mongoose와 같은 단조 시계(`mg_millis`)로 합니다(ADR `monotonic-clock-for-expiry`). 저장과 복제가 없는 지금은 벽시계의 장점(재시작 뒤에도 같은 순간을 가리킴)을 쓸 곳이 없고, 벽시계가 한 번에 옮겨지면(WSL2의 시각 맞춤, NTP, `date -s`) key가 한꺼번에 만료되거나 오래 살아남습니다. M6 `persist`를 하게 되면 저장하고 불러올 때 `벽시계 지금 + (만료 시각 − 단조 시계 지금)`으로 바꿔 적습니다. 버린 대안: 벽시계, 절전 시간까지 세는 시계(서버는 보통 절전하지 않음).
- **Q4 지우는 시점 (문제 4):** 조회할 때의 검사와 주기 청소를 둘 다 둡니다. 검사만 있으면 다시 조회되지 않는 key가 영원히 남고, 우리 store에는 메모리가 찼을 때 key를 내보내는 장치도 없습니다. 주기 청소만 있으면 청소 사이에 만료된 값을 돌려줍니다.
- **Q9 주기 청소가 찾는 방법 (문제 4):** 기간이 있는 key만 만료 시각 순 min-heap에 넣고, 맨 앞부터 꺼냅니다(ADR `expiry-heap-with-immediate-removal`). 넣을 때 O(log M), 맨 앞 확인은 O(1), 만료된 key K개를 꺼내는 데 O(K log M)입니다(M은 기간이 있는 key 수). 맨 앞이 만료 전이면 나머지도 만료 전이므로 청소는 그 자리에서 멈춥니다. 버린 대안: 모든 entry를 커서로 훑기(기간이 있는 key가 적어도 전체를 훑고, rehash가 버킷 배치를 한 번에 바꾸면 커서가 key를 건너뛰거나 두 번 봄), 무작위 일부 검사(운이 나쁘면 만료된 key가 오래 남음).
- **Q16 지우거나 덮어쓴 key (문제 4):** heap에서 바로 뺍니다. entry가 만료 시각과 heap 안의 자기 위치를 갖고, heap이 항목의 자리를 바꿀 때마다 그 위치를 고칩니다. 이유: "시간 vs. 공간에서 공간 복잡도를 조금 더 우선시했다"(2단계, 팀원). 덮어쓰기와 삭제마다 O(log M)이 더 들지만, heap의 크기는 언제나 기간이 있는 key 수와 같습니다. 버린 대안: 두었다가 청소가 꺼낼 때 버리기(같은 key를 `TTL: 3600`으로 초당 1,000번 덮어쓰면 1시간 동안 heap에 항목 360만 개가 쌓이고, 그 항목들이 청소의 K를 차지함).
- **덮어쓰기와 heap (Q16에서 따라 나옴):** `store_set`은 `hash_replace`로 entry를 새로 만들어 바꾸므로, 옛 entry의 heap 항목을 빼고, 새 요청에 기간이 있으면 새 entry를 heap에 넣습니다.
- **조회할 때의 검사 (Q4, to-spec 확인에서 결정, 2026-11-14):** 조회는 만료된 key를 "없음"으로 답하고 entry를 지우지 않습니다. 지우는 일은 삭제 요청과 주기 청소가 맡습니다. 이유: `CONVENTION.md`의 동사 표에서 `get`은 "바꾸지 않습니다". 만료된 key는 heap의 맨 앞쪽에 있으므로 다음 청소들이 곧 지웁니다. `DELETE`가 만료된 key를 만나면 entry를 지우고 "없음"으로 답합니다(`404`).
- **store와 시각:** store는 시계를 직접 읽지 않고, 저장, 조회, 삭제, 청소를 부르는 쪽이 "지금"(ms)을 인자로 넘깁니다. 저장은 만료 시각을 받고, "만료 없음"을 나타내는 값을 따로 둡니다. 이유: 테스트가 `sleep` 없이 경계를 ms 단위로 확인합니다. 고침(5단계에서 결정, 2026-11-14): 저장은 "지금"을 받지 않습니다. `store_set`은 만료 시각(`expires_at`)만 받고, "지금"을 받는 것은 `store_get`, `store_delete`, `store_delete_expired`입니다. 보관 기간을 만료 시각으로 바꾸는 일은 api 층이 헤더를 받은 시각으로 하므로, store가 저장할 때 "지금"을 쓸 곳이 없습니다.
- **api 층이 받는 TTL 헤더 (5단계에서 결정, 2026-11-14):** `api_handle`은 `struct api_ttl_header` 하나로 첫 번째 `TTL` 헤더 값의 바이트(`text`, `text_len`), 헤더 개수(`count`), 헤더를 다 받은 시각(`received_at`)을 받습니다. 서버는 값을 해석하지 않고 넘기므로, 티켓 03이 이 인터페이스를 바꾸지 않고 `bad_ttl` 검사를 더합니다. 서버는 이 시각을 연결의 data 칸에 M3의 마지막 활동 시각과 나란히 두고, 요청마다 첫 `MG_EV_HTTP_HDRS`에서만 적습니다. 값 이름에 `value`를 쓰지 않는 것은 `CONVENTION.md`의 이름 표에서 `value`가 저장하는 값이기 때문입니다.
- **Q17 주기 청소를 부르는 자리:** `main`의 루프에서 `mg_mgr_poll`이 돌아온 직후, 마지막 청소 기한에서 S ms가 지났으면 부릅니다. 다음 기한은 "기한 + S"로 잡아 간격의 격자를 지킵니다. 버린 대안: 연결마다 오는 `MG_EV_POLL`(연결 수만큼 불려 한 바퀴에 최대 연결 수 × K개를 지움), 요청을 처리할 때(요청이 끊기면 청소도 멈춤), mongoose 타이머(동작은 같지만 청소 시점이 루프에 보이지 않음), 별도 스레드(ADR `single-thread-event-loop`). **다시 볼 것:** 실제 청소 간격은 루프가 깨어나는 시점에 묶이므로, 측정에서 S가 100 ms보다 작은 조합은 `POLL_INTERVAL_MS`도 함께 바꿔 잽니다. 이 자리를 유지할지는 M4 측정에서, 캐시와 함께 쓸 때의 영향은 M5의 성능 비교(L17)에서 다시 판단합니다.
- **Q18 한 번의 청소량:** 한 번에 최대 K개를 지우고, 나머지는 다음 청소가 지웁니다. 청소 한 번은 `DELETE` K개를 연달아 처리한 것과 같아서, M3에서 재는 방해 요청과 같은 기준으로 다룹니다. 버린 대안: 시간 예산(`mg_millis`의 단위가 ms라 1 ms 안팎의 예산을 재기 어렵고, 테스트에 시계를 바꿔 끼워야 함), 상한 없음(10만 개를 지우는 동안 모든 요청이 기다림).
- **Q19 S와 K를 바꾸는 자리:** 빌드할 때 정하는 상수입니다. 평소에는 기본값으로 빌드하고, `make bench`가 조합마다 서버를 다시 빌드해 잽니다. 서버 실행 인자는 만들지 않습니다(M3 spec의 Out of Scope "실행 중에 바꾸는 설정"과 같은 생각).
- **Q20 측정 시나리오:** `make bench`에 세 시나리오를 더합니다. 모두 M3처럼 작은 GET을 정해진 시각마다 보내면서 잽니다.

  | 시나리오 | 내용 | 보려는 것 |
  |---|---|---|
  | 한꺼번에 만료 | key 10만 개가 같은 만료 시각 | K가 막아야 하는 최악의 경우 |
  | 꾸준한 만료 | 초당 1,000개씩 만료 | S가 회수를 따라잡는지(M5의 평소 모습) |
  | 큰 value의 만료 | 16 MiB value 여러 개가 같은 순간에 만료 | 지우는 개수가 적어도 비용이 큰 경우 |

  각 시나리오에서 작은 GET의 p99와, 만료된 key가 만료 시각 뒤에 얼마나 남았는지를 함께 잽니다.
- **Q21 값을 고르는 규칙:** 세 시나리오 모두에서 작은 GET의 p99가 10 ms 이하인 조합 가운데, 만료된 key가 가장 짧게 남는 조합을 기본값으로 고릅니다. 회수 지연에는 따로 목표 숫자를 두지 않습니다. K가 1이어도 목표를 넘는 경우는 S와 K로 풀 수 없는 문제이므로, M3 Q14처럼 드라이버가 판단해 줄이거나 한계로 적고, 그 원리를 PR에 씁니다. 고른 값과 숫자는 이 문서의 "측정 결과"에 적습니다. 측정 전에는 드라이버가 정한 임시 기본값을 씁니다.
- **청소가 일으키는 rehash:** PR #18 뒤에도 entry 수가 버킷 수 아래로 내려가면 버킷을 줄이는 rehash가 한 번 일어나고, K로는 그 rehash를 자를 수 없습니다. "한꺼번에 만료"에서 이 멈춤이 목표를 넘으면 M3의 E 시나리오처럼 한계로 적습니다.
- **빌린 value:** 서버는 handler 안에서 value를 송신 버퍼로 복사하고, 주기 청소는 handler가 모두 끝난 뒤에만 돕니다. 그래서 ADR `get-lends-value-until-next-change`는 M4에서도 그대로 유효합니다.
- **응답 표에 더하는 줄:**

  | 상황 | 상태 코드 | body |
  |---|---|---|
  | `PUT`의 `TTL`이 1 이상의 정수가 아니거나, 너무 크거나, 두 번 옴 | `400` | `bad_ttl` |

  만료된 key의 조회와 삭제는 이미 있는 `404 key_not_found` 줄을 따릅니다.
- **용어:** **보관 기간**, **만료**, **만료 시각**, **주기 청소**를 `GLOSSARY.md`에 더했습니다(2단계).

## Testing Decisions

- **좋은 테스트:** 공개 함수나 HTTP 요청처럼 바깥에서 보이는 동작만 확인합니다. 기대하는 상태 코드, body, 조회 결과는 검사 대상 코드로 계산하지 않고 직접 적습니다. heap의 배열이나 entry 안의 heap 위치 같은 내부는 확인하지 않습니다.
- **seam 세 개 (to-spec에서 팀 확인, 2026-11-14):** 새 seam은 만들지 않고 M1~M3의 seam을 그대로 씁니다.
  - store의 공개 함수: "지금"을 직접 넘겨, 만료 경계(만료 시각 1 ms 전에는 조회됨, 같은 순간에는 없음), 덮어쓰기와 삭제 뒤의 기간, 주기 청소가 지운 개수와 K 상한, 기간이 없는 key는 청소가 건드리지 않음을 확인합니다. 선례는 M1의 store 테스트입니다.
  - api 층의 공개 함수: 소켓 없이 `TTL` 값 검사(0, 음수, 숫자 아님, 빈 값, 너무 큼, 두 번)와 `400 bad_ttl`의 상태 코드, `Content-Type`, body를 확인합니다. 선례는 M2의 `411`, `413`과 M3의 `408`, `503` 테스트입니다.
  - 실제 서버: `TTL: 1`로 저장하고 실제로 기다려 `404`를 받는지, 헤더 없는 `PUT`이 기간을 지우는지, `GET`이 기간을 늘리지 않는지 확인합니다. 선례는 M3의 기능 테스트이고, 같은 방식으로 기다리는 테스트들을 함께 돌려 `make verify`가 늘어나는 시간을 줄입니다.
- **시계 (overview 문제 6):** 단위 테스트는 store와 api 층에 "지금"을 직접 넘기므로 시계를 바꿔 끼울 일이 없습니다. 기능 테스트는 서버의 실제 시계로 1~2초 기다립니다. 테스트에 맞춰 서버 코드를 바꾸지 않는다는 M3의 결정을 따릅니다.
- **파일과 도구:** 단위 테스트는 `tests/expire_test.c` 하나에 acutest의 한국어 문장 이름으로 적습니다. 기능 테스트는 `tests/functional/`에 python3 표준 라이브러리로 둡니다. `make verify`가 모두 실행합니다.
- **격리:** 단위 테스트는 테스트마다 새 store를 만들고 없앱니다. 기능 테스트는 테스트마다 서로 다른 key를 씁니다.
- **시나리오 후보 (4단계에서 팀이 확인):** User Stories 1~14, 17~21, 29~30의 각 줄.
- **테스트하지 않는 것:** p99 목표와 회수 지연은 측정으로 확인하고 자동 테스트로 판정하지 않습니다. 시스템 시각을 바꾸는 테스트와 절전 테스트는 하지 않습니다.
- **ID:** ADR의 `결정:` 줄이나 `docs/requirements.md`의 `근거` 칸이 인용하는 테스트에만 ID를 붙이고, `T14` 다음 번호부터 씁니다. 어느 테스트를 인용할지는 4단계에서 정합니다.

## Out of Scope

- 기간만 바꾸기, 남은 기간 묻기, 기간 없애기 API(Q8). 기간은 `PUT`을 다시 보내 바꾸거나 없앱니다.
- 절대 시각 입력("이 시각에 만료"), ms 단위 입력(Q10, Q12).
- query string과 body로 기간 받기(Q6).
- 서버가 모든 key에 정하는 기본 보관 기간(Q2).
- 메모리가 가득 찰 때 key를 내보내는 정책(eviction): LMS에 없습니다.
- 큰 value를 다른 스레드에서 해제하기: ADR `single-thread-event-loop`.
- 청소 간격과 상한을 실행 중에 바꾸는 설정(Q19).
- 재시작 뒤에도 만료 시각을 지키기: M6 `persist`에서 다룹니다.

- 이유 문장: ADR `monotonic-clock-for-expiry`(Q5)와 `ttl-in-request-header`(Q6)의 이유 칸은 팀원의 문장을 기다립니다. ADR `expiry-heap-with-immediate-removal`은 Q16의 문장을 받았고, Q9(heap을 고른 이유)의 문장을 기다립니다.

## Redis와 대조

2단계 끝(2026-11-14)에 공개한 Redis의 방식입니다. 6단계에서 팀이 배운 것을 이 절에 더합니다.

| 주제 | 우리 생각 | Redis의 방식 | 우리가 고른 것 |
|---|---|---|---|
| 누가 정하나 | client가 key마다 정합니다. | 같습니다. 명령마다 정하고, 서버 기본값은 없습니다. | 같습니다. |
| 보내는 자리 | `PUT` 헤더 `TTL` | 명령 인자(`SET k v EX 60`). 이미 있는 key에는 `EXPIRE`를 씁니다. | 값과 기간을 요청 하나로 보낸다는 생각은 같고, 자리만 HTTP에 맞췄습니다. |
| 입력 형식 | 상대 시각, 초 | 상대(`EX` 초, `PX` ms)와 절대(`EXAT`, `PXAT`)를 모두 받고, 저장은 절대 시각(ms)입니다. | 상대 시각만 받습니다. |
| 잘못된 값 | 1 이상의 정수만, 그 밖은 `400 bad_ttl` | `SET`에 0 이하를 주면 오류입니다. `EXPIRE`에 0 이하를 주면 key를 바로 지웁니다. `SET k v EX 10 EX 20`은 문법 오류입니다. | `SET`과 같습니다. |
| 시계 | 단조 시계 | 벽시계(Unix ms). 명령 하나가 도는 동안은 시각을 한 번만 읽습니다. 디스크 저장(RDB, AOF)과 복제에 절대 시각을 보내기 때문입니다. | 다릅니다. 우리에게는 저장과 복제가 없습니다. |
| 만료된 key 조회 | `404 key_not_found` | 없는 key와 같은 nil | 같습니다. |
| 덮어쓰기, 조회 | 덮어쓰면 기간이 사라지고, `GET`은 바꾸지 않습니다. | `SET`은 기간을 지웁니다(`KEEPTTL`로 유지). `GET`은 바꾸지 않습니다. | 같습니다. |
| 기간만 다루는 API | 만들지 않습니다. | `TTL`, `PTTL`, `PERSIST`, `EXPIRE`가 있습니다. | 다릅니다. |
| 지우는 시점 | 조회할 때 검사 + 주기 청소 | 같습니다. | 같습니다. |
| 청소가 찾는 방법 | 만료 시각 순 min-heap | 기간이 있는 key만 모은 별도 테이블을 커서로 조금씩 훑습니다(한 번에 약 20개, 만료 비율이 10%를 넘으면 한 번 더). 6.0 전에는 무작위 샘플링이었습니다. rehash 중에도 key를 놓치지 않는 커서를 씁니다. | 다릅니다. 우리는 rehash와 커서의 문제를 heap으로 피했고, key마다 heap 위치를 둡니다. |
| 청소 예산 | 간격 S와 개수 K, 빌드 상수, 측정으로 정함 | 시간 예산(느린 주기는 CPU 25%, 빠른 주기는 1 ms)이고, 설정으로 강도를 조절합니다. 큰 value는 옵션으로 백그라운드 스레드가 해제합니다. | 다릅니다. |

## 측정 결과

### 환경

- 머신: Intel Core Ultra 7 155H(논리 코어 22개), Windows의 WSL2 Ubuntu 26.04.1(커널 6.18.58.1-microsoft-standard-WSL2, 메모리 15 GiB). M3의 측정과 다른 머신이라 M3의 숫자와 나란히 보지 않습니다. 서버, wrk, python client가 같은 WSL 안에서 `127.0.0.1`로 주고받습니다.
- 도구: gcc 15.2.0, wrk 4.1.0(Ubuntu 패키지 `4.1.0-4build3`), Python 3.14.4.
- 빌드: M3와 같은 `make bench`의 측정 서버(`-O2`, sanitizer 끔, `assert` 남김)에 `-DSWEEP_TRACE`를 더했습니다. 조합마다 `SERVER_FLAGS`로 다시 빌드했습니다.
- 명령: 조합 하나는 아래처럼 잽니다. 시나리오마다 서버를 새로 띄웁니다. `make bench`는 M3의 시나리오와 함께 세 시나리오를 기본값으로 돌립니다.

  ```console
  $ make -B build/bench/mini-redis SERVER_FLAGS='-DSWEEP_INTERVAL_MS=25 -DSWEEP_MAX_COUNT=2000 -DPOLL_INTERVAL_MS=25'
  $ python3 -B scripts/bench/bench.py build/bench/mini-redis f-expire-burst g-expire-steady h-expire-large
  ```

### 시나리오

세 시나리오 모두 key 100,000개(value 100바이트)를 미리 채우고, M3처럼 python 열린 루프가 그 key에 작은 GET을 100연결로 초당 5,000개씩 10초 동안 보냅니다. 지연은 응답을 다 받은 시각에서 예정 시각을 뺀 값입니다.

| 시나리오 | 만료되는 key | 만료되는 때 |
|---|---|---|
| `f-expire-burst` 한꺼번에 만료 | 100바이트 value key 100,000개, `TTL: 4`, wrk로 저장 | 측정 시작 뒤 약 2초부터 약 1~1.4초 동안 |
| `g-expire-steady` 꾸준한 만료 | 측정 동안 101번째 연결로 1 ms마다 key 하나, `TTL: 2` | 측정 2초부터 끝난 뒤 2초까지 초당 1,000개 |
| `h-expire-large` 큰 value의 만료 | 16 MiB value 50개(합쳐서 800 MiB), `TTL: 4`, 이어서 저장 | 측정 시작 뒤 약 1~2초부터 약 2.5초 동안 |

- **"같은 만료 시각"의 뜻:** 보관 기간은 초 단위이고 만료 시각은 서버가 헤더를 받은 순간에서 세므로(Q11), key 10만 개의 만료 시각은 서버가 그 10만 개를 받는 시간(이 머신에서 약 1~1.4초, 초당 7~12만 개)만큼 퍼집니다. 서버가 하나의 스레드로 저장도 받으므로, 만료되는 속도는 저장을 받은 속도를 넘지 못합니다. 그래서 청소 한 번이 마주하는 만료된 key는 최대 K개와 "저장 속도 × S" 가운데 작은 쪽입니다. 16 MiB value도 같은 이유로 저장 하나가 약 50 ms라 50개의 만료 시각이 약 2.5초에 걸쳐 퍼지고, 청소 한 번은 1~4개를 지웠습니다.
- **청소가 일으키는 rehash:** "한꺼번에 만료"에서 entry는 200,001개에서 100,001개로 줄고 버킷은 65,536개라서, entry 수가 버킷 수 아래로 내려가지 않아 버킷을 줄이는 rehash가 일어나지 않습니다. 일어나는 경우에도 rehash는 남은 entry를 옮기므로 M3 E와 같은 규모(entry 약 13만 개 이상이 남을 때 한 번 10 ms를 넘음)이고, 그 한계는 M3 E에 이미 적혀 있습니다.

### 회수 지연을 재는 방법

측정 빌드에서만 켜는 `SWEEP_TRACE`가 청소가 key를 지울 때마다 끝난 시각(`mg_millis`, `CLOCK_MONOTONIC_RAW`의 ms)과 지운 개수를 stderr에 한 줄 적고, `bench.py`가 같은 시계로 잰 저장 시각과 견줍니다. 만료된 key는 조회해도 없는 key와 같은 `404`라서 바깥의 요청으로는 남아 있는지 알 수 없고, 프로세스의 RSS는 100바이트 value에서 움직이지 않으며 glibc가 해제한 메모리를 바로 돌려주지 않기 때문입니다(M3 D). 기본 빌드에는 그 줄이 없고 store와 api 층은 바뀌지 않으므로, 테스트의 seam(Testing Decisions)은 그대로입니다.

- 묶음(f, h): 묶음 뒤에 같은 TTL로 key `expire-last`를 하나 더 저장합니다. 만료 시각이 가장 늦어 청소가 마지막에 지우므로, 청소가 지운 개수가 묶음 + 1이 된 시각에서 그 만료 시각을 뺀 값을 회수 지연으로 적습니다. 청소가 저장보다 느리면 이 key가 가장 오래 남은 key입니다.
- 꾸준한 만료(g): heap은 만료 시각 순으로 꺼내므로 i번째로 지운 key를 i번째로 만료된 key로 보고, key마다 회수 지연을 잽니다. p50과 max를 적습니다.
- 한계: 시각의 단위가 ms입니다. 만료 시각은 client가 보내기 시작한 시각으로 정하므로 회수 지연을 편도 전송 지연만큼 길게 잽니다. 열린 루프가 끝나고 30초 안에 다 지우지 못하면 거기서 멈추고 "넘게"로 적습니다.

### 고른 값과 근거

- **S 25 ms, K 2,000, `POLL_INTERVAL_MS` 25 ms.** Q21의 규칙대로, 잰 조합 가운데 세 시나리오 모두에서 작은 GET의 p99가 10 ms 이하(3회 모두 6.547 이하)이고 회수 지연이 가장 짧은 조합입니다. 한꺼번에 만료 10만 개를 마지막 key 기준 3~52 ms, 꾸준한 만료를 key마다 max 35~47 ms, 큰 value 50개를 12~31 ms 안에 지웠습니다.
- **임시 기본값 S 100, K 20은 버렸습니다.** 초당 200개만 지워, 꾸준한 만료(초당 1,000개)에서 만료된 key가 쌓이고 한꺼번에 만료 10만 개에 약 500초가 걸립니다. p99는 목표 안이었습니다.
- **K 2,000의 비용:** 청소 한 번이 2,000개를 지워도 작은 GET의 p99는 0.6 ms 안팎이었습니다. 잰 조합 가운데 청소가 원인으로 보이는 목표 초과는 없었으므로, K가 1이어도 목표를 넘는 경우나 청소의 rehash가 목표를 넘는 경우는 생기지 않았고 한계로 적을 것이 없습니다.
- **Q17의 "다시 볼 것":** 요청이 있는 동안은 루프가 자주 깨어나 청소 간격이 S를 따르고, 요청이 없을 때는 `POLL_INTERVAL_MS`가 간격의 하한입니다. 그래서 `POLL_INTERVAL_MS`를 S와 같은 25 ms로 두고, 청소를 부르는 자리(`mg_mgr_poll` 직후)는 유지합니다. 그 대가로 한가한 서버도 초당 40번 깨어납니다.
- **재지 않은 것:** S가 25 ms보다 짧은 조합과 K가 2,000과 20,000 사이인 조합은 재지 않았습니다. 고른 조합은 잰 범위의 끝(가장 짧은 S)이라, 더 짧은 S가 회수 지연을 더 줄일 수도 있습니다. 캐시와 함께 쓸 때의 영향은 M5의 성능 비교(L17)에서 다시 봅니다.
