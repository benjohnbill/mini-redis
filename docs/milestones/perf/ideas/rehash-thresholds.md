# 버킷당 entry 수의 허용 범위를 바꿀 때의 time & memory 차이 비교

## 관찰 대상

[CJG] `rehash`의 발동 조건 수정에 따른 시간 효율 vs. 메모리 비용을 검증합니다.

## 측정 방법

`make rehash-micro`(`scripts/bench/rehash_micro.c`)로, 서버 없이 store 함수를 직접 불러서 재요. 설정마다 `src/hash.c`를 따로 빌드하고, 설정마다 3회 반복해요.

| 검사 | 하는 일 | 재는 것 |
|---|---|---|
| 저장 | `store_set`으로 `prefill-0`\~`prefill-4194303`(value 100바이트)을 차례로 넣어요 | 저장 하나의 평균 시간, 저장 하나의 최대 시간(가장 긴 rehash 멈춤) |
| 조회 | 같은 key를 무작위 순서로 `store_get`해요 | 조회 하나의 평균 시간 |
| 메모리 | 다 넣은 뒤의 버킷 수를 읽어요 | 버킷 배열 메모리(버킷 수 × `sizeof(struct list)` 32바이트) |

### key 수에 따른 시간과 메모리 효율

첫 측정에서 (2, 1)이 빨랐던 이유는 entry가 캐시에 없어서 비교 한 번이 비쌌기 때문으로 보여요. 그래서 이득의 크기는 key 수에 따라 달라질 수 있어요. (4, 2)와 (2, 1)만 두고 key 수를 바꿔서 시간과 메모리를 각자의 비율로 비교해요.

| 항목 | 내용 |
|---|---|
| 바꾸는 요인 | key 수: 100,000개, 1,048,576개, 4,194,304개. value 크기(100바이트)와 key 모양(`prefill-N`)은 고정해요 |
| 시간 이득 % | (4, 2) 대비 (2, 1)의 조회 하나 평균 시간이 줄어든 비율이에요 |
| 메모리 비용 % | (4, 2) 대비 (2, 1)에서 key 하나당 메모리가 늘어난 비율이에요. key 하나당 메모리는 다 넣은 뒤 프로세스 RSS가 늘어난 양 ÷ key 수로 재요 |
| 효율 | 시간 이득 % ÷ 메모리 비용 %예요. 1보다 크면 메모리를 낸 비율보다 시간을 더 큰 비율로 샀다는 뜻이에요 |
| 결론 규칙 | 효율이 1보다 큰 key 수에서는 (2, 1)을, 1보다 작은 key 수에서는 (4, 2)를 택해요 |
| 반복 | key 수마다 3회, 회마다 두 설정을 번갈아 실행해요 |

### 버킷당 entry 수의 최적값

(2, 1)보다 범위를 더 좁히면 비교는 더 줄지만 버킷 배열은 두 배씩 커져요. 한 단계 좁힐 때마다 얻는 시간과 내는 메모리를 바로 앞 단계와 견줘서, 어디까지 좁히는 것이 이득인지 찾아요.

| 항목 | 내용 |
|---|---|
| 설정 | (위쪽 경계, 목표, 아래쪽 경계) = (8, 4, 2), (4, 2, 1), (2, 1, 0.5), (1, 0.5, 0.25), (0.5, 0.25, 0.125). 지금 설정 (4, 2, 1)의 비율을 그대로 두고 세 값을 함께 절반씩 줄여요. 버킷당 entry는 각각 4\~8, 2\~4, 1\~2, 0.5\~1, 0.25\~0.5개 사이를 오가요. 0.5 같은 값은 `-D`로 실수를 주면 `rehash`의 곱셈과 나눗셈이 실수로 계산된 뒤 버킷 수로 잘려요 |
| key 수 | 100,000개, 1,048,576개, 4,194,304개 |
| 단계 효율 | 한 단계 좁힐 때 바로 앞 설정 대비 조회 시간 이득 % ÷ key 하나당 RSS 비용 %예요 |
| 결론 규칙 | key 수마다 단계 효율이 1보다 큰 마지막 단계가 최적이에요. 측정 뒤에 설정마다 숫자 하나로 비교하도록 "시간 × 메모리"가 가장 작은 설정을 최적으로 바꿨어요. 두 규칙은 거의 같은 답을 냈어요 |
| 반복 | key 수마다 3회, 회마다 다섯 설정을 번갈아 실행하고, 3회의 중앙값으로 계산해요 |

아래쪽 경계를 함께 줄이는 이유는, 아래쪽 경계가 위쪽 경계보다 크면 범위가 비기 때문이에요. 범위가 비면 `rehash`는 저장마다 이상적인 버킷 수를 다시 계산하는 M3 이전의 동작으로 돌아가요. 첫 시도는 아래쪽 경계를 1로 둔 채 재서 (0.5, 0.25)의 버킷이 계산의 두 배가 됐고, 그 결과는 버렸어요.

## 결과

**결론:** 범위를 (2, 1, 0.5)로 줄였어요. 서버 없이 잰 조회는 key가 100만 개 이상일 때 약 25% 빨라지고, key 하나당 메모리는 약 4% 늘었어요([`rehash-micro/001`](../../../measurements/rehash-micro/001-CJG-rehash-thresholds.md)). 서버 전체에서는 조회 이득이 회마다의 흔들림에 묻혀 보이지 않았어요([`server/006`](../../../measurements/server/006-CJG-rehash-thresholds-before.md), [`server/007`](../../../measurements/server/007-CJG-rehash-thresholds-after.md), [`server/008`](../../../measurements/server/008-CJG-rehash-thresholds-2-1-0.5.md)).

### 탐색 과정

아래 두 단계는 실험 브랜치 `CJG-hash-bench`에서 쟀고, 측정 기록으로 남기지 않았어요. 예상을 적기 전에 잰 결과예요.

1. **(4, 2), (8, 2), (2, 1), key 400만 개:** 범위를 좁힌 (2, 1)은 조회가 약 24% 빨랐고, rehash를 드물게 한 (8, 2)는 저장과 조회 모두 지금보다 느렸어요. (8, 2)는 rehash가 18번에서 9번으로 줄었지만, 버킷당 entry가 최대 8개까지 쌓여서 늘어난 비교 시간이 줄어든 rehash 시간보다 컸어요.
2. **(4, 2)와 (2, 1), key 10만, 100만, 400만 개:** key 10만 개에서는 두 설정의 조회 시간 범위가 겹쳤고, 100만 개 이상에서는 (2, 1)이 21\~28% 빨랐어요. entry가 CPU 캐시에 들어가면 비교 한 번이 싸서 비교를 줄인 효과가 작기 때문으로 봐요.
3. **다섯 설정:** 처음에는 아래쪽 경계를 1로 둔 채 재서, 아래쪽 경계가 위쪽 경계보다 큰 설정의 범위가 비었어요. 그 결과는 버리고 세 값의 비율을 유지해 다시 잰 것이 `rehash-micro/001`이에요.

### 판단 기준

설정마다 `조회 시간 비율 × 메모리 비율`(지금 설정 (4, 2, 1) = 100)을 계산해서, 가장 작은 설정을 메모리 대비 시간 효율이 가장 좋은 설정으로 봤어요. 이 지표는 시간 1%와 메모리 1%를 같은 값으로 친다고 가정하고, 가장 긴 멈춤은 셈에 넣지 않아요. 값은 key 1,048,576개와 4,194,304개에서 (1, 0.5, 0.25)가 가장 작았고(68.8, 66.9), key 100,000개에서는 (2, 1, 0.5)가 가장 작았어요(81.4).

### 결정

처음에는 시간 × 메모리가 가장 작은 (1, 0.5, 0.25)를 골랐어요. 서버에서 재 보니(`server/007`) 조회 이득은 보이지 않았고, 버킷을 한 번 늘리는 멈춤(E)은 3회 가운데 2회에서 길어졌어요. 그래서 원인을 쪼개 봤어요.

- **조회 이득이 안 보인 이유:** 서버는 요청 하나에 CPU를 약 14 µs 쓰는데, 서버 없이 잰 조회 이득은 약 0.8 µs(약 5%)예요. 이 머신에서는 같은 빌드도 요청 하나의 CPU가 12.6\~17.3 µs로 흔들려서 이 차이를 가려낼 수 없었어요. 확인하지 못한 원인이에요.
- **멈춤이 길어진 이유:** 버킷을 늘리는 rehash는 entry를 옮기기 전에 새 버킷 배열을 할당하고 초기화해요. 그 일만 따로 재 보니 버킷 2,097,152개(64 MiB)는 약 35 ms, 8,388,608개(256 MiB)는 약 136 ms였어요. E에서 (4, 2, 1)은 64 MiB, (1, 0.5, 0.25)는 256 MiB를 만들므로, 약 100 ms 차이가 늘어난 멈춤과 같은 크기예요.

그래서 (2, 1, 0.5)로 한 단계 덜 줄였어요(2026-11-18). 새 배열이 128 MiB(약 72 ms)라서 멈춤 증가가 절반 정도이고, 메모리 증가도 4%예요. `server/008`은 머신 상태가 006과 달라서 이 변경의 효과를 판정하는 데 쓰지 않았어요. 멈춤을 줄이는 나눠 옮기기([`rehash-incremental.md`](rehash-incremental.md))는 보류했어요.
