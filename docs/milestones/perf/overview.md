# M7 `perf`: 성능 개선

## 요구사항

LMS에 따로 있는 요구사항은 아닙니다. L8(동시성 문제)과 L17(캐시 사용 전후 비교)이 남긴 측정 결과에서 출발합니다(`docs/requirements.md`).

## 앞 마일스톤

- M3 `concurrency`: 지연 목표는 "방해 요청이 있어도 작은 GET의 p99 10 ms 이하"이고, `make bench`로 잽니다. B(16 MiB 저장)와 E(버킷을 한 번 늘림)는 목표를 넘어 한계로 기록했습니다([server/003](../../measurements/server/003-DA-slower-rehash.md)).
- M4 `expire`: 주기 청소의 기본값을 S 25 ms, K 2,000, `POLL_INTERVAL_MS` 25 ms로 정했습니다. 그래서 요청이 없어도 서버가 초당 40번 깨어납니다([server/004](../../measurements/server/004-CJG-expire-sweep.md)).
- M5 `cache`: 상품 데모의 캐시 사용 전후를 시나리오 18개로 쟀습니다([cache-demo/004](../../measurements/cache-demo/004-CJG-sqlite-grid.md)). 같은 조건을 반복하는 목록은 빨라졌지만, 상세 조회는 캐시를 켜면 p50이 약 1.4 ms에서 약 8.6 ms로 늘었습니다.

## 진행 방식

이 마일스톤은 기능 하나가 아니라 측정된 증상을 하나씩 줄이는 일을 다룹니다. 그래서 6단계를 증상 하나에 한 번씩 돌지 않고, 아래 순서로 진행합니다.

1. **기준선:** 개선 전의 숫자를 측정 기록으로 고정합니다. `cache-demo/004`(커밋 `0b27d7b`)가 상품 데모의 기준선이고, [`server/005`](../../measurements/server/005-CJG-baseline.md)가 서버만 재는 기준선입니다. 두 기록 모두 같은 WSL2 머신에서 쟀습니다.
2. **증상:** 목표를 넘는 시나리오를 아래 "증상과 원인" 표에 한 줄씩 적습니다. 어디서, 어떻게, 얼마나 깨지는지 적습니다.
3. **원인 쪼개기:** 목표를 넘는 증상만 구간별로 다시 재서 원인을 찾습니다. code-review와 구조 검토에서 나온 발견은 이 단계에서 원인 후보로 붙입니다. 증상과 연결되지 않는 발견은 코드 품질 작업으로 따로 다루고, 반영한 뒤 한 번 다시 재서 성능이 바뀌지 않았다는 기록을 남깁니다.
4. **분류:** 범용과 구체는 시나리오가 아니라 원인에 붙입니다. 같은 시나리오가 두 원인으로 함께 느려질 수 있기 때문입니다. 판정 질문은 하나입니다. **"client를 바꿔도 이 원인이 남는가?"** 남으면 범용(mini-redis `src/`, `server/` 측정으로 재현됨)이고, 특정 client나 사용 방식에서만 나타나면 구체입니다.
5. **ticket:** ticket 하나는 원인 하나를 다룹니다. 고친 뒤 같은 도구로 다시 재서 새 번호의 측정 기록을 남깁니다.

### 목표

- **서버(`server/`):** M3와 같은 "방해 요청이 있어도 작은 GET의 p99 10 ms 이하"입니다.
- **client까지(`cache-demo/`와 이후 시나리오):** "적중률이 50% 이상인 시나리오에서 cache on의 p50이 cache off의 p50보다 크지 않다"입니다. 적중이 많은데도 캐시를 켜서 느려진다면 고쳐야 할 증상이기 때문입니다.

### 구체 ticket의 경계

- `main`에 들어가는 구체 ticket은 client 쪽 코드(`demo/`나 이후 시나리오 폴더)만 고칩니다. 범용 mini-redis가 특정 제품 하나에 맞춰 바뀌지 않게 하기 위해서입니다.
- `src/` 변경을 `main`에 넣으려면 판정 질문을 통과한 범용 ticket이어야 합니다.
- 실험 브랜치(`CONVENTION.md` 1번)에서는 구체 최적화가 `src/`를 고쳐도 됩니다. 쓸모 있다고 판명된 변경은 판정 질문을 통과시킨 뒤 개인 브랜치로 옮겨 PR을 올립니다.
- ticket마다 얻은 것과 함께 치른 값(늘어난 코드, 나빠진 다른 시나리오, 새로 생긴 설정값)을 적습니다.

### PR 단위

| PR | 담는 것 |
|---|---|
| A 틀과 기준선 | 이 `overview.md`, `server/005` 기준선, 실험 브랜치 규칙 |
| B 원인 쪼개기 | 구간별 측정에 필요한 측정 빌드 전용 코드, 그 측정 기록, 아래 표의 원인 칸 |
| C ticket 하나 | 고친 코드와 전후 측정 기록. 범용 ticket과 `main`에 들어가는 구체 ticket이 모두 이 단위입니다 |
| D 코드 품질 | 증상과 연결되지 않은 리뷰 발견과, 성능이 바뀌지 않았다는 측정 기록 |

- C PR은 각자 `main`에서 갈라지고 서로 기대지 않습니다. 팀원이 PR 하나를 받아들이거나 미뤄도 다른 PR이 막히지 않게 하기 위해서입니다.
- C PR의 측정 기록에서 `previous`는 PR을 올리는 시점에 `main`에 있는 가장 최근 기록입니다. 두 PR이 같은 코드 경로를 건드리면, 나중에 병합하는 쪽이 병합 직전에 관련 시나리오만 다시 잽니다.
- C PR의 본문은 증상, 원인, 바꾼 것, 얻은 것과 치른 값, 전후 기록의 순서로 씁니다. 팀원이 답보다 증상을 먼저 읽게 하기 위해서입니다. 아직 검토하기 어려운 PR은 draft로 올립니다.

## 증상과 원인

분류는 원인을 쪼개 재기 전이므로 잠정입니다. `기존 한계`는 README의 "알려진 한계"에 이미 적힌 항목이며, 원인을 쪼개 본 뒤에 다시 열지 판단합니다. 다시 열면 이 마일스톤의 `spec.md`에 밝힙니다.

| 증상 | 어디서 | 얼마나 | 원인 | 분류 (잠정) | 기존 한계 |
|---|---|---|---|---|---|
| 버킷을 늘리는 rehash 한 번에 서버가 멈춤 | [`server/005`](../../measurements/server/005-CJG-baseline.md) E | 작은 GET p99 443\~587 ms, 늘리는 저장 535\~676 ms | `hash.c`의 `rehash`가 entry 전부를 한 번에 옮김. 나눠 옮기도록 바꾼 뒤 다른 머신에서 p99 233\~250 → 0.21\~0.22 ms([`server/006`](../../measurements/server/006-DA-rehash-baseline.md) → [`server/007`](../../measurements/server/007-DA-incremental-rehash.md)) | 범용 | 예 |
| 16 MiB value를 저장하는 동안 서버가 멈춤 | [`server/005`](../../measurements/server/005-CJG-baseline.md) B | 작은 GET p99 24\~85 ms, 저장 p50 29\~44 ms | | 범용 | 예 |
| 측정 client가 멈춘 회에 p99가 튐 | [`server/005`](../../measurements/server/005-CJG-baseline.md) f 3회째, A 2회째 | p99 최대 117 ms, client 늦음 max 최대 43 ms | 측정 client(python)나 WSL로 추정, 확인하지 않음 | 측정 도구 | |
| 요청이 없어도 서버가 초당 40번 깨어남 | `server/004`, [`idle-wakeup/001`](../../measurements/idle-wakeup/001-CJG-baseline.md) | 초당 약 40번 | 할 일과 상관없이 `mg_mgr_poll`이 25 ms(`POLL_INTERVAL_MS`)마다 깨어남 | 범용 | 예 |
| 상세 조회에서 캐시를 켜면 느려짐 | `cache-demo/` 상세 | p50 약 1.4 → 8.6 ms, 적중률 33\~53% | | 미정 | |
| 다양한 조건에서 cache on의 p95가 튐 | `cache-demo/` 목록·검색 다양 | p95 최대 약 496 ms | 확인하지 않음 | 미정 | |
| 수정이 섞이면 목록·검색 적중률이 떨어짐 | `cache-demo/` 반복 90:10 | 적중률 약 90% | 목록·검색 캐시 전체를 무효화하는 설계 | 구체 | 예 |

README의 나머지 한계 가운데 eviction은 LMS에 없어 이 표에 넣지 않습니다. client가 알아야 할 한계는 성능이 아니라 정확성의 문제이므로 이 마일스톤 밖에 둡니다. 해시 seed는 안전성의 문제지만, hash 함수를 바꾸는 성능 실험과 함께 정했습니다([`ideas/hash-function.md`](ideas/hash-function.md), ADR [`siphash-with-random-seed`](../../adr/siphash-with-random-seed.md)).

## 새 활용 사례 후보

새 제품이나 활용 사례는 떠오르는 대로 한 줄씩 적고, ticket은 만들지 않습니다. 범용 ticket이 끝난 뒤에 시나리오로 다듬습니다. 고르는 기준은 "지금 상품 데모에 없는 요청 패턴을 더하는가"입니다. 상품 데모는 조회가 많고 value가 작으므로, 쓰기가 많은 패턴, 보관 기간을 많이 쓰는 패턴, 큰 value가 빈칸입니다. 탐색은 실험 브랜치에서 하고, 그 브랜치를 링크합니다.
