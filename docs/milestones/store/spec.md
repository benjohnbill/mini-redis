# M1 `store` spec

Status: ready-for-agent

요구사항: L2, L4, L13 (`docs/requirements.md`). 문제는 `overview.md`에 있고, 이 문서는 2단계 grill(2026-11-13)에서 팀이 합의한 답입니다.

## Problem Statement

M0이 끝난 지금, 레포에는 Pintos `hash.c`가 빌드되어 있지만 그 위에서 key로 value를 넣고, 꺼내고, 지우는 코드가 없습니다. M2에서 다른 서버가 HTTP로 부를 대상도 아직 없습니다. 팀은 `hash.c`의 인터페이스(`hash_insert`, `hash_replace`, `hash_find`, `hash_delete`)를 어떻게 써야 key 하나를 평균 상수 시간에 찾는지, 같은 key에 두 번 넣으면 무엇이 남는지, key와 value의 메모리를 누가 책임지는지 코드로 확인하고 설명할 수 있어야 합니다.

## Solution

`hash.c` 위에 store를 만듭니다. store는 key와 value를 바이트 묶음(주소와 길이 한 쌍)으로 받아 entry로 복사해 보관하고, 공개 함수 다섯 개로 만들기, 없애기, 저장, 조회, 삭제를 제공합니다. store는 HTTP를 모릅니다. M1 테스트는 서버 없이 공개 함수만 불러서 저장, 조회, 삭제가 정상으로 동작하는지 확인합니다(L13).

## User Stories

1. 팀원으로서, store를 하나 만들 수 있기를 원합니다. 그래야 서버가 시작할 때 store 하나를 만들어 끝까지 쓸 수 있습니다.
2. 팀원으로서, 다 쓴 store를 없애면 그 안의 모든 entry가 해제되기를 원합니다. 그래야 AddressSanitizer가 누수를 보고하지 않습니다.
3. 팀원으로서, key와 value를 주소와 길이 한 쌍으로 넘기기를 원합니다. 그래야 HTTP 요청 버퍼의 한 구간을 `'\0'`을 붙이지 않고 그대로 넘길 수 있습니다.
4. 팀원으로서, 중간에 `'\0'` 바이트가 있는 value를 저장하고 그대로 돌려받기를 원합니다. 그래야 이미지 같은 바이너리 body도 잘리지 않습니다.
5. 팀원으로서, `store_set`이 돌아온 뒤에 내 버퍼를 다시 써도 저장된 key와 value가 바뀌지 않기를 원합니다. 그래야 서버가 다음 요청을 같은 버퍼에 받을 수 있습니다.
6. 팀원으로서, 저장한 key를 조회하면 저장한 value와 그 길이를 받기를 원합니다.
7. 팀원으로서, 없는 key를 조회하면 "찾지 못함"을 반환값으로 받기를 원합니다. 그래야 value의 주소를 보고 추측하지 않아도 됩니다.
8. 팀원으로서, 0바이트 value를 저장하고 조회하면 "찾았고 길이 0"을 받기를 원합니다. 그래야 빈 value와 없는 key를 구분할 수 있습니다.
9. 팀원으로서, 0바이트 key도 다른 key처럼 저장, 조회, 삭제할 수 있기를 원합니다. 빈 key를 HTTP에서 받을지는 M2가 정합니다.
10. 팀원으로서, 같은 key에 두 번 저장하면 나중 value 하나만 남기를 원합니다.
11. 팀원으로서, 같은 key에 두 번 저장한 뒤 한 번 삭제하면 그 key가 완전히 없어지기를 원합니다. 그래야 옛 entry가 테이블에 숨어 남지 않았음을 확인할 수 있습니다.
12. 팀원으로서, 덮어쓰기에 필요한 메모리를 잡지 못하면 `store_set`이 실패를 알리고 옛 value가 그대로 남기를 원합니다.
13. 팀원으로서, 길이가 다르고 앞부분이 같은 두 key(`"abc"`, `"abcd"`)가 서로 다른 key로 다뤄지기를 원합니다.
14. 팀원으로서, 있는 key를 삭제하면 "지웠음"을, 없는 key를 삭제하면 "지운 것이 없음"을 받기를 원합니다. 두 번째 결과는 오류가 아닙니다.
15. 팀원으로서, 한 key를 삭제해도 다른 key는 그대로 조회되기를 원합니다.
16. 팀원으로서, key를 수천 개 넣어 rehash가 일어난 뒤에도 모든 key를 조회할 수 있기를 원합니다.
17. 팀원으로서, 조회로 받은 value의 주소가 언제까지 유효한지 헤더 주석에서 읽을 수 있기를 원합니다. 그래야 조회 뒤에 같은 store를 바꾸고 옛 주소를 쓰는 실수를 피할 수 있습니다.
18. 팀원으로서, 조회로 받은 value를 실수로 고치지 못하도록 읽기 전용 주소로 받기를 원합니다.
19. 팀원으로서, 길이가 0이 아닌데 주소가 `NULL`인 인자처럼 우리 코드의 버그로만 생기는 호출은 그 자리에서 멈추기를 원합니다. 그래야 원인과 증상이 멀어지지 않습니다.
20. 테스트 작성자로서, 테스트마다 새 store를 만들고 없애기를 원합니다. 그래야 앞 테스트의 key가 다음 테스트에 남지 않습니다.
21. 테스트 작성자로서, 공개 함수만 불러서 모든 동작을 확인하기를 원합니다. 그래야 내부 구조를 바꿔도 테스트가 그대로 남습니다.
22. 팀원으로서, store와 entry라는 이름이 `GLOSSARY.md`의 뜻대로 코드에 쓰이기를 원합니다. 그래야 발표에서 같은 대상을 같은 이름으로 설명할 수 있습니다.
23. 발표하는 팀원으로서, key 하나가 버킷을 고르고 그 버킷 안에서 비교되는 두 단계를 코드에서 짚어 설명하기를 원합니다(L4).
24. 발표하는 팀원으로서, rehash가 언제 일어나고 그동안 무엇이 멈추는지 설명하기를 원합니다(L4, overview 5번).
25. M2를 만들 팀원으로서, store가 HTTP 라이브러리의 타입을 모르기를 원합니다. 그래야 M2에서 라이브러리를 바꿔도 store 코드는 그대로 남습니다.

## Implementation Decisions

- **모듈:** store 모듈 하나를 새로 만듭니다. 공개 헤더는 함수 다섯 개만 내보내고, entry 구조체와 hash 함수, less 함수는 모듈 안에 숨깁니다. `hash.c`와 `list.c`는 고치지 않습니다.
- **Q1 key와 value의 모양:** 모든 공개 함수는 key를 `const void *`와 `size_t` 길이 한 쌍으로 받습니다. `store_set`은 value도 같은 모양으로 받습니다. store는 HTTP 라이브러리의 타입을 쓰지 않습니다. 이유(팀원 문장): HTTP 요청에서 꺼낸 key와 value는 받은 버퍼의 한 구간이라서 끝에 `'\0'`이 없고, value는 중간에 `'\0'`을 포함할 수 있습니다. value의 길이는 `Content-Length`가 이미 알려줍니다.
- **Q2 핸들:** `store_create`가 store를 만들어 주소를 돌려주고, 나머지 함수는 그 주소를 첫 인자로 받습니다. 서버는 store를 하나만 만듭니다. 메모리가 부족하면 `store_create`는 `NULL`을 돌려줍니다.
- **Q3 공개 함수:** `store_create`, `store_destroy`, `store_set`, `store_get`, `store_delete` 다섯 개입니다. 개수 세기나 존재 확인 함수는 쓰는 곳이 생기는 마일스톤에서 추가합니다.
- **Q5 메모리 소유:** `store_set`은 key와 value의 바이트를 store의 메모리로 복사합니다. entry를 해제하는 것도 store입니다(덮어쓰기, 삭제, `store_destroy`). 이유: 서버는 다음 요청을 받으려고 같은 소켓 버퍼를 다시 씁니다.
- **Q6 해시와 비교:** hash 함수는 entry의 key 바이트에 `hash_bytes`를 적용합니다. value는 해시하지 않습니다. less 함수는 짧은 쪽 길이만큼 key를 `memcmp`로 비교하고, 결과가 같으면 길이가 짧은 쪽을 작다고 봅니다. `hash.c`는 `less(a, b)`와 `less(b, a)`가 모두 거짓이면 같은 key로 판단하므로, 길이 비교가 없으면 `"abc"`와 `"abcd"`를 같은 key로 봅니다.
- **Q7 조회:** `store_get`은 "찾았는가"를 `bool`로 돌려주고, value는 store 안의 읽기 전용 주소와 길이로 빌려줍니다. 그 주소는 같은 store에 다음 `store_set` 또는 `store_delete`를 부르기 전까지만 유효하며, 이 규칙을 공개 헤더의 주석에 적습니다. 이유(팀원 문장): 요청을 하나씩 끝까지 처리하면 요청을 받고 반환하는 과정 중간에 같은 key를 덮어쓰거나 삭제하는 일이 일어나지 않습니다. 스레드 수는 M3에서 정하며, 그때 이 결정을 다시 봅니다.
- **Q8 덮어쓰기:** `store_set`은 새 entry(key와 value 복사본)를 먼저 다 만든 뒤 `hash_replace`로 넣고, 밀려난 옛 entry를 통째로 해제합니다. 메모리 할당이 하나라도 실패하면 테이블을 건드리지 않고 `false`를 돌려줍니다. `store_set`이 `false`를 돌려주는 경우는 메모리 부족뿐입니다. key와 value 길이의 합이 `size_t`를 넘어 할당 크기를 계산할 수 없는 경우도 할당 실패로 보고 `false`를 돌려줍니다(5단계 코드 리뷰에서 추가). 이유(팀원 문장): 분기 처리에서 훨씬 더 편합니다.
- **Q9 삭제:** `store_delete`는 `hash_delete`로 entry를 빼고 해제한 뒤 `true`를 돌려줍니다. 없는 key면 `false`를 돌려주며, 이것은 오류가 아닙니다.
- **Q10 빈 key와 빈 value:** 0바이트 key와 0바이트 value를 모두 허용합니다. 길이가 0이면 호출한 쪽은 주소로 `NULL`을 넘겨도 됩니다.
- **Q10 구현 주의:** `hash_bytes`는 주소가 `NULL`이면 assert로 멈추고, C11에서 `memcmp`에 `NULL`을 넘기는 것은 길이가 0이어도 정의되지 않은 동작입니다. 그래서 store는 길이가 0인 key와 value를 보관하거나 비교할 때 내부의 유효한 주소를 씁니다. 0바이트 복사에 `malloc(0)`이 `NULL`을 돌려줄 수 있는 점도 같은 방법으로 피합니다. 조회 결과의 "찾았는가"는 반환값만으로 판단하므로, 0바이트 value의 주소가 무엇이든 동작은 같습니다.
- **Q11 잘못된 인자:** 길이가 0이 아닌데 주소가 `NULL`인 key나 value, `NULL` store, `NULL` 출력 인자는 `assert`로 멈춥니다. 외부 입력의 검사는 M2가 맡습니다.
- **Q4 rehash:** `hash.c`의 rehash(원소를 한 번에 새 버킷 배열로 옮김)를 그대로 받아들입니다. 그동안 `store_set` 한 번이 오래 걸리는 문제는 M3 `concurrency`로 넘깁니다.
- **용어:** `GLOSSARY.md`의 store(`struct store`)와 entry(`struct entry`)를 씁니다. "해시 테이블"은 `hash.c`의 `struct hash`만 가리킵니다.

## Testing Decisions

- **좋은 테스트:** 공개 함수 다섯 개만 불러서 바깥에서 보이는 동작을 확인합니다. 기대값은 검사 대상 함수로 계산하지 않고 직접 적습니다. entry 구조체, less 함수, 버킷 수 같은 내부는 확인하지 않습니다.
- **seam:** store의 공개 함수 하나뿐입니다(팀 확인 2026-11-13). 서버와 store의 연결은 M2에서 다루므로, M1에는 기능 테스트가 없습니다.
- **파일과 도구:** CONVENTION대로 마일스톤 하나에 테스트 파일 하나이고, acutest의 `TEST_LIST`에 한국어 문장 이름을 적습니다. 선례는 M0의 하네스 테스트입니다. 빌드 설정은 새 소스와 테스트 파일을 자동으로 찾으므로 바꾸지 않습니다.
- **격리:** 테스트마다 `store_create`로 새 store를 만들고 끝에서 `store_destroy`합니다. `make verify`의 AddressSanitizer가 누수와 해제된 메모리 사용을 잡습니다.
- **시나리오 후보(4단계에서 팀이 확인):** 저장 후 조회, 없는 key 조회, 빈 value와 없는 key의 구분, 빈 key, `'\0'`을 포함한 value, 저장 뒤 호출한 쪽 버퍼를 바꿔도 값 유지, 같은 key에 두 번 저장, 두 번 저장 뒤 삭제하면 조회되지 않음, `"abc"`와 `"abcd"`의 구분, 있는 key와 없는 key의 삭제, 한 key 삭제 뒤 다른 key 유지, key 수천 개 저장 뒤 전부 조회(rehash).
- **리뷰에서 더한 시나리오:** 5단계 코드 리뷰에서 "0바이트 key도 삭제할 수 있다"(User Story 9)와 "key와 value 길이의 합이 너무 크면 저장에 실패하고 store는 그대로다"를 더했습니다. 팀이 4단계에서 확인한 목록에는 없던 시나리오입니다.
- **테스트하지 않는 것:** 메모리 할당 실패(User Story 12)는 할당 함수를 바꿔 끼울 seam이 없어서 M1에서 자동 테스트하지 않고, 코드 순서(새 entry를 먼저 다 만든 뒤 넣기)와 리뷰로 확인합니다. assert로 멈추는 경우(User Story 19)도 테스트하지 않습니다.
- **ID:** ADR의 `결정:` 줄이나 `docs/requirements.md`의 `근거` 칸이 인용하는 테스트에만 ID를 붙입니다. 어느 테스트를 인용할지는 4단계에서 정합니다.

## Out of Scope

- HTTP로 store를 부르는 일, 요청 해석, 빈 key를 HTTP에서 받을지 여부: M2 `api`.
- 여러 스레드, 조회한 주소의 수명 재검토, rehash 동안 멈추는 시간: M3 `concurrency`.
- 보관 기간: M4 `expire`.
- 개수 세기, 존재 확인, 여러 key 한 번에 삭제 같은 추가 함수.
- key와 value의 최대 길이 제한.
- 해시 seed(아래 `Redis와 대조` 참고): 6단계에서 README "알려진 한계"에 적을지 정합니다.
- eviction: README "알려진 한계"에 이미 있습니다.

## Redis와 대조

Redis 7.2 소스(`dict.c`, `db.c`, `server.c`, `sds.h`)로 확인했습니다. 6단계에서 팀이 배운 것을 이 절에 더합니다.

| 주제 | 우리 생각 | Redis의 방식 | 우리가 고른 것 |
|---|---|---|---|
| key와 value의 모양 | `'\0'`에 기대지 않고 길이를 함께 받아야 합니다. | `sds` 문자열의 헤더에 `len`이 있어, 길이를 `'\0'`을 찾지 않고 헤더에서 읽습니다. | 주소와 길이 한 쌍. 같은 생각입니다. |
| 메모리 소유 | store가 복사해서 갖습니다. | keyspace의 dict 타입이 key 해제 함수와 value 해제 함수를 갖고, 테이블이 메모리를 소유합니다. | 복사. 같은 생각입니다. |
| 해시와 비교 | key 바이트만 해시하고, 비교는 `memcmp` 뒤 길이로 합니다. | 해시는 seed를 섞는 SipHash입니다. 비교 함수는 길이를 먼저 비교하고 같을 때만 `memcmp`하며, 대소가 아니라 같은지만 묻습니다. seed는 서버가 시작할 때마다 `getRandomBytes`로 16바이트를 만들어 `dictSetHashFunctionSeed`에 넘깁니다(`server.c`의 `main`). | `hash_bytes`(seed 없는 FNV)와 less. `hash.c`가 같은지가 아니라 대소를 묻기 때문입니다. |
| 덮어쓰기 | entry 전체를 바꿔 끼웁니다. | 기존 entry의 key는 두고 value만 바꿔 끼운 뒤 옛 value를 해제합니다. | `hash_replace`로 entry 전체 교체. Redis와 다릅니다. |
| 없는 key 삭제 | 오류가 아니라 "지운 것이 없음"입니다. | `DEL`은 지운 key의 개수를 돌려주고, 없으면 0입니다. 여러 key를 한 번에 지울 수 있어서 개수입니다. | `bool`. 같은 생각입니다. |
| rehash | 한 번에 옮기고, 멈추는 시간은 M3로 넘깁니다. | 테이블 두 개를 두고 어디까지 옮겼는지 기억하며, 조회와 삭제 때마다 버킷을 조금씩, 주기 작업이 1ms씩 옮깁니다. 옮기는 동안 새 key는 두 번째 테이블에 넣습니다. | Pintos의 한 번에 옮기는 rehash. Redis와 다릅니다. |
| 충돌 처리 | 버킷마다 체인을 둡니다. | 버킷마다 단방향 리스트이고, 새 entry를 맨 앞에 넣습니다. | Pintos의 양방향 리스트. 둘 다 체이닝입니다. |
